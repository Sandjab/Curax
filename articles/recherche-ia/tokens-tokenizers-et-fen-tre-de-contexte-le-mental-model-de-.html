02 - Tokens, Tokenizers, and Context Windows
Previous Article
01 - Inference and Sequences
Most think an LLM reads words.
It does not.
Before a local model can answer you, your text gets chopped into smaller pieces called tokens, converted into numbers, and placed inside a limited working space called the context window.
Once you understand that, a lot of “LLM weirdness” starts making sense:
  • Why long prompts slow things down
  • Why models sometimes “forget” earlier messages
  • Why output length matters
  • Why different models count text differently
  • Why “context length” is one of the most important specs in local AI
This article gives you the mental model.

What you’ll learn

By the end, you’ll understand:
  • What tokens actually are
  • What a tokenizer does
  • Why tokens are not the same as words
  • What a context window really means
  • Why input and output share the same token budget
  • Why long conversations eventually lose older information

The model does not see text directly

When you type:
Explain local LLMs like I’m new to AI.
The model does not receive that sentence as human-readable text.
First, the text passes through a tokenizer.
The tokenizer splits the text into pieces, then maps each piece to a number.
The model sees those numbers.
A simplified version looks like this:
plaintext
Text:
"Local LLMs are useful"

Tokenizer:
["Local", " L", "LM", "s", " are", " useful"]

Token IDs:
[9012, 426, 11234, 82, 527, 6043]
The exact split depends on the tokenizer.
  • Some tokens are whole words.
  • Some are word fragments.
  • Some include spaces.
  • Some are punctuation.
  • Some are special control tokens used for chat formatting.
The key point: the model operates on token IDs, not raw text.
Takeaway: An LLM does not read your prompt as words. It reads a sequence of token numbers produced by its tokenizer.

Tokens are chunks, not words

A token is usually a chunk of text.
That chunk might be:
  • A full word: apple
  • Part of a word: app + le
  • A space plus a word: hello
  • A punctuation mark: .
  • A number fragment: 202 + 6
  • A special marker: beginning-of-text, end-of-text, user message, assistant message
This is why “token count” and “word count” are not the same.
For English text, a rough rule of thumb is:
plaintext
1 token ≈ 3 to 4 characters
100 tokens ≈ 75 words
1,000 tokens ≈ 750 words
But this varies a lot.
Code, JSON, math, emojis, non-English languages, and weird formatting can tokenize very differently.
For example:
plaintext
"hello" might be 1 token
"antidisestablishmentarianism" might be several tokens
"🔥🚀" might be multiple tokens
"my_variable_name" might be split into pieces
So when a model says it supports “8K context,” that does not mean 8,000 words.
It means roughly 8,000 tokens.
Takeaway: Tokens are the model’s text units. They are related to words, but they are not the same thing.

The tokenizer is the text-to-number translator

A tokenizer is the system that converts text into token IDs and converts generated token IDs back into text.
It does two jobs:
  1. Encode text into tokens
  2. Decode tokens back into text
Encoding
plaintext
"Local models are fun"
→ [31291, 4211, 527, 2523]
Decoding
plaintext
[31291, 4211, 527, 2523]
→ "Local models are fun"
This matters because the model was trained with a specific tokenizer.
The tokenizer defines the model’s vocabulary: the set of token pieces it knows how to represent.
If you use the wrong tokenizer with a model, the input IDs will not match what the model learned during training. The result can be broken, incoherent, or unusable.
This is why model packages usually include tokenizer files alongside weights and config files.
You do not just need “the model.” You need the model and the tokenizer that matches it.
Takeaway: The tokenizer is not an optional helper. It is part of how the model understands text.

Different models split text differently

Not all tokenizers behave the same way.
Two models can receive the same sentence and split it into different token sequences.
Example:
plaintext
Text:
"Tokenization matters."

Tokenizer A:
["Token", "ization", " matters", "."]

Tokenizer B:
["Tokenization", " matters", "."]
Both can work. But the model trained with Tokenizer A expects Tokenizer A’s IDs.
The model trained with Tokenizer B expects Tokenizer B’s IDs.
This is one reason token counts vary across models.
You might paste the same prompt into two different local models and see different token usage. That does not necessarily mean one model is smarter. It may just tokenize the text differently.
This also affects practical usage.
A tokenizer that handles code, non-English text, or symbols more efficiently may fit more useful information into the same context window.
Takeaway: Token counts are model-specific. The same text can cost different numbers of tokens depending on the tokenizer.

Context window means active working space

The context window is the maximum number of tokens the model can actively consider at one time.
If a model has an 8K context window, it can work with about 8,000 tokens in the active sequence.
If it has a 32K context window, it can work with about 32,000 tokens.
If it has a 128K context window, it can work with about 128,000 tokens.
But the phrase “context window” is easy to misunderstand. It does not mean the model permanently remembers 128K tokens.
It means the model can actively process up to that many tokens in the current session input.
That active context can include:
  • System prompt
  • Chat template tokens
  • User messages
  • Assistant messages
  • Retrieved text
  • Tool outputs
  • Code
  • Instructions
  • The model’s own generated answer
Everything in the active sequence consumes part of the budget.
Takeaway: Context window is the model’s active token budget, not permanent memory.

Input and output share the same budget

This is one of the most important beginner concepts.
The context window is shared by both:
  1. The prompt you send in
  2. The answer the model generates
If your model has an 8K context window and your prompt already uses 7,500 tokens, there is not much room left for the reply.
A simplified view:
plaintext
Total context window:
8,000 tokens

Input prompt:
7,000 tokens

Available space for output:
~1,000 tokens
This is why a long prompt can crowd out the answer.
You may ask for a detailed explanation, but if the prompt, chat history, and pasted documents already fill the context, the model has less room to generate.
  • In some systems, generation may stop early.
  • In others, older tokens may be dropped.
  • In others, the runtime may reject the prompt because it does not fit.
Local inference makes this very visible because you often control the context size directly.
Takeaway: Context is not just about how much you can paste in. It also limits how much the model can answer.

Long prompts are not free

A longer context window is useful, but it is not magic. The model has to process the tokens you give it.
More tokens usually means:
  • More memory use
  • More compute work
  • Slower prompt processing
  • Larger KV cache during generation
  • More pressure on your hardware
On local hardware, this matters a lot. A short prompt may start generating quickly. A huge prompt with thousands of tokens may spend noticeable time processing before the first output token appears.
This is sometimes called prompt processing or prefill. You give the model a sequence. The runtime processes that sequence.
Then the model starts generating one token at a time.
Long prompts make that first stage heavier.
This is why bigger context windows are not always better in practice.
A 128K context model sounds amazing, but actually using 128K tokens locally can require serious memory and compute.
Takeaway: Longer context gives you more room, but it can slow down local inference and increase memory use.

Why models seem to forget

When people say “the model forgot,” they often mean one of two things.
First, the information was never in the model’s active context.
Second, the information used to be in context, but it got pushed out.
Imagine a conversation that keeps growing:
plaintext
Message 1
Message 2
Message 3
Message 4
...
Message 80
If the full conversation no longer fits inside the context window, something has to give.
Depending on the app or runtime, older messages may be:
  • Truncated
  • Summarized
  • Dropped
  • Replaced with a shorter memory note
  • Hidden from the model entirely
From the user’s perspective, it feels like the model forgot. From the model’s perspective, the earlier tokens are no longer present.
The model cannot reliably use information that is not in its active context, unless it was already learned during training or stored and reinserted by another system.
This distinction matters:
  • Context: tokens currently visible to the model
  • Training knowledge: patterns stored in the model weights
  • Chat history: messages saved by an app
  • Long-term memory: external notes or database entries reintroduced later
These are not the same thing.
We will cover this more deeply in a later article on KV cache and session memory.
For now, keep the simple version:
If it is not in the active context, do not assume the model can use it.
Takeaway: Models “forget” when relevant information falls outside the active context or is not reinserted by the app.

Context length changes how you prompt

Once you understand token budgets, prompting becomes more practical.
You stop thinking:
“How much text can I dump into the model?”
And start thinking:
“What information does the model actually need in its active context to answer well?”
That shift matters.
A short, precise prompt often beats a giant messy one.
Useful context improves output.
Irrelevant context can dilute the signal.
For example, if you ask a local model to summarize a project, you do not always need to paste every file.
You may get better results by giving it:
  • The goal of the project
  • The relevant file
  • The specific question
  • A short description of what you want back
  • Any constraints it must follow
Context is a budget. Spend it on what matters.
Takeaway: Better prompting is not always more context. Better prompting is the right context.

A simple token budget framework

Here is the save-worthy mental model:
plaintext
Every LLM conversation has a token budget.

That budget is spent on:

1. System instructions
2. Chat formatting
3. User prompt
4. Conversation history
5. Pasted documents or code
6. Retrieved information
7. The model’s answer
Before sending a big prompt, ask:
  1. What must the model know?
  2. What can I remove?
  3. How long should the answer be?
  4. Will old chat history crowd out the important part?
  5. Does this task need a bigger context model, or just a cleaner prompt?
This is the practical local LLM mindset.
Context is not infinite. Tokens are the currency. The tokenizer is the exchange rate.
Takeaway: Treat context like working memory with a fixed budget. Spend tokens intentionally.

Practical next step

Try this with any local model UI that shows token counts.
Paste three versions of the same request:
  1. A short prompt
  2. A long prompt with lots of extra context
  3. A cleaner prompt with only the necessary context
Compare:
  • Token count
  • Time to first token
  • Output quality
  • Whether the answer follows your instructions
  • Whether the model misses anything important
You will quickly build intuition for how context affects behavior.
If your tool does not show token counts, try a tokenizer viewer for the model family you are using.
Do not worry about perfect numbers yet.
Just start noticing the relationship between text length, token count, speed, and answer quality.
Takeaway: The fastest way to understand tokens is to compare how different prompts consume context.

The core mental model

Here is the whole article in one picture:
And the key rule:
plaintext
Input tokens + output tokens must fit inside the context window.
That one rule explains a lot of local LLM behavior.
  • It explains why long prompts slow down.
  • It explains why answers can get cut short.
  • It explains why older conversation can disappear.
  • It explains why tokenizer choice matters.
  • It explains why context length is a real hardware and workflow constraint.
Takeaway: Tokens are the units, tokenizers are the translators, and context windows are the active workspace.
