06 - KV Cache and Session Memory
Previous Article -
05 - Generation, Softmax, Greedy, and Sampling
A local LLM can continue a conversation because the runtime keeps the active context available, and because the KV cache lets the model reuse work it already did.
That sounds like memory, but it is not the same thing as learned knowledge, a database, or long-term personal memory.
In this article, we’ll separate four ideas that beginners often mix together:
  • Context
  • Chat history
  • KV cache
  • Long-term memory
Once you understand the difference, local LLM behavior becomes much less mysterious.

What you’ll learn

By the end, you’ll understand:
  • Why local LLMs can continue a conversation
  • What the KV cache actually stores
  • Why the KV cache makes generation faster
  • Why “session memory” is not the same as real memory
  • Why models forget things when they fall outside the context window

The beginner misconception

A common beginner explanation sounds like this:
“The model remembers what I said earlier.”
That is directionally useful, but technically sloppy.
The model itself is not rewriting its weights during your chat. It is not permanently learning your preferences. It is not adding your messages to its internal knowledge.
Instead, the runtime keeps your previous tokens in the active session, and the model can attend to those tokens while generating the next token.
That active session is temporary.
Takeaway: During normal inference, the model is not learning from your conversation. It is using the conversation as active context.

Context is the model’s working area

In
Article 02
, we covered context windows.
A context window is the maximum number of tokens the model can actively use at one time.
If your local model has an 8k context window, that means the active conversation can contain up to around 8,000 tokens, including:
  • System prompt
  • User messages
  • Assistant messages
  • Tool outputs, if any
  • Any text you paste in
  • The answer being generated
The model does not see your entire life. It does not see every previous chat by default. It only sees what the runtime includes in the current context.
If something is inside the active context, the model can use it.
If something is outside the active context, the model usually cannot use it unless another system retrieves and inserts it.
Takeaway: Context is the model’s temporary working area. If information is not in that working area, the model cannot reliably reason about it.

Chat history is just text in the session

When you use a chat interface, it may look like the model has a persistent conversation memory.
But most of the time, chat history is simply previous messages being included in the prompt again.
A simplified chat might look like this internally:
plaintext
System: You are a helpful assistant.

User: My name is Maya.

Assistant: Nice to meet you, Maya.

User: What is my name?
The model can answer “Maya” because the earlier message is still present in the active context.
It is not because the model permanently stored the fact.
If the earlier message gets removed, truncated, summarized badly, or left out of the next prompt, the model may not know the answer.
Takeaway: Chat history only works as memory while it remains available to the model.

The expensive part: rereading the whole conversation

Now we get to the performance problem. LLMs generate one token at a time.
At each step, the model needs to understand the tokens that came before the next token.
Without optimization, the model would need to repeatedly process the entire previous context every time it predicts a new token.
That would be painfully inefficient.
Imagine asking the model to write a 1,000-token answer after a long prompt.
A naive process would look like this:
plaintext
Read full prompt → predict token 1
Read full prompt + token 1 → predict token 2
Read full prompt + token 1 + token 2 → predict token 3
Read full prompt + token 1 + token 2 + token 3 → predict token 4
...
The longer the sequence gets, the more wasteful this becomes.
The model has already done a lot of work for the earlier tokens. Repeating all of it from scratch would be slow.
This is where KV cache comes in.
Takeaway: Autoregressive generation repeats the next-token process many times, so reprocessing the entire past from scratch would waste a huge amount of compute.

What the KV cache stores

KV cache stands for Key-Value cache.
To understand it at a high level, you only need one idea:
The model creates internal attention data for each token it processes. That attention data helps future tokens decide which previous tokens matter.
Instead of recomputing all of that attention data again and again, the runtime saves part of it.
That saved data is the KV cache.
The KV cache does not store human-readable memories like:
plaintext
User likes small local models.
User prefers short answers.
User works on Linux.
It stores intermediate model states used by attention.
A better mental model:
plaintext
Tokens in context:
[The] [cat] [sat] [on] [the] [mat]

Model computes attention-related data:
K/V data for "The"
K/V data for "cat"
K/V data for "sat"
K/V data for "on"
K/V data for "the"
K/V data for "mat"

Runtime keeps this cached so future tokens can reuse it.
When the model generates the next token, it can use the cached key/value data for previous tokens instead of recomputing everything from scratch.
Takeaway: The KV cache stores internal attention data for previous tokens. It is a speed optimization, not a memory database.

Why KV cache makes generation faster

KV cache matters because local inference has two different phases:
  1. Prompt processing
  2. Token generation
Prompt processing happens when the model reads the input tokens. If you paste a long prompt, the model has to process all of those tokens before it can start generating a useful answer.
Token generation happens after that, one new token at a time.
With KV cache, the model can reuse the processed state of the previous tokens while generating new tokens.
This is why continuing a response can be much faster than rereading the whole conversation from zero each time.
The runtime does not need to rebuild everything from scratch for every new token. It keeps the previous attention information available.
Takeaway: KV cache speeds up continuation by reusing prior attention computations.

KV cache is not free

The KV cache saves compute, but it costs memory. The longer your active context, the more KV cache data the runtime may need to hold.
This is one reason long context can become expensive on local hardware.
A bigger context window does not just mean “the model can read more.”
It also means:
  • More tokens to process
  • More attention state to store
  • More memory pressure
  • Potentially slower prompt ingestion
  • Larger session state
This is especially important when running local models on limited VRAM or system RAM.
A small model with a short context may feel fast and responsive.
The same model with a huge active context may feel slower or use much more memory.
Takeaway: KV cache trades memory for speed. Longer context usually means more cache memory pressure.

Session memory: what people usually mean

When people say a local LLM has “session memory,” they usually mean one of three things:
  1. The chat app keeps previous messages in the active prompt
  2. The runtime keeps a KV cache for the current context
  3. The app saves conversation history and reloads it later
These are useful, but none of them mean the model has permanently learned.
Let’s separate them:
Chat history
  • Human-readable messages
  • Stored by the app
  • Can be inserted into future prompts
  • Limited by context window
KV cache
  • Internal attention data
  • Stored by the runtime during inference
  • Speeds up continuation
  • Not human-readable
Saved sessions
  • Files or app state saved on disk
  • Can restore a conversation later
  • Still must be loaded into context to affect output
Learned weights
  • The model’s parameters
  • Created during training or fine-tuning
  • Not changed by normal chatting
Takeaway: “Session memory” usually means temporary context and runtime state, not permanent learning.

The model only uses what it can see

Here is the practical rule:
If the model needs to use some information, that information must be available somehow.
Usually, that means one of these:
  • It is already in the model’s trained weights
  • It is inside the current context
  • It is retrieved from an external memory system and inserted into context
  • It is provided by a tool
  • It was added through fine-tuning or continued training
If none of those are true, the model cannot reliably use the information.
This explains a lot of “forgetting.”
The model may forget because:
  • The chat became longer than the context window
  • Older messages were dropped
  • A summary removed important details
  • A new session started without the old chat
  • The app did not reload previous state
  • The information was never included in the first place
This is not the model being moody.
It is a context management issue.
Takeaway: For a model to use information, that information must be in weights, context, tools, retrieved memory, or fine-tuned state.

Why older messages disappear

Context windows are finite.
When a conversation gets too long, the app or runtime has to make a choice.
It may:
  • Keep the most recent messages
  • Drop old messages
  • Summarize old messages
  • Ask you to start a new chat
  • Use a larger context setting
  • Store older information somewhere else
Different tools handle this differently.
But the core constraint is the same: the model can only attend to the tokens that fit inside its active context.
If your first message contained a key detail and that message later falls out of context, the model may stop using that detail.
It may still guess correctly if the answer is obvious, but it is no longer grounded in that earlier message.
Takeaway: Forgetting often happens because old tokens fall out of the active context window.

How this feels in local inference

When you run a local LLM, these concepts show up in very practical ways.
You may notice:
  • The first response after a long prompt takes longer to start
  • Continuing a response feels faster once the prompt is processed
  • Long chats consume more memory
  • Larger context settings increase resource use
  • Restarting the app can lose the active session
  • Reloaded chats may not behave exactly like uninterrupted chats
  • Some frontends remember history better than others
This is not just user interface behavior. It reflects how the runtime handles context, KV cache, and session state.
Takeaway: Local LLM “memory” depends heavily on the runtime and frontend, not just the model file.

The save-worthy framework: 4 layers of “memory”

Use this simple framework whenever someone says an LLM “remembers” something.
1. Weights: learned memory
This is what the model learned during training.
Examples:
  • Language patterns
  • General facts
  • Coding syntax
  • Reasoning patterns
  • Style tendencies
Normal chatting does not update these weights.
Question to ask: Did the model learn this during training or fine-tuning?
2. Context: active memory
This is what the model can currently see in the prompt.
Examples:
  • Your current message
  • Earlier chat turns
  • A pasted document
  • A system instruction
  • Retrieved notes
This is temporary and limited by the context window.
Question to ask: Is the information currently inside the active context?
3. KV cache: computational memory
This is cached internal attention data for previous tokens.
Examples:
  • Key/value states for tokens already processed
  • Runtime state used to continue generation faster
This is not human-readable and not permanent.
Question to ask: Is this just helping the model avoid recomputing past tokens?
4. External memory: stored memory
This is information stored outside the model and later inserted back into context.
Examples:
  • Notes
  • Databases
  • Vector stores
  • User profiles
  • Saved chat summaries
  • Agent memory systems
The model can only use this when the system retrieves it and places it into the active context.
Question to ask: Was the stored information actually retrieved and shown to the model?

Simple rule

If you remember one thing, make it this:
  • Weights are what the model learned.
  • Context is what the model can currently see.
  • KV cache is how the runtime avoids repeated work.
  • External memory is what another system stores and retrieves.
Takeaway: Do not call all of these “memory.” They behave differently, fail differently, and cost different resources.

Common mistakes beginners make

Mistake 1: Thinking chat updates the model
Normal inference does not train the model.
If you tell a local model your name, it may use that name during the session. But unless something stores that information externally or changes the weights, the base model has not learned your name.
Takeaway: Chatting with a model is not the same as training it.
Mistake 2: Thinking KV cache stores facts
KV cache is not a note file. It is not a list of facts.
It is internal attention data used for efficient generation.
You cannot open the KV cache and read “the user prefers Python” like a database row.
Takeaway: KV cache helps the model compute faster. It does not store semantic memories in a user-friendly format.
Mistake 3: Thinking larger context means perfect memory
A larger context window helps, but it does not solve everything.
Long contexts can be expensive, slow, noisy, and harder for the model to use perfectly. Also, if the frontend does not include the right information, the model still will not see it.
Takeaway: Bigger context increases capacity, but it does not guarantee reliable recall.
Mistake 4: Confusing saved chat history with active context
An app may save your old chats. That does not automatically mean every old message is included in every new prompt.
Saved history must be reloaded, summarized, or retrieved before the model can use it.
Takeaway: Stored somewhere is not the same as visible to the model.
Mistake 5: Blaming the model for frontend behavior
Sometimes the model “forgot” because the app dropped old context.
Sometimes a session reset cleared the cache.
Sometimes the model file is fine, but the interface changed what it sends.
Takeaway: Memory behavior comes from the whole stack: model, runtime, frontend, and storage.

Practical next step

Try this simple experiment in any local chat interface:
  1. Start a new chat.
  2. Tell the model: “My project codename is Blue Lantern.”
  3. Ask: “What is my project codename?”
  4. Continue chatting for a long time, or paste a large document.
  5. Ask again: “What is my project codename?”
Then compare what happens.
If the original detail remains in context, the model should answer correctly. If it falls out of context, gets summarized away, or the session resets, the model may forget.
That experiment teaches the difference between context memory and true long-term memory better than any definition.
Takeaway: Test memory by controlling what stays in context and what gets removed.

Final takeaway

A local LLM can continue a conversation because the runtime keeps active context and cached computation available.
The context contains the tokens the model can currently use.
The KV cache stores internal attention data so the model does not need to recompute everything from scratch.
The chat history is text that may or may not be included in the current prompt.
And long-term memory requires some external system, saved state, or weight update.
Once you separate those layers, local LLM behavior becomes much easier to predict.
The model is not magically remembering. It is working with what the runtime gives it.
