09 - From Theory to Running a Local Model
A local LLM does not “wake up” and start chatting. When you run one, a whole chain of pieces snaps together: model files, tokenizer, chat template, context window, inference runtime, sampling settings, KV cache, and your hardware. This is the bridge from theory to what actually happens when you press Run.

What you’ll learn

  • What a local inference runtime actually does
  • How GGUF, llama.cpp, Ollama, and LM Studio fit into the picture
  • How your prompt becomes tokens, then output
  • Why context, sampling, and KV cache matter at runtime
  • Why hardware shapes the real experience more than most beginners expect

The full local inference loop

By now, the pieces should feel familiar:
  • The model weights store learned patterns.
  • The tokenizer turns text into token IDs.
  • The context window defines the active token budget.
  • The transformer processes token relationships.
  • Self-attention lets tokens influence each other.
  • Sampling decides which token gets picked next.
  • The KV cache avoids recomputing old context every step.
Running a local model is just all of those pieces working together inside a runtime. A runtime is the software that loads the model and performs inference. Examples include:
  • llama.cpp
  • Ollama
  • LM Studio
  • text-generation-webui
  • vLLM
  • MLX
  • Transformers
  • Other local inference stacks
Some are command-line tools. Some are desktop apps. Some are servers. But the core job is the same:
Load the model, prepare the prompt, run next-token prediction, return text.
Takeaway: A local model is not one magic object. It is a runtime coordinating model files, tokenization, context, sampling, cache, and hardware.

The runtime loads the model

When you start a local model, the runtime first loads the model package. For a GGUF model, that usually means a single file containing the weights plus metadata needed by the runtime. GGUF is common in llama.cpp-based workflows because it is built for efficient local inference. For other stacks, the model might be packaged as:
  • safetensors weight files
  • tokenizer files
  • config JSON files
  • chat templates
  • generation settings
  • special token definitions
The runtime needs to know things like:
  • What architecture is this?
  • How many layers does it have?
  • What tokenizer should be used?
  • What context length is supported?
  • What precision or quantization format are the weights in?
  • How should chat messages be formatted?
This is why downloading “a model” often means downloading more than just learned numbers.
Takeaway: Loading a local model means loading both the weights and the instructions needed to interpret them correctly.

Your message gets formatted

Most beginners think the model receives exactly what they type. It usually does not. If you type:
Explain transformers simply.
A chat model may actually receive something closer to a structured prompt like:
plaintext
<system>
You are a helpful assistant.
</system>

<user>
Explain transformers simply.
</user>

<assistant>
The exact format depends on the model’s chat template. A chat template tells the runtime how to convert messages into the format the model was trained to expect. This matters because instruct and chat models are usually trained on structured conversations, not raw text boxes. If the template is wrong, the model may still answer, but quality can drop. It might ignore roles, behave strangely, repeat itself, or fail to follow instructions well. Tools like Ollama, LM Studio, llama.cpp frontends, and other runtimes often manage this for you. But conceptually, this step always exists. Takeaway: Chat models do not just read your text. The runtime wraps your messages into the format the model expects.

Text becomes tokens

Once the prompt is formatted, the tokenizer converts it into token IDs.
The model does not process letters or words directly. It processes numbers that represent chunks of text. For example, a sentence might become something like:
plaintext
[128000, 9906, 11, 1268, 527, 499, 30]
Those numbers are token IDs from the model’s vocabulary. This is where the earlier token lesson becomes real:
  • Your system prompt consumes tokens.
  • Your user message consumes tokens.
  • Prior chat history consumes tokens.
  • Uploaded documents or copied text consume tokens.
  • The model’s answer also consumes tokens.
All of this must fit inside the active context window. Takeaway: Every local chat begins by turning formatted text into token IDs that fit inside the model’s context budget.

The context window sets the active workspace

The context window is the model’s active token budget. If your runtime is set to 4,096 tokens, then the active conversation, instructions, and generated answer must fit inside that space. If it is set to 8,192, 32,768, or more, the model can consider more tokens at once, assuming the model and runtime support it. But a larger context is not free. More context can mean:
  • More memory use
  • Slower prompt processing
  • Larger KV cache
  • More pressure on your hardware
  • More room for irrelevant information to distract the model
This is one reason local inference often feels different from hosted chat apps. Hosted systems hide the infrastructure. Local systems make the tradeoffs visible. Takeaway: Context is the model’s active workspace, not permanent memory. Bigger context helps, but it costs memory and speed.

The model predicts one token

After the prompt is tokenized, inference begins. The model takes the current token sequence and predicts what token should come next. It does not write the full answer in one pass. It does this:
  1. Read the current token sequence.
  2. Produce scores for possible next tokens.
  3. Convert scores into probabilities.
  4. Pick one token using the sampling settings.
  5. Add that token to the sequence.
  6. Repeat.
That loop is the heart of generation. If the model outputs 500 tokens, it has gone through this process roughly 500 times after processing the prompt. This is why longer answers take longer. The runtime is not “typing slowly” for dramatic effect. It is repeatedly running next-token prediction.
Takeaway: Local generation is iterative. The model predicts one token, appends it, then predicts the next.

Sampling turns probabilities into text

At each generation step, the model produces possible next tokens with different probabilities. Sampling settings decide how the runtime chooses from them. Common settings include:
  • Temperature: controls randomness
  • Top-p: limits choices to a probability mass
  • Top-k: limits choices to the top k tokens
  • Repeat penalty: discourages repetition
  • Max tokens: limits answer length
  • Stop sequences: tell the runtime when to stop
A low-temperature setting makes output more predictable. A higher-temperature setting allows more variation, but can also increase weirdness. Greedy decoding always picks the most likely next token. Sampling lets the model choose from likely alternatives. This is why the same prompt can produce different answers across runs, even with the same model. Takeaway: The model produces probabilities. Sampling settings decide how conservative or creative the final text becomes.

The KV cache speeds continuation

Without caching, each new token would require the runtime to recompute attention information for the entire previous sequence again and again. That would be wasteful. The KV cache stores intermediate attention data for previous tokens, so the model can continue generation more efficiently. This is why continuing a response token by token is faster than fully recomputing the whole context each time. But the KV cache is often misunderstood. It is not:
  • Long-term memory
  • A database of facts
  • A saved personality
  • A replacement for context
  • Something the model “learns” from permanently
It is temporary runtime state that helps the model continue working with the active sequence. When the session ends, the cache can disappear unless the runtime saves state in some way. Takeaway: KV cache makes ongoing generation faster, but it is not memory in the human sense.

Hardware decides what feels practical

This is where local LLMs become very real. The same model can feel fast, slow, smooth, or unusable depending on your hardware. The main constraints are:
  • RAM or VRAM: Can the model fit?
  • Memory bandwidth: How fast can weights move?
  • CPU or GPU compute: How fast can operations run?
  • Context length: How large does the KV cache get?
  • Quantization: How compressed are the weights?
  • Batching and runtime optimizations: How efficiently does the software run?
A 7B model may run comfortably on many consumer machines. A 70B model may require much more memory, aggressive quantization, GPU offload, or a high-memory system. This is why “Can I run this model?” is not just about parameter count. It depends on:
  • Model size
  • Weight precision
  • Quantization format
  • Runtime
  • Context length
  • CPU/GPU split
  • Available memory
  • Your speed expectations
A model that technically runs at 1 token per second may not be pleasant for chat. A smaller model at 30 tokens per second may be more useful for daily work. Takeaway: Local inference is a capability and hardware tradeoff. The best model is the one that fits your machine and your use case.

Where GGUF, Ollama, LM Studio, and llama.cpp fit

These names often confuse beginners because they refer to different parts of the local LLM world. Here is the clean mental model: GGUF GGUF is a model file format commonly used with llama.cpp-based runtimes. It often packages quantized model weights and metadata into a local-friendly format. Think:
“A file format for running models efficiently on local machines.”
llama.cpp llama.cpp is an inference engine focused on efficient local CPU and GPU inference. It is widely used under the hood by many local LLM tools. Think:
“A core runtime engine that can load and run models locally.”
Ollama Ollama is a user-friendly local model manager and runtime wrapper. It makes pulling, running, and serving models easier. Think:
“A convenient way to manage and run local models.”
LM Studio LM Studio is a desktop app for discovering, downloading, chatting with, and serving local models. Think:
“A graphical local LLM workspace.”
Different tools, same underlying chain:
plaintext
model files
→ runtime loads them
→ prompt gets templated
→ tokenizer creates tokens
→ model predicts next token
→ sampling picks output
→ KV cache speeds continuation
→ hardware determines speed
Takeaway: Tools differ in interface and packaging, but the core inference process is the same.

The save-worthy framework: the local inference stack

When you run a local model, remember this stack:
plaintext
1. Model package
   Weights, config, tokenizer, metadata, template

2. Runtime
   llama.cpp, Ollama, LM Studio, Transformers, MLX, etc.

3. Prompt formatting
   System message, user message, assistant prefix, chat template

4. Tokenization
   Text becomes token IDs

5. Context window
   Active token budget for prompt, history, and output

6. Transformer inference
   The model predicts the next token from the sequence

7. Sampling
   Settings choose which likely token gets emitted

8. KV cache
   Prior token attention data is reused for faster continuation

9. Hardware
   Memory, bandwidth, compute, and optimization decide practical speed
If something goes wrong, locate the layer. Bad answers may come from:
  • Wrong chat template
  • Weak model
  • Poor prompt
  • Bad sampling settings
  • Too much irrelevant context
  • Context truncation
  • Runtime mismatch
  • Hardware constraints
  • Over-compressed quantization
Takeaway: Debug local LLM behavior by identifying which layer of the stack is responsible.

Common beginner mistakes

1. Thinking the model is only the weights Weights matter, but the runtime also needs tokenizer behavior, config, templates, special tokens, and execution settings. Takeaway: A model is a package, not just a blob of numbers. 2. Ignoring the chat template A good model can behave badly if the messages are formatted in a way it was not trained to follow. Takeaway: Prompt format matters as much as prompt wording. 3. Setting context too high by default A huge context window sounds better, but it can slow things down and consume memory. Takeaway: Use enough context for the task, not the largest number available. 4. Treating KV cache as memory KV cache helps the runtime avoid recomputation. It does not give the model permanent memory or new knowledge. Takeaway: Cache is speed infrastructure, not learned memory. 5. Comparing models without considering hardware A bigger model may be more capable but worse for your actual workflow if it runs too slowly. Takeaway: The best local model is capability plus usability on your machine. 6. Expecting tools to change the core mechanism Ollama, LM Studio, and llama.cpp may feel different, but they still perform the same inference loop. Takeaway: Interfaces differ. The underlying process remains next-token prediction.

Practical next step

Pick any local LLM tool you like, such as LM Studio, Ollama, or llama.cpp, and inspect the settings before running a model. Do not focus on installing everything perfectly yet. Just identify:
  • Model name
  • File format
  • Quantization level, if shown
  • Context length
  • Temperature
  • Top-p or top-k
  • Max output tokens
  • CPU/GPU usage
  • Chat template or prompt format, if visible
Then ask:
Which part of the local inference stack does each setting control?
That one exercise turns local LLMs from a black box into a system you can reason about. Takeaway: Before optimizing local models, learn to map every visible setting to the underlying inference process.

The big picture

A local LLM is not just “ChatGPT on your laptop.” It is a complete inference system running under your control. When you send a message, the runtime:
  1. Loads the model.
  2. Formats your chat.
  3. Tokenizes the prompt.
  4. Fits it into context.
  5. Runs transformer inference.
  6. Predicts one token at a time.
  7. Applies sampling.
  8. Uses KV cache for speed.
  9. Pushes against your hardware limits.
Once you understand that chain, local LLMs become less mysterious. You stop asking only:
Which model is best?
And start asking better questions:
Which model fits this task, this hardware, this context length, this speed target, and this quality bar?
That is the real shift from theory to practice. Takeaway: Running local models is not about memorizing tools. It is about understanding the inference stack well enough to make smart tradeoffs.
