The Ultimate Skill Playbook for Claude Code (Builder's Guide)

here is the truth nobody tells ai builders.

prompt engineering is dead. 100x engineers now

SKILLIFY
Most agent skills you write are making your agent worse.
Not obviously. Not dramatically. Slightly. Every session.
You do not need more prompts. All you need is a skill folder structured for cost, not convenience. A description written as a router, not a summary. A body made entirely of constraints the model doesn't already know. Evals written before the skill exists, not after.

This article is 4,000 words of the mistakes I made, what three teams converged on, and why the bottleneck in skill authoring is not what you think.
If you want to understand how to build and master skills read the below guide :

The Convergence Nobody Planned

Garry Tan posted in April that nailed this point first. His exact words: "when someone asks how I 'prompt' my AI, the answer is: I don't. the skills are the prompts."
Barry Zhang and Mahesh Murag from Anthropic said the same thing on stage at AIE: stop building agents, build skills.
Perplexity published an internal guide on skill design shortly after. Their opening line: "if you write a skill like you do code, you will fail."
Three of the most respected teams in AI. Same answer. Different routes to get there.
The reason they converged is that prompting doesn't compound. Every session you re-type the same instructions. The agent starts from zero. You get slightly better at prompting. The system never gets smarter.
Skills compound. The skill you write today is still running next month. You append to it when the agent fails. The failures become the guide. Over time the skill reflects every edge case you have encountered, not just the happy path you imagined on day one.
I spent the last few weeks reading everything published on this, then shipping skills, breaking them, and rewriting them. What I found was worse than I expected. The format is misleadingly approachable: a folder, a SKILL.md, some yaml, some markdown. Done. Except half the instincts you built writing software actively work against you here.
Here is what I learned.

A Skill Is Not a File. It Is a Folder.

This is the first thing Perplexity's guide says and the first thing most builders get wrong.
The typical beginner skill is a single markdown file with a long body. It loads entirely on every relevant session. Every instruction, every example, every edge case, all of it, every time.
The folder structure that works looks like this:
bash
your-skill/
├── SKILL.md        ← description + constraints only
├── scripts/        ← deterministic code the agent doesn't reinvent every run
├── references/     ← heavy docs, loaded only when needed
└── assets/         ← templates, schemas, output formats
The reason the shape matters is context cost.
SKILL.md is the only file the agent reads by default. Keep it short. Push everything heavy into references/. Nothing in references/ costs a token until the agent explicitly reads it. That distinction is the entire optimization.
Most builders treat the skill file like a wiki. They put the API docs in there, the error handling tables, the edge case lists, the full style guide, everything. The file balloons to 8,000 tokens. The agent loads it every time the skill triggers. Eight thousand tokens multiplied by every session, every user, forever.
Push the API docs to references/api.md. The agent reads it when it needs it. Not before.
The scripts folder exists because some tasks are deterministic. If the skill always runs the same git commands, the same linter, the same file rename pattern, put that in a script. Deterministic code in scripts/ runs the same way every time and costs nothing at load. Non-deterministic code in the skill body gets reinvented by the model on every run, with slight variations, at full token cost.
I did not design this separation from scratch. I arrived at it by watching the model perform worse as I added more to a single file, then tracing back to figure out why.

The Description Is the Most Expensive Line You Will Ever Write

One hundred tokens. Every session. Every user. Paid always, even when the skill doesn't trigger.
The description is not a summary of what the skill does. It is a routing trigger. The agent reads every description in your skill library at session start to decide what to load. Get it wrong and the wrong skills trigger. Get it wrong the other direction and the right skill never loads. Get it slightly wrong on both and every other skill in your library gets slightly worse because the model is reasoning with irrelevant context loaded alongside the task.
Start every description with "Load when."
Not "This skill helps with." Not "Use for X." Load when.
  • "Load when the user is debugging a failed API call or getting a 4xx error in a service they own."
  • "Load when the user asks to write, refactor, or review a skill file."
  • "Load when the user mentions a deploy, migration, or schema change."
The phrase forces you to think in terms of triggers, not capabilities. Capabilities are what the skill does. Triggers are when the agent should decide to load it. Those are different questions, and only one of them matters for the description.
The other half of the description is vocabulary. Use the words engineers say when frustrated. Not what they should say. What they actually say.
  • "my build is broken" not "there is a compilation error in my project."
  • "this is slow as hell" not "the query is underperforming."
  • "why does this keep happening" not "there is a recurring failure pattern."
The model routes based on semantic similarity to the user's actual message. If the user says "my build is broken" and your description says "compilation error resolution," the skill might not load. Write the description in the register your user operates in when something is on fire.
I spent two hours rewriting a single description once. The skill had been triggering on the wrong requests for a week and I couldn't figure out why. The fix was changing "handles authentication errors" to "Load when the user is getting 401s or can't log in." One sentence. Wrong half the time before. Right almost every time after.

The Body Is Not Documentation. It Is Constraints.

Every sentence in the skill body should pass one test before it stays: would the agent get this wrong without this line?
If no, delete it. The model already knows it.
The model knows how to write a pull request description. You don't need "write a clear title and describe the changes." The model knows Python. You don't need "use descriptive variable names." The model knows git. You don't need the commit message format unless you have a non-obvious house style.
What the model doesn't know is your taste.
Your taste is: "we don't force-push to main, ever, even during a hotfix." Your taste is: "type stubs go in the same file as the implementation, not in a separate .pyi." Your taste is: "API errors always get logged before they're raised, never after." That is what goes in the body.
The test catches approximately sixty percent of what most builders write. The first draft of almost any skill is two-thirds things the model already knows. Delete them. What's left is the skill.
Don't write commands. Write intent.
My first PR-review skill had twelve steps. Check the title format. Run the linter. Grep for TODO comments. Read the diff. Check the test coverage. The rewrite is four sentences: "I review PRs against the team's style guide in references/style.md. I flag anything that would fail in production, not just anything that's suboptimal. I never approve without reading the test file. Here are three PRs I thought were well-reviewed and why."
The rewrite produces better output now. It will keep getting better as models improve. Procedural skills age. Intent-based skills compound.

References and the Zero-Cost Tier

The folder structure creates three tiers of context cost.
  1. Index tier: about 100 tokens, always loaded. That's your description. You cannot escape this cost, so every word must earn its place.
  2. Load tier: 2,000–8,000 tokens, loaded when the skill triggers. That's SKILL.md. This is what you optimize. Most skills should stay under 1,500 tokens here.
  3. Runtime tier: unbounded, loaded only when the agent requests it. That's references/. This is free until needed.
Push everything you can to the runtime tier.
Style guides go in references/style.md. API docs go in references/api.md. Error tables go in references/errors.md. Output templates go in assets/. The agent loads them when the task requires them. Not before.
The index tier references the runtime tier without loading it. In the skill body: "Consult references/style.md for house style before writing any prose." That line costs eight tokens and tells the agent what to load when it needs it. The alternative is pasting the entire style guide into the skill body and paying for it every session.
I had one skill that was 6,000 tokens before I applied this. After moving the reference material to references/ and the templates to assets/, the skill body was 800 tokens. The skill ran faster. Context budget went to things that mattered. Behavior was identical. I had been paying 5,200 extra tokens per session for nothing.

Evals Come Before the Skill. Not After.

Write 10 to 20 queries before you write a single line of the skill.
For each query, mark it: "should trigger" or "should not trigger." Ten should-trigger queries. Ten should-not-trigger queries.
The should-triggers tell you what the skill is actually for. The should-not-triggers force you to define the boundary. Both are information you need before you write the description.
If you can't write the evals, you don't need the skill.
This sounds obvious. It's almost never done. The typical workflow is: decide to make a skill, write the skill, test it by eyeballing a few responses, ship it. The skill works for the happy path. Three weeks later it's triggering on requests it shouldn't and missing requests it should catch.
The eval set catches this before you write anything.
Run the eval set before you ship. Run it again after every significant change. If a change breaks more than two evals, revert it. The evals are the contract. The skill is the implementation.
The other thing evals give you: a forcing function against vague skills. If you're writing a skill called "writing-helper" and you can't write ten specific should-trigger queries, the skill is too broad. Break it up. "writing-helper" becomes "api-changelog-writer" and "error-message-copywriter." Now the evals write themselves.
I shipped a skill without evals once. It ran fine for a week. Then it started triggering whenever users asked about anything file-related, because the description mentioned "file operations" and the skill was actually about git operations. It was costing context budget on half my sessions. Writing the evals after the fact made the problem obvious in five minutes. It should have taken five minutes before I ever wrote the skill.

Skills Are Append-Mostly

When the agent fails, don't rewrite the description. Don't rewrite the body. Append a gotcha.
bash
Gotchas

- If the repo uses pnpm workspaces, the root package.json is not the entrypoint. Start from packages/.
- The staging environment requires VPN. CI runs without VPN. Never test staging from CI.
- API rate limits reset at midnight UTC, not midnight local. Retries before midnight will always fail.
The gotcha section is the only part of a skill that should grow after you ship. Everything else should stay stable.
This is not a convention. It is a design decision. The reason: if you rewrite the description every time the agent fails, the description drifts. It accumulates qualifications and special cases until it no longer routes correctly.
The gotcha section doesn't affect routing. It loads as part of the skill body, after the agent has already decided to load the skill. You can append to it indefinitely without touching anything that matters for routing.
The gotcha section is also the institutional memory of the skill. Every entry is a real failure the agent made on a real task. Over time it becomes more valuable than the original skill body, because the original body was written from imagination and the gotchas were written from experience.
One of my oldest skills has a body of 600 tokens and a gotcha section of 400 tokens. Most of the useful instructions are in the gotchas. That is what three months of real usage looks like.

Don't Let the LLM Write the Skill

This is the rule that surprised me most when I read it. Perplexity called it out directly. Barry and Mahesh implied it on stage.
Self-generated skills provide no benefit on average.
The model can draft the structure. It can fill in obvious constraints. It cannot identify the gaps in its own training distribution.
A skill is valuable because it encodes something the model would get wrong without it. The model cannot see what it would get wrong. It doesn't have access to the cases where it failed. It can't observe its own blind spots from the inside.
The person who can write a good skill is someone who has watched the agent fail. On real tasks. More than once. With the same failure mode appearing in different contexts.
That person is you. Not the model.
The model can write a skill that looks correct. Correct structure, correct format, covers the obvious cases. Ships fine. Then three weeks later it's missing the cases that actually matter in your environment, because those cases are specific to your stack, your conventions, your users, your failure history. None of that is in the model's training data.
Skill authoring is one of the few software tasks left where the bottleneck is genuine human judgment.
Use /skillify if you have it. But treat the output as a first draft. It needs a human who has seen the agent fail to make it real.

What Happened Over Six Weeks

  • Week 1: I shipped nine skills in three days. Felt great. The agent handled a PR review correctly and I thought I had figured something out.
  • Week 2: The agent started triggering the wrong skills. A debug-api skill was loading on any request that mentioned an API, even documentation requests. A PR skill was loading during code reviews that had nothing to do with PRs. Context was filling with irrelevant instructions before the agent had started thinking.
  • Weeks 3–4: I rewrote every description. Went from capability-language to trigger-language. "Helps with API debugging" became "Load when the user is getting a 4xx or 5xx from a service they own and are trying to diagnose it." Skills started routing correctly. The noise dropped.
  • Week 4: I moved everything heavy to references/. Skill bodies went from an average of 3,200 tokens to 900. Session performance improved. I stopped running into context budget problems on complex tasks.
  • Week 5: I wrote the evals, retroactively, for every skill I had shipped. Found three skills overlapping on the same triggers. Merged two. Deleted one entirely because I couldn't write ten real should-trigger queries for it. It turned out I had written it for a task I did once.
  • Week 6: I opened a skill I hadn't touched in three weeks and found a line in the gotcha section I didn't remember writing. The agent had failed on a task involving a monorepo, logged the failure, and during a reflection cycle the skill had been updated. The gotcha was correct. It had caught something I hadn't thought to anticipate when I wrote the original.
I do not want to overstate this. The system is not magic. Skills still fail. What changed is that the mistakes stopped repeating, and the skills that caught failures once kept catching them without me re-teaching the lesson.

What to Watch Out For

Description drift. You rewrite the description after every failure. After six rewrites it doesn't route correctly anymore.Fix: never rewrite the description after shipping. Append gotchas. Only rewrite the description if the skill's entire scope changes.
Token blindness. Skill body is 5,000 tokens. Loads on every trigger. Half the content is things the model already knows. Fix: run the "would the agent get this wrong" test on every line. Move reference material to references/. Target under 1,500 tokens for the skill body.
Trigger collision. Two skills trigger on the same queries. Both load. Context fills with conflicting instructions. Fix:write evals before shipping. Include should-not-trigger queries that cover adjacent skills. If two skills share more than three should-trigger queries, merge them or redefine their boundaries.
LLM-drafted skills with no edge cases. Agent-generated skill looks correct, ships fine, misses every case that actually happens in your environment. Fix: only ship a skill after a human who has seen the agent fail has reviewed and added real gotchas. Use /skillify as a scaffold, not a final draft.
Stale references. references/api.md is six months old. The agent reads it confidently and calls endpoints that no longer exist. Fix: date every file in references/ with a last-updated header. Flag anything older than 60 days for review in the skill manifest.
Eval rot. Evals pass because the skill now routes on the eval queries specifically, not because the routing logic is correct. Fix: add new real-world queries to the eval set every month. Evals should include queries from actual sessions, not just ones you wrote before shipping.

The 7-Day On-Ramp

The thing most builders get wrong is trying to build the system first and then use it. Build the system by using it.
  • Day 1: Read the three sources. Garry Tan's post. Barry Zhang and Mahesh Murag's AIE talk "Don't Build Agents. Build Skills Instead." Perplexity's "Designing, Refining, and Maintaining Agent Skills at Perplexity." All three in one sitting. They cover the same ground from different angles and the overlap is the consensus.
  • Day 2: Clone gbrain. Add gstack →
    github.com/codejunkie99/agentic-stack
  • Day 3: Pick one workflow you do every week. Not a new workflow. Something you already do. Something you know the failure modes of.
  • Day 4: Do it once in your agent. Don't optimize. Watch where the agent gets it wrong. Those wrong places are the skill body.
  • Day 5: Type /skillify. Watch it become permanent. The skill is now in the library. The agent will find it next time.
  • Day 6: Run it on a real instance. Append the gotchas. The first real run will find things you didn't anticipate. Those go in the gotcha section, not the body.
  • Day 7: Two more workflows.
By day 7 you have three skills, three scripts, three triggers. You stop writing prompts. The workflows you encoded last week are still in the library next month. They run identically. They improve every time the agent fails and you append a gotcha. You didn't have to do anything to make that happen. That's the compounding.

Things I Would Do Differently

Write the evals before the description. I wrote the description before the evals every time in the first two weeks and paid for it for the next two weeks.
Start with five skills, not twenty. Each one you add increases the routing problem. Get five routing correctly before adding more.
Put "Load when" in every description from the first draft. Going back and retrofitting it later is how you find out your description was never a trigger to begin with.
Build the references/ folder before you need it. The impulse when you first write a skill is to put everything in the body because it's faster. Fight the impulse.
Keep a failure log separate from the gotcha section. One file, one line per failure, date and skill name. When the gotcha section gets long enough that you can't scan it in thirty seconds, you have missed failures that should have been gotchas.
Don't use /skillify without a failure story to give it. The output without that context is a skill that covers the happy path. That's the part you didn't need help with.

Conclusion

Right now most people are getting better at prompting. That's not the same as the system getting better.
The teams that converged on skills didn't coordinate. They ran the experiment independently and landed in the same place because that's where the experiment points. Prompts live in your head and your chat history. They reset every session. They don't accumulate. They don't catch the failure from last Tuesday and apply it to the task on Thursday.
Skills live in plain files in a git repo. The gotcha section grows. The references get updated. The evals catch regressions. The system knows more next month than it does today without you re-teaching anything.
What surprises me most about this is that the bottleneck is not technical. The folder structure is simple. The format is approachable. The part that is actually hard is having watched the agent fail enough times to know what it needs that it doesn't already have. That knowledge is yours. It can't be generated. It can only be accumulated.
Own your skills. Own the failures that shaped them. Keep them in plain files and git where no one can take them from you, and where they keep getting better every time the agent fails.

I built the first version of my skill library in an afternoon. A library worth using took six weeks. It has been getting better every week since, without me touching the early skills.
