Understanding the .claude/ Folder
In this blog, we will learn about the .claude/ folder in Claude Code. We will understand what each file and subfolder does and how to use them to configure Claude Code for our projects.
We will cover the following:
  • What is the .claude/ folder?
  • Project-level vs User-level .claude/
  • CLAUDE.md - Project Instructions
  • Rules - Path-Specific Instructions
  • Skills - Custom Slash Commands
  • Settings - settings.json and settings.local.json
  • Hooks - Lifecycle Automation
  • MCP Servers Configuration
  • Custom Subagents
Let's get started.

What is the .claude/ folder?

The .claude/ folder is a project-level configuration directory for Claude Code. It stores settings, instructions, custom commands, hooks, rules, and subagent definitions - all in one place.
In simple words, it is the control center of Claude Code for our project.
The best part is that we can commit this folder to git and share it with our entire team. This means everyone on the team gets the same Claude Code behavior, the same rules, and the same custom commands.
Here is the complete structure of the .claude/ folder:
markdown
our-project/
├── .claude/
│   ├── settings.json          # Shared project settings
│   ├── settings.local.json    # Personal project overrides (gitignored)
│   ├── CLAUDE.md              # Project instructions
│   ├── rules/                 # Path-specific and topic-based rules
│   │   ├── code-style.md
│   │   ├── testing.md
│   │   └── security.md
│   ├── skills/                # Custom slash commands
│   │   └── deploy/
│   │       └── SKILL.md
│   ├── agents/                # Custom subagent definitions
│   │   └── code-reviewer.md
│   └── hooks/                 # Hook scripts
│       └── validate-command.sh
├── .mcp.json                  # MCP servers configuration
└── CLAUDE.md                  # Alternative location (root level)
Now, let's understand each part in detail.

Project-level vs User-level .claude/

This is very important to understand. There are two levels of .claude/ configuration:
Project-level (.claude/): This lives inside our project directory. It is shared with the team through git. When we set rules or permissions here, every team member using Claude Code on this project gets the same behavior.
User-level (~/.claude/): This lives in our home directory. It is personal to our machine. Settings here apply to all projects but are not shared with anyone.
Here is the configuration precedence from highest to lowest:
  • Managed - Organization-enforced settings (cannot override)
  • Command-line arguments - Flags passed when running Claude Code
  • Local - .claude/settings.local.json (personal, gitignored)
  • Project - .claude/settings.json (shared via git)
  • User - ~/.claude/settings.json (personal, all projects)
So, if we set a permission in settings.local.json, it will override the same permission in settings.json.

CLAUDE.md - Project Instructions

CLAUDE.md is the most important file in the .claude/ folder. It contains persistent instructions that Claude loads at the start of every session.
We can place CLAUDE.md in two locations:
  • At the root of our project: ./CLAUDE.md
  • Inside the .claude/ folder: ./.claude/CLAUDE.md
Both work the same way. We can choose whichever location we prefer.
Here is an example of a CLAUDE.md file:
markdown
# Project Standards

## Build and Test
- Run `npm test` before committing
- Use 2-space indentation
- Follow our API design patterns

## Code Style
- Use TypeScript strict mode
- Prefer functional components in React
- Always add error handling for API calls

## Architecture
- Follow clean architecture pattern
- Keep business logic in the service layer
We can think of CLAUDE.md as a set of instructions for Claude Code. Whatever we write here, Claude will follow it throughout the session.
Note: We should keep it under 200 lines for optimal context usage. If we have more instructions, we can split them using rules.

Rules - Path-Specific Instructions

As our CLAUDE.md grows, it becomes hard to manage. This is where rules come into the picture.
Rules are modular instruction files that live inside .claude/rules/. The best part is that we can scope them to specific file paths. This means they load into context only when we are working on the relevant files.
Here is an example:
markdown
.claude/rules/
├── code-style.md
├── testing.md
├── security.md
├── frontend/
│   ├── react-patterns.md
│   └── styling.md
└── backend/
    └── api-design.md
We can add path scoping using frontmatter as below:
markdown
---
paths:
  - "src/api/**/*.ts"
  - "src/services/**/*.ts"
---

# API Development Rules

All API endpoints must include:
- Input validation
- Standard error response format
- OpenAPI documentation comments
Here, the rules will only load when we are working on files matching the src/api/**/*.ts or src/services/**/*.ts patterns.
Rules without the paths field load at session start along with the main CLAUDE.md.
This is how we can keep our instructions modular and organized.

Skills - Custom Slash Commands

Skills allow us to create custom slash commands for Claude Code. They are the modern way to extend Claude Code with our own commands.
Skills live inside .claude/skills/<skill-name>/SKILL.md.
We can create skills at two levels:
  • Project skills: .claude/skills/<skill-name>/SKILL.md (shared via git)
  • User skills: ~/.claude/skills/<skill-name>/SKILL.md (personal)
Here is the structure of a skill:
markdown
deploy/
├── SKILL.md              # Required - frontmatter + instructions
├── template.md           # Optional - template for Claude to fill
└── examples/
    └── sample.md         # Optional - example output
And here is an example SKILL.md:
markdown
---
name: deploy
description: Deploy to production environment
tools: Bash, Read
argument-hint: "[env]"
---

Deploy the application to the specified environment.

Steps:
1. Run all tests
2. Build the application
3. Deploy using the deploy script
Now, we can invoke this skill by typing /deploy in Claude Code.
We can also control who can invoke the skill:
  • disable-model-invocation: true - Only the user can invoke it, not Claude
  • user-invocable: false - Only Claude can invoke it, not the user
This is how we can create powerful custom commands for our workflow.

Settings - settings.json and settings.local.json

The settings files control permissions, environment variables, hooks, and more.
settings.json is the shared settings file. It is committed to git and shared with the team.
settings.local.json is the personal override file. It is automatically gitignored and only applies to our machine.
Here is an example settings.json:
json
{
  "permissions": {
    "allow": [
      "Bash(npm run test)",
      "Bash(git *)"
    ],
    "deny": [
      "Bash(curl *)",
      "Read(.env)"
    ]
  },
  "env": {
    "NODE_ENV": "development"
  }
}
Here, we have:
  • permissions.allow - Tools and commands that Claude can use without asking
  • permissions.deny - Tools and commands that Claude must never use
  • env - Environment variables available during the session
The settings.local.json has the same structure. If we set a permission in both files, settings.local.json takes precedence.

Hooks - Lifecycle Automation

Hooks are shell commands that execute automatically at specific points in Claude Code's lifecycle. They are deterministic - they always run, unlike instructions which are suggestions.
Hooks are configured in settings.json under the hooks key.
Here are some of the hook events we can use:
  • PreToolUse - Before a tool executes (can block it)
  • PostToolUse - After a tool succeeds
  • UserPromptSubmit - When we submit a prompt
  • SessionStart - When a session begins
  • Stop - When Claude finishes responding
Here is an example that auto-formats code after every edit:
json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write \"$FILE_PATH\""
          }
        ]
      }
    ]
  }
}
Here, every time Claude edits or writes a file, Prettier automatically formats it.
We can also use hooks to block dangerous commands by adding the path of the following script in the settings JSON file:
bash
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

# Block if file matches protected pattern
if [[ "$FILE_PATH" == *.env* ]]; then
  echo "Blocked: Cannot edit .env files" >&2
  exit 2  # Exit 2 = block the action
fi

exit 0  # Exit 0 = allow the action
Here, exit code 2 blocks the action, and exit code 0 allows it.
There are four types of hooks:
  • command - Shell command that reads JSON stdin
  • prompt - Single LLM call for yes/no decision
  • agent - Multi-turn subagent for verification
  • http - POST event data to a remote endpoint
This is how we can automate and enforce rules in our workflow.

MCP Servers Configuration

MCP (Model Context Protocol) connects Claude Code to external tools and data sources like GitHub, databases, APIs, and more.
MCP servers are configured in .mcp.json at the project root (not inside .claude/).
Here is an example .mcp.json:
json
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "node",
      "args": ["/path/to/github-mcp-server.js"]
    },
    "postgres": {
      "type": "stdio",
      "command": "python",
      "args": ["-m", "mcp_postgres"]
    }
  }
}
Here, we have configured two MCP servers:
  • github - Connects Claude Code to GitHub
  • postgres - Connects Claude Code to a PostgreSQL database
There are three types of MCP servers:
  • stdio - Local executable (Node, Python, and etc.)
  • sse - Remote HTTP server with Server-Sent Events
  • http - Remote HTTP server
We can configure MCP servers at two levels:
  • Project scope - .mcp.json (shared via git)
  • User scope - ~/.claude.json (personal)
This is how we can extend Claude Code with external tools and data sources.

Custom Subagents

We can define custom subagents inside .claude/agents/. Subagents are specialized Claude instances with their own system prompts, tools, and rules.
Here is an example .claude/agents/code-reviewer.md:
markdown
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Grep, Glob
model: claude-sonnet-4-6
---

You are a code reviewer. Review the code for:
- Code quality and readability
- Potential bugs and edge cases
- Performance issues
- Security vulnerabilities

Provide feedback in a structured format.
Now, Claude Code can use this subagent for code review tasks.
This is how we can create specialized agents for different tasks in our workflow.
