1 Architecture globale

L'Agent view s'appuie sur un processus superviseur par utilisateur qui héberge toutes les sessions en arrière-plan. Il démarre automatiquement au premier dispatch et reste indépendant du terminal.

💡 CLAUDE_CONFIG_DIR : si cette variable d'environnement est définie, le supervisor utilise ce répertoire au lieu de ~/.claude/ et tourne comme une instance séparée avec ses propres sessions.

2 Cycle de vie d'une session

Une session passe par plusieurs états. Après ~1h d'inactivité, le superviseur arrête le process pour libérer des ressources — le transcript et l'état restent sur disque et un nouveau process est relancé au prochain accès.

4 Flux d'interaction

Trois interactions principales : dispatch (créer), peek/reply (interagir vite), attach (reprendre la main).

Détacher d'une session attachée

Aucune de ces actions ne stoppe une session en arrière-plan — elles te font juste sortir du terminal :

  • ← sur prompt vide — retour à Agent view (depuis n'importe quelle session, désactivable dans /config)
  • Ctrl+Z — détach immédiat si un dialog bloque ←
  • Ctrl+C, Ctrl+D, /exit — laissent aussi la session tourner en bg
  • /stop — la seule commande qui termine définitivement la session depuis l'intérieur

5 Trois manières de dispatcher

A · Depuis Agent view

Tape un prompt dans l'input du bas + Enter. Session nommée automatiquement (renommer avec Ctrl+R). Tu peux coller une image (screenshot, diagramme) dans le prompt.

  • <agent-name> <prompt> — si le 1er mot matche un subagent, il devient l'agent principal
  • @<agent> — mentionne un subagent (équivalent explicite, prioritaire sur un repo de même nom)
  • @<repo> — cible un repo voisin
  • /<skill> — lance une skill
  • #<PR> ou URL de PR — sélectionne la session existante sur ce PR
  • Shift+Enter — dispatch + attach immédiat

B · Depuis une session interactive

  • /background (alias /bg) — backgroundise la session courante
  • /bg run the tests — envoie une dernière instruction puis backgroundise
  • ← sur prompt vide — bg + ouvre agent view, session pré-sélectionnée

C · Depuis le shell

  • claude --bg "<prompt>"
  • claude --agent code-reviewer --bg "..."
  • Retourne un ID court : 7c5dcf5d

9 Isolation des écritures fichiers

Toutes les sessions en arrière-plan lisent le code source partagé, mais leurs écritures sont automatiquement redirigées dans un git worktree isolé sous .claude/worktrees/.

⚠ Le worktree est supprimé avec la session — penser à merger ou pusher avant claude rm.

10 Que se passe-t-il si 2 sessions modifient le même fichier ?

Claude Code anticipe le problème en bloquant les écritures directes dans le working directory pour toute session en arrière-plan. Dès qu'une session tente d'éditer un fichier, elle est automatiquement déplacée dans un git worktree isolé sous .claude/worktrees/<session-id>/. Chaque session travaille donc sur sa propre copie, sans se voir mutuellement.

Conséquences concrètes

SituationQue se passe-t-il
Pendant l'éditionAucun conflit. Chaque session voit sa propre copie du fichier dans son worktree. Elles ne se voient pas mutuellement.
A commitCommit sur la branche du worktree A uniquement. Le working dir principal et la branche B sont intacts.
B commitIdem côté B. Aucune interaction avec A.
Récupérer les 2 résultatsTu merges/rebases manuellement les 2 branches → conflit git standard si les changements se chevauchent sur les mêmes lignes.
2 PR séparéesGitHub gère le conflit au moment du 2e merge sur main.

Cas où l'isolation NE s'applique PAS

D'après la doc, le blocage des écritures dans le working directory ne s'applique pas dans 3 cas :

⚠ Session déjà dans un worktree

Si tu as lancé claude depuis .claude/worktrees/X, elle écrit dans ce worktree directement (pas de double isolation).

⚠ Pas un repo git

Écritures directes autorisées. Risque réel de race condition si 2 sessions modifient le même fichier (dernière écriture gagne, pas de garde-fou).

⚠ Écritures hors du working dir

Ex : ~/.config/, /tmp/. Directes aussi → même risque de collision.

Workflow recommandé

1. Dispatch session A : "refactor auth"           → worktree A cree auto
2. Dispatch session B : "add logging to auth"     → worktree B cree auto
3. Les 2 tournent en parallele, chacune commit dans sa branche
4. Session A finit  → PR depuis branche A vers main
5. Session B finit  → PR depuis branche B vers main
6. Tu merges PR A   → main avance
7. Tu rebases B sur main → resous conflits eventuels → merges
8. claude rm <id-A> et <id-B>  ⚠ supprime les worktrees

Pièges à connaître

  • ⚠ claude rm détruit le worktree : merger ou pusher la branche avant de supprimer la session, sinon le travail est perdu.
  • ⚠ Worktrees orphelins : si une session se termine sans cleanup propre, .claude/worktrees/ se remplit. Lister avec git worktree list et nettoyer avec git worktree remove <path>.
  • ⚠ Lectures non synchronisées : la session B ne voit pas les modifs de A tant que A n'a pas mergé sur main puis que B n'a pas rebasé. Deux sessions "parallèles" sur le même fichier travaillent en réalité sur la version d'origine chacune.
  • 💡 Forcer l'isolation pour un subagent : ajouter isolation: worktree dans son frontmatter pour qu'il s'isole toujours, quelle que soit la façon dont il est lancé.

11 Troubleshooting

SymptômeCause + remède
Agent view est vide à l'ouvertureAucune session dispatchée. Tape un prompt + Enter dans l'input du bas.
Sessions en "stopped" après réveil de la machineLes sessions ne survivent pas au sleep/shutdown. Attache/peek/reply pour relancer une session, ou claude respawn --all pour tout relancer en bloc.
Session lente à répondre après attachProcess arrêté après 1h inactif, le supervisor relance un process frais. Quelques secondes de latence normale. Sessions Working ou Needs input ne sont jamais arrêtées ainsi.
.claude/worktrees/ se remplitWorktrees orphelins (session terminée sans cleanup). Lister : git worktree list. Nettoyer chaque entrée : git worktree remove <path>.
