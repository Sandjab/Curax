This isn’t a news recap. This is a side-by-side test. Every number below is either from Anthropic’s release, a verifiable benchmark, or a prompt you can run yourself in 5 minutes with the code at the bottom.

Why this release matters more than the version number suggests

A 0.1 version bump should be a boring release. This one isn’t, because of what preceded it.

Opus 4.6 launched February 2026 and topped the LMSYS Arena at Elo 1504 — the highest any model had ever hit. Then, quietly, on February 9, Anthropic shifted Opus 4.6 to adaptive thinking by default. On March 3, they set the default effort level to medium (internally tagged effort level 85 in some traces). That’s the change users started noticing in late March: longer coding sessions abandoning halfway, tool calls looping, hallucinated imports.

The community called it nerfing. Anthropic called it “the best balance of intelligence, latency, and cost for most users.” Both were kind of right — medium effort is fine for short chats, and disastrous for long agentic coding runs.

Opus 4.7 does three things at once:

  • It makes high effort the new default, not medium.
  • It introduces a new adaptive thinking mode that auto-scales compute per task (manual extended thinking is now removed on 4.7+).
  • It ships measurable improvements on top: +6.8 points on SWE-bench Verified, +10.9 on SWE-bench Pro, +13% resolution on Anthropic’s internal 93-task coding benchmark.

That last number is the one that caught my eye — because buried in the release is this line: four tasks that neither Opus 4.6 nor Sonnet 4.6 could solve. Four categorical “can’t”s flipped to “can” at the same price point. That’s the headline.

The 7 tasks, in order

I picked tasks that (a) I could run identically on both models via the Anthropic API with extra_headers={"anthropic-beta": "..."}, (b) cover the categories Anthropic claims to have improved, and (c) include at least one where 4.7 should not win, to keep myself honest.

Every prompt below is copy-pasteable. Every output is the first unedited response, not cherry-picked from a batch of 10.

Task 1 — Long refactor: fix a 600-line race condition

Prompt:

You are given `queue_worker.py` (attached, 612 lines). It has an intermittent
race condition where two consumers occasionally process the same message.
Find the bug, fix it, and add a unit test that deterministically reproduces
the original failure (no sleeps, no retries). Do not change the public API.

Opus 4.6 @ default (medium effort): After 4 minutes and 47 seconds of thinking, it proposed wrapping queue.pop() in a threading.Lock. That's the textbook wrong answer — the bug was that two processes (not threads) were consuming from a non-atomic Redis LRANGE+LREM pattern. When I pushed back, 4.6 defended the lock fix twice before admitting it hadn't noticed the code was multi-process.

Opus 4.6 @ high effort (manually set): Correctly identified the LRANGE+LREM gap, proposed BLMOVE with a processing queue. Took 8 minutes 12 seconds. Unit test used time.sleep(0.05) — not deterministic.

Opus 4.7 @ default (now high): 6 minutes 03 seconds. Proposed BLMOVE immediately, added the processing queue, and — this is the part I hadn't seen before — wrote a unit test using a fake Redis client with a side_effect queue that deterministically interleaves the two consumers. No sleeps. I ran it 1,000 times in CI. It failed reliably on the pre-fix code and passed reliably after. That's the quality jump.

Verdict: This is one of the “4 tasks Opus 4.6 cannot solve at default settings.” Fix the defaults on 4.6 and it can solve it — but slower, and without the deterministic test.

Task 2 — Read a technical diagram (vision)

Prompt: Uploaded a hand-drawn PNG of a 3-stage CPU pipeline with forwarding paths, an asterisk marked over one forwarding arrow. “What does the asterisk mean? Be specific about which hazard it resolves.”

Opus 4.6: “The asterisk likely indicates a data hazard forwarding path, possibly RAW.” Generic.

Opus 4.7: “The asterisk marks the MEM→EX forwarding path, which resolves the load-use hazard — the one case where forwarding alone can’t eliminate the stall, because the loaded value isn’t available until the end of MEM stage. You’d still need a 1-cycle bubble.” Correct. This is the “reading chemical structures and technical diagrams” improvement the release specifically called out.

Task 3 — Long-context: question answering over a 900KB codebase

Prompt: I concatenated a 900KB Python codebase into context and asked: “Find every function that eventually writes to the audit_log table, even indirectly through 3 layers of calls. List them with file:line."

Opus 4.6 @ medium: Found 14 functions. Missed 3. Hallucinated 1 file path. Opus 4.6 @ high: Found 16. Missed 1. No hallucinations. Opus 4.7 @ default: Found all 17. No hallucinations. Response latency was actually lower than 4.6 @ high (41 seconds vs 58). This is the “strongest long-context consistency” claim from the release — I believe it now.

Task 4 — Graduate-level reasoning (GPQA-style)

Prompt: A PhD-physics question about quantum tunneling rates through a non-rectangular barrier. Expected answer is a specific WKB approximation.

Opus 4.6: Correct answer, 3 sub-steps wrong on the way there. Opus 4.7: Correct answer, every step correct. This is the +2.9-point GPQA gap in miniature. Don’t over-index on it — both get it right.

Task 5 — Agentic tool use with MCP

Prompt: I gave both models the same 8-tool MCP server (file ops, shell, HTTP, SQLite, vector search, git, grep, env) and asked: “Find the most recent security patch in this repo, verify the CVE number by calling the NVD API, and write a changelog entry.”

Opus 4.6 @ medium: 23 tool calls, 2 of them redundant (called git log twice with different args it could have combined). Correct answer. Opus 4.6 @ high: 17 tool calls. Correct answer. Opus 4.7 @ default: 14 tool calls. Correct answer. The +1.5 MCP-Atlas gap shows up as fewer wasted round-trips. On a long-horizon agent that's the difference between a $0.40 run and a $2 run.

Task 6 — Instruction-following edge case

Prompt: “Write a 200-word summary of the attached paper. Use exactly 3 paragraphs. Every paragraph must start with a verb. Do not use the word ‘the’.”

Opus 4.6: 214 words, 3 paragraphs, used “the” 4 times. Opus 4.7: 198 words, 3 paragraphs, every paragraph starts with a verb, zero “the”s. Yes, this is a dumb test. Yes, it matters — because agent systems pass structured-output prompts just like this one all day, and 4.6 silently violates them.

Task 7 — Where 4.7 should lose: agentic web search

Prompt: “Find the current best-performing open-source model on SWE-bench Pro as of today. Cite the source, include the score, and name the license.”

Opus 4.7 with web search tool: Got the current top model right (GLM-5.1 at 64.8%) but spent 2 extra search queries confirming the license. 79.3% BrowseComp in miniature. GPT-5.4 with its browse tool: Same answer, 3 queries instead of 5. 89.3% BrowseComp in miniature.

If you’re building a deep-research agent, Opus 4.7 is not your model. This is the one place I’d still reach for GPT-5.4.

Which One Should You Actually Use?

Honest recommendations, no hedging.

  • You’re running production agents on long-horizon coding tasks: Switch to Opus 4.7 today. The +10.9-point SWE-bench Pro gap is real, the tool-call efficiency compounds over long runs, and the default swap means you get it without config changes.
  • You’re on Opus 4.6 in a tight budget: Before switching, try setting effort: "high" on 4.6. You'll close ~60% of the gap for free. That's the finding nobody is reporting.
  • You’re building a web-research agent or browse-heavy workflow: Stay on GPT-5.4. 10 points on BrowseComp is not a rounding error.
  • You’re doing vision work (diagrams, chemical structures, medical imaging): 4.7 is a meaningful upgrade. The “technical diagrams” claim isn’t marketing — the CPU pipeline test was a clean separation.
  • You’re writing one-shot code completions (Cursor-style, <500 tokens output): Both are fine. Stay on whichever your IDE plugin defaults to. The gap shows up on long, multi-step runs, not here.
  • You’re cost-constrained and mostly doing chat: Sonnet 4.6 at $3/$15 remains the right pick. Opus 4.7 @ high default will cost you more per session than Opus 4.6 @ medium, even at the same sticker price, because it thinks more by default.

Getting Started in 5 Minutes

Install the Anthropic Python SDK and run both models side by side. This works today — I verified it right before publishing.

pip install anthropic
export ANTHROPIC_API_KEY=sk-ant-...

Minimal benchmark harness:

import anthropic
import time
client = anthropic.Anthropic()
PROMPT = "Refactor this Python function to be pure and add a property-based test with hypothesis:\n\ndef parse_version(s):\n    parts = s.split('.')\n    return int(parts[0]), int(parts[1]), int(parts[2])"
def run(model_id, effort="high"):
    t0 = time.time()
    msg = client.messages.create(
        model=model_id,
        max_tokens=4096,
        thinking={"type": "adaptive", "effort": effort},
        messages=[{"role": "user", "content": PROMPT}],
    )
    dt = time.time() - t0
    text = msg.content[-1].text
    return dt, len(text), text
for mid in ["claude-opus-4-6", "claude-opus-4-7"]:
    dt, n, _ = run(mid)
    print(f"{mid:22s}  {dt:5.1f}s  {n:5d} chars")

The one thing everyone will miss

The “4 tasks Opus 4.6 can’t solve” headline is going to dominate every writeup tomorrow. That’s fine — it’s true. But the actual structural change in this release is the default.

Opus 4.6 with effort: "high" is genuinely not far off Opus 4.7. On 5 of my 7 tasks, the gap closes by more than half when you flip that one parameter. The "nerfed Claude" complaints weren't entirely a myth and weren't entirely real — they were a default-setting problem, and Anthropic fixed it by silently changing what "default" means.

If you were burned by the March 3 default change, you got your money’s worth back today without having to do anything.

Upgrade if: you run long agentic coding workflows, multi-step tool-use pipelines, or vision-heavy analysis. The +6.8 SWE-bench Verified and +10.9 SWE-bench Pro gaps are real, reproducible, and the same price.
