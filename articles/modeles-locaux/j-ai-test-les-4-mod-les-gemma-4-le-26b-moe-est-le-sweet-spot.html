I Tested All 4 Gemma 4 Models: The 26B One Is Cheating (In the Best Way)

Chew Loong Nian - AI ENGINEER

Google dropped Gemma 4 this week under Apache 2.0 — free to use, free to commercialize, no strings attached. Four model sizes landed at once: E2B, E4B, 26B MoE, and 31B Dense. I pulled all four on my local machine the day they released, ran the same tasks on each, and found something I didn’t expect.

The 26B model is faster than the 4B model. Significantly faster. And it’s within 2% of the 31B on every benchmark I ran.

Here’s exactly what I found — and which one you should actually be running.

What Google Actually Released

Before we get into results, the naming deserves a minute because it’s confusing.

E2B — “Effective 2B.” 2.3 billion actual parameters. Designed to run on a smartphone or CPU-only laptop. This is the one Google is pitching for on-device AI.

E4B — “Effective 4B.” 4.5 billion parameters. Needs 8GB of RAM minimum. A strong everyday model for mid-range machines.

26B A4B (MoE) — This is the interesting one. It has 25.2 billion total parameters, but only 3.8 billion activate during any single inference pass. It’s a Mixture of Experts architecture — the model routes each token to a subset of specialist layers rather than running the full network every time. The result: 26B-class output at roughly 4B-class compute cost.

31B Dense — The flagship. All 30.7 billion parameters fire on every token. Highest quality, highest cost. Needs an 80GB H100 unquantized, though Q4 quantization brings it down to a 24GB GPU.

All four are multimodal (text + images), all four are Apache 2.0, and all four are on HuggingFace and Ollama day one.

I ran each model through three tasks: a multi-step reasoning problem, a code generation task, and a long-context summarization. For each task I measured time-to-first-token, total generation time, and output quality (scored manually on a 1–10 scale).

Results: E2B — Impressive for Its Size, Limited by It

The E2B is genuinely impressive for 2.3 billion parameters. It handles straightforward Q&A, basic summarization, and simple Python well. It starts generating in under 200ms, which feels snappy.

import ollama
response = ollama.chat(
    model='gemma4:e2b',
    messages=[{
        'role': 'user',
        'content': 'Write a Python function to find all prime numbers up to n using the Sieve of Eratosthenes.'
    }]
)
print(response['message']['content'])# Output: Clean, correct implementation in ~1.2 seconds
# Time to first token: 180ms
# Total generation time: 1.2s for ~120 tokens

Where it fell apart: multi-step reasoning. Give it a problem that requires holding more than 3–4 logical dependencies at once and it starts hallucinating intermediate steps. On my reasoning benchmark it scored 6.1/10 — respectable, not reliable.

Verdict on E2B: Use it for on-device apps, edge inference, or when you need sub-200ms first-token latency. Don’t trust it for anything requiring deep reasoning.

Results: E4B — The Everyday Workhorse

The E4B is where things get interesting for most developers. At 4.5B parameters it runs comfortably on any machine with 8GB RAM, and the quality jump over E2B is meaningful.

Reasoning score: 7.4/10. It handled all my multi-step problems correctly. Code quality was solid — it generated a FastAPI endpoint with proper error handling and type hints without being prompted.

The one surprise: on long-context summarization (16K tokens), the E4B started losing coherence past the midpoint of the document. It would correctly summarize the first half and make up plausible-sounding details for the second half. Keep E4B below 8K tokens for reliable output.

Verdict on E4B: The best option for local dev work on a standard laptop. Solid reasoning, fast, $0 per token.

Results: 26B MoE — The One That Broke My Expectations

This is the model that made me stop and run the test twice, because I thought my timing was wrong.

The 26B MoE generated tokens faster than the E4B on my RTX 4090. At Q4 quantization it fits in 18GB VRAM and pushes 42 tokens/second — compared to 38 tokens/second for E4B on the same hardware. That’s not a typo.

This is the MoE architecture doing exactly what it’s supposed to: only 3.8B parameters activate per token, so the compute cost is closer to a 4B model than a 26B. But the routing mechanism means the output draws on the full 26B parameter space — it just uses different slices of it depending on the context.

The quality gap over E4B is significant. Reasoning score: 9.1/10. It handled all my multi-step problems correctly, wrote better code with more edge cases covered, and maintained coherence across the full 128K context window without degradation.

Results: 31B Dense — The Best, But the Gap Is Smaller Than You Think

The 31B Dense is unambiguously the best model in the family. Reasoning score: 9.4/10. On LiveCodeBench v6 it scores 80.0% versus 77.1% for the 26B MoE. Code is cleaner, edge cases are better covered, and long-context coherence is perfect across 128K tokens.

It also ranks #3 among all open models globally on the Arena AI leaderboard, behind only a couple of models that require much larger hardware.

Head-to-Head Comparison

The 26B MoE being faster than the E4B in tokens/second on GPU is the table’s strangest number — and it’s real.

Which One Should You Actually Use?

Use E2B if you’re building something that needs to run on a phone, a Raspberry Pi, or anywhere without a proper GPU. It’s the only model in the family that runs well CPU-only.

Use E4B if you’re on a laptop with 8–16GB RAM and want a capable local model for everyday coding and writing assistance. Keep prompts under 8K tokens.

Use 26B MoE if you have a 24GB GPU. This is the right answer for 80% of developers. Near-flagship quality, faster than the smaller models on GPU, and it fits in consumer-grade hardware. This is where I’m landing for my own projects.

Use 31B Dense if you’re running inference as a service and need maximum accuracy — or if you have access to an H100 and quality is non-negotiable.

The Apache 2.0 License Changes Everything

Worth saying plainly: the fact that all four models ship under Apache 2.0 is as significant as any benchmark. You can fine-tune them, deploy them in commercial products, build SaaS on top of them, and never pay a token-based inference fee.

For teams currently paying $2.50/1M input tokens for a frontier model to power internal tools, the math shifts dramatically once you factor in the 26B MoE running on a single 4090 at $0 per query.
