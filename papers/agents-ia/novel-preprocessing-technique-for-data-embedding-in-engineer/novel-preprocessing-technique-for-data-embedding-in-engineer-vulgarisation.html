Novel Preprocessing Technique for Data Embedding in Engineering Code Generation Using Large Language Model

Vulgarisation

Quand les manuels techniques sont trop secs pour les IA

GPT-4 génère du Python correct en quelques secondes. Demandez-lui un script pour analyser la distribution de courant dans une puce électronique avec RedHawk-SC, un outil de simulation industriel d'Ansys — et il invente des noms de fonctions, mélange les API, produit du code inutilisable. Une équipe de chercheurs de l'Université Nationale de Taïwan et d'Ansys a voulu comprendre pourquoi, et surtout comment y remédier sans réentraîner le modèle.

Leur réponse tient en une idée : le problème ne vient pas du LLM lui-même, mais de la qualité des données qu'on lui fournit en contexte. En retravaillant la façon dont la documentation technique et les scripts existants sont découpés, enrichis et présentés au modèle, ils ont obtenu 73,33 % de lignes correctes sur des problèmes de génération de code MapReduce — un résultat encourageant pour un domaine où le modèle n'a strictement aucune connaissance préalable.

Le problème : des documents écrits pour des experts, pas pour des machines

La technique de Retrieval-Augmented Generation (RAG) est aujourd'hui la méthode standard pour donner à un LLM accès à des connaissances qu'il ne possède pas. Le principe : on découpe des documents en morceaux, on les convertit en vecteurs numériques (des embeddings), et quand l'utilisateur pose une question, on récupère les morceaux les plus proches sémantiquement pour les injecter dans le prompt.

Sur un manuel technique comme celui de RedHawk-SC, cette approche se heurte à deux obstacles. Le premier : le découpage. Les outils RAG classiques tranchent le texte tous les 500 ou 1 000 caractères, sans se soucier du sens. Une description de fonction API peut se retrouver coupée en deux, avec la syntaxe dans un morceau et les paramètres dans un autre. Le vecteur résultant ne représente correctement ni l'un ni l'autre.

Le second obstacle est plus insidieux. Les manuels techniques de logiciels industriels sont rédigés avec une concision extrême. Une fonction qui pilote la génération de cartes thermiques de courant dans un réseau d'alimentation tient en trois lignes : nom, syntaxe, une phrase de description. Pour un ingénieur chevronné, c'est suffisant. Pour un LLM qui doit inférer comment utiliser cette fonction dans un script complet, c'est trop maigre. L'embedding d'un chunk aussi court capture mal sa position dans l'espace sémantique, et même si le RAG le retrouve, le modèle manque de contexte pour en faire quelque chose d'utile.

À ces deux problèmes s'en ajoute un troisième : la rareté des exemples. L'équipe ne disposait que de 23 scripts RedHawk-SC. Vingt-trois. Pour un domaine entier d'ingénierie de simulation. Impossible de fine-tuner un modèle avec si peu de données, et le RAG seul ne peut pas compenser l'absence de code de référence.

La méthode : préparer les données comme on prépare un cours

Les chercheurs ont attaqué le problème sur quatre fronts simultanés. Leur pipeline de prétraitement transforme la documentation brute et les scripts existants en une base de connaissances que le RAG peut exploiter efficacement.

Découper intelligemment : le Data Splitter

Plutôt que de couper le texte à intervalles fixes, l'équipe demande au LLM lui-même de segmenter la documentation par unités sémantiques. Le modèle reçoit quelques pages de manuel et doit identifier les frontières naturelles du texte : où commence et finit la description d'une fonction, où s'arrête un concept et où en démarre un autre. Chaque morceau résultant couvre un sujet cohérent et complet.

L'analogie la plus parlante : découper un texte à taille fixe, c'est comme trancher un livre de recettes toutes les 30 lignes, en coupant potentiellement une recette au milieu des ingrédients. Le Data Splitter, lui, découpe recette par recette. Le LLM est bien adapté à cette tâche — segmenter relève de la classification binaire (couper ici ou non), un exercice plus simple que la génération de texte.

Un détail technique malin : quand le découpage tombe au milieu d'un paragraphe en bord de page, le système garde en mémoire le fragment incomplet et le rattache au contenu de la page suivante lors de l'itération suivante.

Enrichir sans inventer : la Data Renovation

Une fois les morceaux bien découpés, chacun est « rénové » par le LLM. Le modèle reçoit un chunk technique concis et doit l'enrichir en s'appuyant sur ses connaissances générales — sans rien inventer. La description laconique get_current_heatmap() — Returns a heatmap of current for all edges in the power/ground grid devient un paragraphe détaillé expliquant ce que la fonction fait, à quoi elle sert dans un contexte d'analyse, et comment l'utiliser.

Le risque évident : que le modèle ajoute des informations fausses. Les chercheurs ont conçu un double mécanisme de contrôle pour gérer ce risque.

Le premier volet, baptisé CoDRC (Chain of Density for Renovation Credibility), adapte une technique existante de résumé de texte. Le système compare le contenu avant et après rénovation, identifie tout ce qui a été ajouté, puis classe chaque ajout en trois catégories : déductible des informations fournies, déductible de connaissances techniques générales, ou ni l'un ni l'autre. Sur cette base, le LLM attribue un score de confiance entre 0 et 10.

Le second volet est l'algorithme ATR (Adaptive Text Renovation). Son principe : plus un chunk a grossi après rénovation, plus le score de confiance doit être élevé pour que la version enrichie soit retenue. L'algorithme normalise les scores de confiance et les taux de croissance du texte sur l'ensemble du corpus, puis applique un seuil ajustable. Un chunk dont le texte a doublé mais dont le score de confiance reste moyen sera rejeté — on garde la version originale. Un chunk légèrement enrichi avec un score de confiance élevé sera conservé. L'ensemble du document sert de référence pour calibrer ces décisions.

Multiplier les exemples : la Data Augmentation

Vingt-trois scripts, c'est insuffisant. L'équipe a demandé au LLM de générer de nouveaux scripts à partir des existants. Le modèle reçoit deux ou trois scripts originaux choisis au hasard, la documentation via RAG, et une consigne précise : produire un nouveau script avec une structure différente de celles fournies en référence. Pas une variation cosmétique — une reconstruction qui combine les API différemment, selon des objectifs que le modèle définit lui-même.

Cette stratégie a permis de générer 20 scripts supplémentaires à partir des 23 originaux. Des experts RedHawk-SC internes à Ansys les ont évalués : syntaxe correcte dans tous les cas, objectifs cohérents, mais des optimisations de performance restaient nécessaires. Ces scripts enrichissent la base de connaissances du RAG et lui donnent davantage d'exemples concrets de code à retrouver.

Penser avant de coder : la technique IKEC

La dernière brique est une technique de prompt baptisée IKEC (Implicit Knowledge Expansion and Contemplation). L'idée : demander au modèle de réfléchir en interne à ce qu'il sait sur un sujet avant de produire sa réponse, mais sans lui demander d'écrire cette réflexion. Contrairement au Chain-of-Thought classique où le modèle détaille son raisonnement étape par étape (ce qui augmente le nombre de tokens et le coût), IKEC lui dit en substance : « Prends le temps de mobiliser tes connaissances sur MapReduce et Python, garde ça pour toi, puis génère ta réponse en t'appuyant dessus. »

Le test est parlant. Sur un même squelette de code à compléter, le RAG seul produit un script auquel il manque le calcul du nombre de couches et la valeur de retour du MapReduce. Avec IKEC, ces deux éléments sont présents et corrects. La seule erreur résiduelle est un nom de fonction mal orthographié — le type d'erreur que le prétraitement des données peut justement aider à corriger en fournissant les bons noms via RAG.

Résultats clés : 73 % de lignes correctes, sans aucun réentraînement

L'expérience préliminaire a porté sur cinq scripts de test. Pour chacun, les chercheurs ont rédigé manuellement une requête utilisateur (« génère un code pour obtenir les instances d'horloge dans RedHawk-SC, optimisé avec MapReduce »), puis mesuré le pourcentage de lignes de code correctes dans la sortie du modèle. Une ligne est comptée comme incorrecte si elle contient un nom de fonction erroné, une erreur de syntaxe, ou une omission logique.

Le pipeline complet — RAG avec données prétraitées, combiné au workflow ChatEDA et à la technique IKEC — a atteint en moyenne 73,33 % de lignes correctes. Sur l'exemple détaillé dans l'article, la version avec IKEC obtient 93,10 % (2 lignes erronées sur 29), contre 86,21 % pour le RAG seul (4 lignes erronées sur 29). Les deux lignes d'écart correspondent exactement aux erreurs logiques que la réflexion implicite du modèle a permis d'éviter : le retour de la structure de données et le résultat du MapReduce.

Les auteurs sont transparents sur les limites de ces chiffres. Cinq scripts de test, c'est un échantillon minimal. L'expérience complète, conçue mais pas encore réalisée au moment de la publication, prévoit 20 scripts classés par difficulté (facile, moyenne, difficile), évalués par des tests unitaires conçus par des experts Ansys, et comparés à travers dix configurations expérimentales incluant des études d'ablation pour isoler la contribution de chaque composant.

Pourquoi ça compte : du code spécialisé sans fine-tuning

Le résultat le plus significatif de ce travail n'est pas le chiffre de 73 %. C'est la démonstration qu'on peut obtenir une génération de code fonctionnelle dans un domaine totalement inconnu du LLM, sans réentraîner le modèle, en travaillant uniquement sur la préparation des données fournies en contexte.

Le fine-tuning d'un modèle de langage exige des données d'entraînement abondantes, des ressources de calcul conséquentes, et un accès aux poids du modèle — ce qui exclut les modèles propriétaires comme GPT-4. L'approche proposée ici ne demande que la documentation existante et quelques scripts de référence. Elle peut être déployée en quelques jours sur n'importe quel outil industriel disposant d'une API documentée.

Pour les éditeurs de logiciels de simulation, c'est une piste concrète. Leurs clients passent un temps considérable à écrire des scripts d'automatisation. Si un assistant IA peut en générer des versions fonctionnelles à 70 ou 80 %, même imparfaites, le gain de productivité est réel — l'ingénieur corrige et optimise plutôt que de partir de zéro.

La technique de rénovation des données a aussi des applications au-delà de la génération de code. Toute entreprise qui utilise le RAG sur de la documentation technique interne — manuels de maintenance, spécifications d'API, protocoles industriels — se heurte au même problème de concision excessive. Enrichir automatiquement ces chunks avant de les indexer pourrait améliorer la qualité des réponses de n'importe quel chatbot documentaire, à condition de contrôler la fiabilité des ajouts comme le font CoDRC et ATR.

Questions ouvertes et pistes futures

L'honnêteté des auteurs sur l'état préliminaire de leurs résultats mérite d'être soulignée. L'expérience complète avec 20 scripts, tests unitaires et études d'ablation n'a pas été menée. Sans ces données, on ne peut pas affirmer quelle part de l'amélioration vient du Data Splitter, quelle part de la Renovation, et quelle part d'IKEC. Les interactions entre composants restent inexplorées.

La technique IKEC soulève une question de reproductibilité. Demander à un modèle de « réfléchir intérieurement » sans tracer cette réflexion rend le processus opaque. Fonctionne-t-elle parce qu'elle modifie réellement le traitement interne du modèle, ou simplement parce que le prompt plus élaboré oriente mieux la génération ? Sans accès aux états internes du modèle, la distinction est difficile à établir.

L'évaluation par « pourcentage de lignes correctes » est pragmatique mais grossière. Une ligne manquante dans un import peut casser tout le script ; une erreur dans un commentaire n'a aucun impact. L'expérience complète prévoit des tests unitaires et un critère d'exécutabilité, ce qui donnera une mesure plus fiable de l'utilité réelle du code généré.

Reste la question de la généralisation. RedHawk-SC est un cas extrême : documentation minimaliste, quasi-aucun code public, domaine ultra-spécialisé. Si la méthode fonctionne ici, elle devrait fonctionner sur des outils mieux documentés. Mais chaque domaine a ses particularités — la structure des API, le style de la documentation, la complexité des interactions entre fonctions. Tester le pipeline sur d'autres logiciels industriels (outils CAO, simulateurs thermiques, plateformes de test automatisé) serait la prochaine étape logique pour valider sa portabilité.

Ce travail a remporté le premier prix dans la catégorie IA générative au concours Tech New Stars organisé par le Ministère des Affaires Économiques de Taïwan — une reconnaissance qui, au-delà du palmarès, indique que le problème de la génération de code spécialisé intéresse au-delà du monde académique.
