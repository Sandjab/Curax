Scaling Coding Agents via Atomic Skills

Vulgarisation

Apprendre aux agents codeurs les gestes élémentaires plutôt que les tours complets

1. Quand les agents IA codent… mais n'apprennent pas vraiment

Un agent de code entraîné à corriger des bugs corrige des bugs. Demandez-lui de refactorer du code, et ses performances s'effondrent. Ce constat, mesuré et documenté par une équipe de chercheurs de HKUST, NUS et PKU, pointe un défaut structurel dans la façon dont l'industrie forme ses agents de programmation. L'article Scaling Coding Agents via Atomic Skills, publié en avril 2026, propose une approche radicalement différente : au lieu d'entraîner les agents sur des tâches complètes, leur enseigner les compétences élémentaires qui composent ces tâches.

L'idée paraît simple. Sa mise en œuvre ne l'est pas. Et les résultats — une amélioration moyenne de 18,7 % sur dix benchmarks distincts — suggèrent que la communauté a peut-être pris le problème à l'envers depuis le début.

2. Le piège de l'entraînement sur tâches composites

Depuis l'apparition de SWE-bench en 2023, la norme pour évaluer (et entraîner) les agents de code consiste à leur soumettre des tâches complètes : résoudre un ticket GitHub, corriger un bug vérifié par une suite de tests, implémenter une fonctionnalité. Ces tâches sont dites composites parce qu'elles exigent simultanément plusieurs capacités — comprendre un rapport de bug, localiser le code concerné, rédiger un correctif, vérifier qu'il ne casse rien.

Le problème : quand on entraîne un modèle sur ce type de tâche par apprentissage par renforcement (RL), la seule récompense qu'il reçoit est binaire. Les tests passent, ou ils ne passent pas. Le modèle n'a aucune indication sur ce qu'il a bien fait dans sa démarche. A-t-il localisé le bon fichier ? Son correctif est-il propre ? Ses tests de non-régression tiennent-ils la route ? Mystère. L'agent optimise un score global sans feedback sur les étapes intermédiaires.

La conséquence est prévisible : l'agent mémorise des raccourcis propres à la distribution d'entraînement. Il apprend des heuristiques fragiles — des patterns qui fonctionnent sur SWE-bench mais s'effondrent dès qu'on change de contexte. Les chercheurs le démontrent avec un graphique frappant : un agent entraîné uniquement sur la correction de bugs voit sa performance en refactoring stagner, voire régresser. Le transfert d'une tâche composite à une autre est quasi nul.

L'autre difficulté est l'extensibilité. Créer un benchmark composite exige un effort considérable : il faut des dépôts réels, des suites de tests, des environnements d'exécution. Chaque nouveau type de tâche (sécurité, optimisation de performance, migration de code) demande une infrastructure dédiée. On ne peut pas couvrir l'infinie diversité des tâches réelles de développement logiciel en multipliant les benchmarks composites.

3. Cinq gestes fondamentaux pour tout construire

L'analogie la plus parlante vient de la musique. Un pianiste qui ne répéterait que des morceaux complets, sans jamais travailler ses gammes, ses arpèges ou son déchiffrage, développerait des automatismes limités aux pièces qu'il connaît. Face à une partition inédite, il serait démuni. Le travail technique isolé — les gammes — construit la dextérité transférable qui permet d'aborder n'importe quel morceau.

Ma et ses collègues appliquent cette logique aux agents de code. Ils décomposent le travail de développement logiciel en cinq compétences atomiques, définies selon trois critères : chaque compétence doit avoir des entrées et sorties précises, être évaluable sans ambiguïté, et servir de brique réutilisable pour des tâches plus complexes.

La localisation de code consiste à identifier, dans un dépôt entier, quels fichiers doivent être modifiés pour résoudre un problème donné. L'agent reçoit la description d'un ticket et doit produire une liste de chemins de fichiers. La récompense est stricte : soit la liste correspond exactement aux fichiers modifiés dans le correctif de référence, soit elle ne correspond pas. Pas de crédit partiel.

L'édition de code isole la capacité à modifier du code correctement. On fournit à l'agent le contexte du code et l'instruction précise de modification. La validation passe par l'exécution des tests unitaires et de non-régression : tous les tests doivent passer.

La génération de tests unitaires évalue si l'agent produit des tests qui valident le bon comportement d'une fonction et détectent des erreurs introduites volontairement. Pour créer les erreurs de référence, les chercheurs utilisent un autre modèle de langage (Kimi-K2-Thinking) qui génère seize variantes buguées mais plausibles de chaque fonction cible. Les tests de l'agent doivent passer sur le code correct et échouer sur chaque variante défectueuse.

La reproduction de bug demande à l'agent de créer un script minimal qui déclenche le problème décrit dans un ticket. Le script doit échouer sur le code original et réussir après application du correctif. Un juge automatique — encore un modèle de langage — compare les logs d'exécution avant et après le patch pour vérifier que le bug apparaît puis disparaît.

Enfin, la revue de code évalue si l'agent peut juger la qualité d'une pull request. On lui présente un ticket et un correctif proposé, et il doit déterminer si le correctif résout effectivement le problème. La récompense est binaire : le jugement de l'agent correspond-il à la réalité vérifiée par les tests ?

Ces cinq compétences ne couvrent pas tout le spectre du développement logiciel. Mais elles se combinent pour résoudre la grande majorité des tâches courantes. Corriger un bug, par exemple, mobilise la localisation, l'édition et la reproduction. Le refactoring s'appuie sur la localisation, l'édition et la revue. La sécurité implique la reproduction, l'édition et la génération de tests.

4. L'entraînement conjoint : les résultats qui changent la donne

Le modèle de base utilisé est GLM-4.5-Air-Base, un modèle de 106 milliards de paramètres dont 12 milliards sont actifs à chaque inférence (architecture MoE — Mixture of Experts). Les chercheurs commencent par un fine-tuning supervisé (SFT) sur 1 500 trajectoires vérifiées, soit 300 par compétence atomique. Ces trajectoires proviennent d'un modèle puissant (GPT-oss-120B) et ont été validées par des juges automatiques.

Vient ensuite la phase d'apprentissage par renforcement conjoint. Le terme « conjoint » est central : au lieu d'entraîner un modèle séparé par compétence, un unique modèle s'entraîne sur les cinq compétences simultanément. Les tâches sont mélangées dans un tampon unifié. À chaque épisode d'entraînement, le modèle tire une tâche au hasard parmi les cinq types, interagit avec un environnement sandboxé (commandes bash, édition de fichiers), et reçoit sa récompense spécifique à la compétence.

L'optimisation repose sur GRPO (Group-based Relative Policy Optimization), un algorithme qui compare les performances relatives au sein d'un groupe de tentatives plutôt que d'évaluer chaque tentative isolément. Pour une même tâche, le modèle génère plusieurs solutions candidates, et l'algorithme renforce celles qui surpassent la moyenne du groupe. Cette approche relative résout un problème technique important : les échelles de récompense diffèrent entre compétences, et comparer directement les scores absolus fausserait l'entraînement.

L'infrastructure sous-jacente est un investissement massif. Plus de 10 000 sandboxes d'exécution concurrentes tournent sur des clusters Kubernetes hybrides. Chaque sandbox est éphémère — créée à la demande, détruite après usage — pour éviter toute fuite d'état entre épisodes. Plus de 25 000 images Docker pré-construites fournissent les environnements de test. L'accès réseau est coupé et l'historique Git supprimé dans chaque sandbox, pour empêcher le modèle de tricher en cherchant les réponses en ligne ou dans les commits.

Les chiffres de performance racontent une histoire nette. Sur les cinq compétences atomiques, le modèle entraîné par RL conjoint (SFT+RL) dépasse systématiquement le modèle SFT seul : localisation passe de 0,665 à 0,712, édition de 0,458 à 0,611, reproduction de 0,542 à 0,605, génération de tests de 0,359 à 0,472, revue de code de 0,563 à 0,622. Les cinq courbes d'apprentissage montent de façon monotone — aucune compétence ne régresse quand les autres progressent.

Le résultat le plus remarquable concerne la généralisation. Les chercheurs évaluent le modèle sur cinq benchmarks composites qu'il n'a jamais vus pendant l'entraînement : SWE-bench Verified (correction de bugs Python), SWE-bench Multilingual (bugs multi-langages), Terminal-Bench (tâches en ligne de commande), un benchmark de refactoring maison, et SEC-Bench (sécurité). Sur chacun de ces benchmarks, le modèle SFT+RL surpasse le modèle SFT. Sur SWE-bench Verified, le score passe de 0,507 à 0,585 — une amélioration relative de 15 %. Et le modèle dépasse même GLM-4.5-Air, la version complètement post-entraînée du même modèle de base, sur plusieurs de ces benchmarks.

L'étude d'ablation enfonce le clou. Un modèle entraîné par RL uniquement sur l'édition de code (single-skill RL) améliore bien sa compétence d'édition, mais ses gains sur les autres compétences et les tâches composites restent faibles et irréguliers. Un modèle entraîné uniquement sur SWE-bench Verified (single-benchmark RL) atteint un score comparable sur ce benchmark spécifique, mais transfère mal vers le refactoring ou la sécurité. Le RL conjoint sur les compétences atomiques est le seul à produire des gains larges et cohérents.

5. Ce que ça change concrètement

Pour les équipes qui développent des agents de code, cette recherche remet en question la stratégie dominante. Investir massivement dans la collecte de données pour un benchmark spécifique (SWE-bench, par exemple) produit un agent spécialiste. Investir dans cinq jeux de données plus simples, un par compétence atomique, produit un agent généraliste qui se débrouille aussi bien — voire mieux — sur le benchmark cible, tout en fonctionnant sur des tâches inédites.

L'argument économique est direct. Construire un benchmark composite de qualité coûte cher : il faut des dépôts réels, des tests fonctionnels, une validation manuelle. Les compétences atomiques, elles, se prêtent à la génération semi-automatique. La localisation de code se construit à partir de n'importe quelle pull request résolue. La génération de tests se fabrique à partir de n'importe quel dépôt qui possède déjà une suite de tests. Le pipeline est extensible sans intervention humaine lourde.

Pour les utilisateurs finaux — développeurs qui utilisent des assistants de code au quotidien —, les implications touchent la fiabilité. Un agent qui maîtrise la localisation produira moins de correctifs appliqués au mauvais endroit. Un agent entraîné à la revue de code détectera mieux les faux correctifs. Un agent capable de reproduire un bug vérifiera ses propres corrections. Ces compétences, invisibles dans un benchmark global, constituent la différence entre un assistant utile et un assistant qui génère du travail supplémentaire.

La décomposition en compétences atomiques offre aussi un levier de diagnostic. Quand un agent composite échoue sur une tâche, il est difficile de savoir pourquoi. A-t-il mal localisé le problème ? Mal édité le code ? Mal vérifié son correctif ? Avec des compétences évaluées séparément, on peut identifier le maillon faible et concentrer les efforts d'amélioration dessus.

6. Questions ouvertes et pistes de recherche

Cinq compétences atomiques ne suffisent probablement pas à couvrir l'ensemble du génie logiciel. La gestion des dépendances, la rédaction de documentation, l'optimisation de performance, la migration entre versions d'un framework — autant de capacités qui ne se réduisent pas aux cinq compétences identifiées ici. Les auteurs le reconnaissent et suggèrent d'étendre la bibliothèque de compétences. La question est de savoir si l'ajout de nouvelles compétences continuera à produire des gains positifs ou si des interférences apparaîtront au-delà d'un certain nombre.

Le modèle utilisé (106 milliards de paramètres, 12 milliards actifs) est un modèle massif. Les auteurs notent eux-mêmes un « effet de seuil » : les modèles plus petits peinent à suivre les instructions de base nécessaires pour l'exploration en RL. La transposabilité de la méthode à des modèles de taille plus modeste reste une inconnue. Si seuls les modèles géants bénéficient du RL conjoint sur compétences atomiques, l'approche restera confinée aux laboratoires disposant de ressources de calcul massives.

La question de la composition elle-même mérite exploration. Les auteurs montrent que les compétences atomiques se transfèrent vers des tâches composites, mais le mécanisme exact de cette composition reste une boîte noire. Le modèle apprend-il implicitement à chaîner les compétences ? Développe-t-il des représentations partagées qui servent de fondation commune ? Ou bien les gains observés résultent-ils simplement d'un meilleur alignement général avec les tâches de développement ? Des travaux d'analyse mécanistique pourraient éclairer ce point.

Enfin, l'infrastructure décrite — 10 000 sandboxes concurrentes, 25 000 images Docker — représente un investissement que peu d'organisations peuvent reproduire. Le coût de la décontamination des données (vérifier qu'aucune instance de test n'apparaît dans les données d'entraînement) et de la validation des trajectoires par des modèles juges ajoute une couche de complexité supplémentaire. Des efforts de reproduction indépendants, sur des modèles open-source plus accessibles, confirmeraient la robustesse de l'approche.

Ce qui se dégage de ce travail dépasse le cadre des agents de code. L'idée de décomposer une capacité complexe en sous-compétences évaluables indépendamment, puis de les entraîner conjointement, pourrait s'appliquer à d'autres domaines agentiques : la recherche automatisée, l'analyse de données, la gestion de systèmes. Le principe reste le même — maîtriser les gammes avant de jouer le concerto.
