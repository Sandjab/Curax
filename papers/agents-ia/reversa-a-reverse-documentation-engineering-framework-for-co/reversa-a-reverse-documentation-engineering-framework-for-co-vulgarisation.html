Reversa: A Reverse Documentation Engineering Framework for Converting Legacy Software into Operational Specifications for AI Agents

Vulgarisation

Quand le COBOL rencontre les agents IA

Un distributeur automatique de billets écrit en COBOL dans les années 1990 fonctionne encore aujourd'hui dans bien des banques. Les règles métier qu'il applique — plafond de retrait, formatage monétaire, gestion des comptes à découvert — vivent dans des fichiers .DAT, des noms de variables abrégés et la tête de l'ingénieur de maintenance qui part bientôt à la retraite. Le code marche, mais personne ne sait vraiment pourquoi il marche comme ça.

Sanderson Macedo et Ronaldo Costa, deux chercheurs brésiliens, ont publié en mai 2026 une proposition pour résoudre un problème devenu pressant : comment confier la modernisation de ces systèmes à des agents IA codeurs si ces derniers n'ont aucun contrat de comportement à respecter ? Leur réponse s'appelle Reversa, un framework d'ingénierie inverse de la documentation. L'idée n'est pas de générer du code, mais de produire les spécifications opérationnelles dont les agents ont besoin pour modifier un système sans le casser.

Le vrai problème : la connaissance fantôme du legacy

Quand on parle de système legacy, on pense souvent à du vieux code. C'est réducteur. Un système legacy concentre surtout des décisions accumulées sur des années : règles de gestion arbitrées en réunion il y a quinze ans, exceptions opérationnelles ajoutées suite à un incident client, conventions de données héritées d'une migration partielle de 2003. Une partie de cette connaissance se lit dans les noms de fonctions ou les requêtes SQL. Le reste est tacite : il vit dans la mémoire des équipes, dans des patterns d'implémentation, dans l'historique des changements.

Les agents IA capables de modifier du code — Claude Code, Cursor, SWE-agent et leurs cousins — supposent que la tâche est claire, que les critères de correction sont fournis et que le contexte tient dans le prompt. Cette hypothèse tombe dès qu'on les met face à un système non documenté. L'agent voit le code, infère un comportement plausible, modifie ce qu'il croit comprendre, et casse silencieusement une règle métier que personne ne lui avait expliquée.

La littérature récente a bien identifié les briques voisines du problème. On sait extraire de la documentation au niveau d'un dépôt avec des LLM (RepoAgent), générer des spécifications à partir de commentaires (Xie et al.), et faire travailler des agents sur de vrais bugs de production (SWE-bench). Ce qui manquait, c'est le pont entre ces briques : transformer un système legacy sans spécification existante en contrats opérationnels traçables, marqués par leur niveau de certitude.

La méthode : une équipe d'agents qui fouillent le code

Reversa décompose le travail d'archéologie logicielle en une équipe d'agents spécialisés, chacun avec un rôle précis et des livrables définis. La métaphore filée par les auteurs — qu'on retrouve jusque dans les noms — est celle d'une enquête.

  • Scout cartographie la surface du projet : langages, dépendances, points d'entrée. Il dresse l'inventaire initial.
  • Archaeologist creuse les modules un par un, classifie les faits techniques observables.
  • Detective extrait les règles métier implicites : permissions, états, exceptions cachées.
  • Architect synthétise l'architecture, les dépendances entre composants, la matrice d'impact.
  • Writer traduit ce matériau en spécifications unitaires : requirements.md, design.md, tasks.md.
  • Reviewer relit, retourne au code source pour vérifier les affirmations fragiles, reclasse les éléments douteux.

L'intérêt de cette décomposition ne tient pas à une supériorité magique du multi-agent sur l'agent unique. Elle tient à la traçabilité du raisonnement : si une affirmation se révèle fausse plus tard, on peut remonter à l'étape qui l'a produite et corriger le maillon. C'est l'équivalent logiciel d'une chaîne de garde judiciaire pour la preuve.

Le modèle de confiance : la vraie idée différenciante

La contribution la plus intéressante de Reversa n'est pas l'architecture multi-agent, qui ressemble à ChatDev et consorts. C'est le traitement explicite de l'incertitude. Chaque affirmation produite par le pipeline est étiquetée selon trois statuts :

  • Une affirmation confirmée repose sur une preuve directe dans le code ou un artefact vérifiable.
  • Une affirmation inférée s'appuie sur des patterns récurrents, des noms, des structures — sans certitude.
  • Un gap enregistre ce qui n'a pas pu être déterminé de manière sûre et nécessite une validation humaine.

Cette distinction tranche avec la production habituelle des LLM, qui mélangent allégrement faits et hallucinations dans une prose fluide. Macke et Doyle ont montré empiriquement qu'une documentation incorrecte dégrade la compréhension du code par un LLM, alors qu'une documentation absente ou incomplète ne produit pas le même type de dommage. Conclusion logique : mieux vaut une spécification honnête sur ses trous qu'une documentation lisse qui présente des suppositions comme des faits.

Une installation qui ne casse pas le projet hôte

Reversa se distribue comme un paquet Node.js, installable via npx reversa install. La CLI détecte les moteurs d'agents disponibles (Claude Code, Codex, Cursor, Gemini CLI, Windsurf, Aider et une dizaine d'autres) et copie les skills d'agents au bon endroit pour chacun. Le framework écrit son état sous .reversa/ et ses artefacts sous _reversa_sdd/.

Détail souvent négligé dans les outils de ce type : un manifeste SHA-256 enregistre les hash de chaque fichier installé. À la mise à jour ou à la désinstallation, Reversa sait distinguer un fichier intact, un fichier modifié par l'utilisateur, et un fichier disparu. Les fichiers modifiés sont préservés. C'est trivial à décrire, mais ça évite la classe d'incidents où un outil bien intentionné écrase trois jours de personnalisation.

Le test grandeur nature : un DAB COBOL vers Go

Les auteurs ont mis Reversa à l'épreuve sur un cas concret : la migration d'un distributeur de billets monoposte écrit en GnuCOBOL vers une réimplémentation en Go. Cinq modules dans le scope : MENU, CONTA, EXTRATO, UTIL, kbdread. Aucun test automatisé existant. Persistance sur fichiers .DAT indexés. Le contexte typique du legacy qu'on n'ose pas toucher.

Le pipeline a tourné entre le 4 et le 7 mai 2026 et a produit 517 affirmations sur le scope actif. La répartition par module :

  • 490 affirmations confirmées, 24 inférées, 3 marquées comme gap.
  • Index de confiance interne calculé : 97,1 % (les confirmées valent 1, les inférées 0,5).
  • 10 gaps projet enregistrés : 3 critiques, 3 modérés, 2 cosmétiques, 2 hors scope.
  • 53 scénarios Gherkin de parité couvrant login, solde, retrait, dépôt, virement, relevé, formatage monétaire, masquage clavier.

Sur les 11 tâches du plan de reconstruction, 9 ont été terminées au moment de l'inventaire : packages Go, persistance SQLite, point d'entrée CLI, modules métier. La parité Docker était en cours. Le cutover final restait en suspens. Les auteurs sont honnêtes sur ce point : ils ne revendiquent pas une migration achevée, juste une démonstration que le pipeline structure le travail.

L'index de 97,1 % mérite une mise en garde que les auteurs eux-mêmes soulignent. Ce nombre mesure la classification produite par le pipeline lui-même, pas la précision factuelle des affirmations. Aucun audit indépendant n'a vérifié si les 490 affirmations « confirmées » étaient effectivement vraies. C'est un index opérationnel, pas un score de qualité.

Pourquoi ça intéresse les équipes qui modernisent du legacy

La modernisation de systèmes legacy reste l'un des chantiers les plus coûteux de l'industrie logicielle. Les banques, assurances, administrations et entreprises industrielles font tourner des millions de lignes de COBOL, RPG, ABAP ou Visual Basic 6 dont la connaissance opérationnelle s'évapore avec les départs en retraite. Les estimations varient mais le marché de la modernisation pèse plusieurs dizaines de milliards de dollars par an.

Jusqu'ici, deux options dominaient. Le lift-and-shift déplace le code sans le comprendre, en émulant l'environnement d'origine. Le rewrite reconstruit à partir de spécifications recueillies en interrogeant les utilisateurs et en lisant le code, exercice long et coûteux. Les agents IA promettaient une troisième voie : laisser une IA lire le code legacy et écrire le code moderne. Cette promesse butte sur le mur de la connaissance implicite.

Reversa propose une étape intermédiaire qui change la nature du problème. Au lieu de demander à un agent de tout faire d'un coup, on lui demande d'abord de produire une documentation traçable avec des trous explicites. La validation humaine se concentre sur les gaps et les inférences fragiles, pas sur la totalité du code. Les agents de migration héritent ensuite d'un contrat clair plutôt que d'une intuition.

L'autre effet concerne la responsabilité. Quand un agent IA modifie un système financier sans contrat de comportement, l'équipe qui a appuyé sur le bouton porte une responsabilité diffuse. Quand le même agent travaille à partir de spécifications explicites avec des niveaux de confiance, on peut tracer une mauvaise modification jusqu'à une affirmation inférée mal validée. C'est un changement qualitatif pour les domaines régulés.

Pour aller plus loin : limites et angles morts

L'étude reste exploratoire et les auteurs ne s'en cachent pas. Un seul système analysé, un domaine bancaire simplifié, un seul stakeholder, un projet éducatif sans usage en production. Aucune comparaison contrôlée contre un agent unique, un outil de documentation classique, ou une exécution sans spécifications préalables. Aucune mesure d'utilité aval avec des agents codeurs réels. Le protocole d'évaluation existe sur le papier ; son application complète attend des cas d'étude supplémentaires.

Plusieurs questions méritent un examen sérieux avant d'envisager un déploiement industriel. La maintenance des spécifications coûte-t-elle plus cher que ce qu'elle économise en aval ? Une étude de cartographie de Tian et al. (2021) montre que la traçabilité aide la maintenance mais introduit ses propres coûts. Le cas Reversa hérite de ce compromis sans le résoudre.

Le modèle de confiance dépend entièrement de l'agent qui produit l'étiquette. Rien n'empêche un LLM mal calibré de marquer comme « confirmé » ce qui n'est qu'une coïncidence textuelle. Sans audit externe, l'index de 97,1 % reste auto-déclaratif. Une évolution naturelle serait d'introduire un agent vérificateur indépendant, idéalement basé sur un modèle différent, pour casser la corrélation des erreurs intra-modèle.

La portabilité multi-moteur est élégante en théorie. Elle suppose en pratique que les skills installés produisent des résultats comparables à travers Claude Code, Codex, Cursor et les autres. Les modèles sous-jacents diffèrent, leurs comportements diffèrent, et un même prompt peut produire des spécifications de qualité hétérogène. Le framework laisse cette variance à la charge de l'utilisateur.

Enfin, le cas COBOL-vers-Go est presque optimal pour ce type d'exercice : un domaine bien borné, un langage source dont la sémantique est stable, une cible moderne riche en bibliothèques. Les vrais legacy qui font peur — gros mainframes avec millions de lignes, dépendances sur des produits propriétaires, comportements liés à des chronométrages de production — restent à éprouver. Les auteurs annoncent une extension à des projets industriels diversifiés comme prochaine étape. C'est là qu'on saura si l'approche tient la charge ou si elle reste un beau pattern de laboratoire.

Reversa propose un cadre conceptuel qui mérite l'attention pour une raison simple : il prend au sérieux l'idée que les agents IA codeurs ont besoin de contrats, pas seulement de contexte. Que le framework lui-même survive ou soit remplacé par un concurrent, cette intuition restera. Avant de demander à une IA de réécrire un système legacy, il faut d'abord lui dire ce que ce système est vraiment censé faire — et reconnaître honnêtement ce qu'on ne sait pas.
