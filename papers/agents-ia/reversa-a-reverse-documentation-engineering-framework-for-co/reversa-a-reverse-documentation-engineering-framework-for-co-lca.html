Reversa: A Reverse Documentation Engineering Framework for Converting Legacy Software into Operational Specifications for AI Agents

Lecture Critique d'Article

Objectif et contexte

Reversa s'attaque à un point de friction concret : les agents de coding ont besoin de contrats comportementaux explicites pour modifier du code en production, or les systèmes legacy concentrent des règles métier, exceptions opérationnelles et conventions tacites qui n'existent comme spécification nulle part. Les auteurs introduisent le terme « reverse documentation engineering » pour désigner la dérivation, depuis un système existant, d'artefacts documentaires traçables, marqués par un niveau de confiance et accompagnés de lacunes assumées.

Quatre questions de recherche structurent le travail : décomposition multi-agents (RQ1), mécanismes de traçabilité et de confiance (RQ2), séparation des rôles agentiques (RQ3) et protocole d'évaluation (RQ4). Le positionnement est explicitement modeste : un framework, un protocole, et un premier point empirique exploratoire — pas une démonstration de supériorité.

Méthodologie

Le framework est livré comme CLI Node.js (npx reversa install) compatible avec une quinzaine de moteurs d'agents (Claude Code, Codex, Cursor, Gemini CLI, Copilot, Aider, etc.). L'architecture sépare trois couches : installation préservée par manifeste SHA-256, équipes d'agents skills-based, et artefacts générés dans _reversa_sdd/.

Le pipeline Discovery enchaîne sept rôles : un orchestrateur, Scout (cartographie), Archaeologist (analyse modulaire), Detective (règles métier), Architect (synthèse), Writer (spécifications unitaires), Reviewer (relecture de confiance). Chaque affirmation est classée confirmed, inferred ou gap. Des équipes additionnelles (Migration, Code Forward) prolongent la boucle vers la modernisation.

L'évaluation propose sept métriques candidates : couverture fichiers, couverture unités, densité de traçabilité, distribution de confiance, gaps bloquants, précision experte, utilité agent. Le protocole en cinq étapes (état initial, installation, exécution, revue, évaluation) reste largement non instancié : sur les sept métriques, seules trois sont effectivement mesurées dans l'étude de cas.

Résultats principaux

L'étude de cas porte sur banco-atm, un ATM COBOL éducatif (modules MENU, CONTA, EXTRATO, UTIL, kbdread) migré vers Go avec SQLite. Le pipeline a produit en quatre jours (4–7 mai 2026) : 517 claims dans le périmètre actif (490 confirmés, 24 inférés, 3 gaps), 10 gaps projet (3 critiques, 3 modérés, 2 cosmétiques, 2 hors périmètre), 53 scénarios Gherkin de parité, et un plan de reconstruction de 11 tâches dont 9 complétées.

L'indice de confiance interne calculé est de 97,1 % (confirmés = 1,0 ; inférés = 0,5). Les auteurs précisent immédiatement que ce chiffre reflète l'auto-classification du pipeline et ne mesure pas la précision factuelle — aucun audit indépendant n'a été conduit. La parité Docker était en cours et le cutover final non réalisé au moment de l'inventaire.

Discussion et limites

La principale faiblesse est structurelle : n = 1, sur un système éducatif simplifié, sans tests préexistants, sans intégrations de production, avec un unique stakeholder. Aucune comparaison contrôlée n'est conduite contre les trois baselines pourtant identifiées par les auteurs eux-mêmes : prompt unique sans décomposition de rôles, agent générique sans spécifications préalables, outil de documentation conventionnel.

L'indice de confiance de 97,1 % est trompeur pris isolément : il mesure ce que le pipeline pense de son propre output, pas la véracité factuelle des claims. Sur les sept métriques proposées, expert precision et agent utility — les deux qui mesureraient vraiment l'intérêt du framework — sont explicitement non mesurées. La section 7 (threats to validity) est cependant remarquablement honnête : les auteurs nomment chacune de ces limites sans euphémisme.

Le risque conceptuel non discuté tient à la circularité du marquage de confiance : un même LLM produit les claims et les classe ; un Reviewer issu du même modèle peut partager les biais du Writer. Le protocole prévoit la revue humaine comme garde-fou, mais elle n'est ni quantifiée ni intégrée à l'étude.

Reproductibilité

Le framework est distribué comme package Node.js, ce qui facilite la reproduction de la mécanique d'installation. En revanche, le code source du projet ATM, les prompts exacts des agents, les artefacts générés (_reversa_sdd/) et les 53 scénarios Gherkin ne sont pas mis à disposition dans l'article. Le projet banco-atm n'est pas référencé publiquement. La reproduction exacte de l'étude de cas est donc impossible en l'état.

Impact et applications

Le repositionnement de la documentation legacy comme contrat opérationnel pour agents, plutôt que comme texte narratif pour humains, est la contribution conceptuelle la plus solide. La distinction explicite confirmed/inferred/gap répond à un problème réel documenté par Macke & Doyle [23] : une documentation incorrecte dégrade la compréhension du code par les LLM, alors qu'une documentation absente est moins nocive.

L'architecture portable multi-moteurs et la préservation par manifeste SHA-256 traitent un point pratique souvent négligé dans les frameworks agentiques : la coexistence avec les fichiers du projet hôte. La boucle Discovery → Migration → Code Forward esquisse un cycle de vie où la documentation inverse devient un artefact maintenu, pas un livrable jetable.

Positionnement dans la littérature

Le tableau 1 de l'article structure le positionnement contre quatre lignes : reverse engineering classique (Washizaki et al. [35], Reis & Silva [27]), documentation repository-level avec LLM (RepoAgent [22], Diggs et al. sur la modernisation legacy [9]), génération de spécifications (Xie et al. [37], Krishna et al. [18], ReqInOne [42]), et agents logiciels (SWE-bench [15], SWE-agent [38], ChatDev [26]).

Le différentiel revendiqué est l'intersection : partir du code legacy (pas de commentaires existants), produire des contrats opérationnels (pas seulement de la narration), avec traçabilité et confiance explicites, à destination d'agents (pas d'humains). Ce positionnement est défendable conceptuellement, mais l'absence de comparaison empirique contre ne serait-ce qu'un prompt mono-agent laisse ouverte la question : la décomposition en sept rôles apporte-t-elle réellement quelque chose face à un Claude/GPT-4 unique avec un prompt structuré ?

Conclusion analytique. L'article est mieux lu comme un position paper avec implémentation outillée que comme une validation empirique. Le cadre conceptuel — séparer claims confirmés, inférés et gaps pour servir des agents de coding — est solide et opérationnellement testable. La validation reste à faire : trois à cinq cas industriels, comparaison contre prompt mono-agent, mesure d'agent utility downstream, audit externe des claims. En l'état, Reversa propose un vocabulaire et un outil ; l'évidence empirique reste à construire.
