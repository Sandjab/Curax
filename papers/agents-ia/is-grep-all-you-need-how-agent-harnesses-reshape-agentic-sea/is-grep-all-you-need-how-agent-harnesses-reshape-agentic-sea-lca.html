Is Grep All You Need? How Agent Harnesses Reshape Agentic Search

Lecture Critique d'Article

Objectif et contexte

Les auteurs interrogent une convention installée des systèmes RAG : la supériorité supposée de la recherche vectorielle dense sur la recherche lexicale dans les boucles agentiques. Leur thèse est que cette comparaison a été conduite hors contexte agentique, sur des pipelines statiques où le top-k est concaténé dans le prompt. Or, dans un agent moderne, le harness décide quand chercher, comment formuler la requête, comment ingérer les résultats et quand s'arrêter.

Deux questions structurent l'article. D'abord, lexical ou dense produit-il un avantage stable lorsque le harness et le mode de livraison des résultats (inline vs fichier) varient ? Ensuite, ces deux familles se dégradent-elles de la même façon quand on injecte progressivement des sessions distractrices autour des sessions oracles ?

Méthodologie

Le benchmark est un sous-ensemble de 116 questions de LongMemEval, couvrant six catégories de mémoire long-terme (knowledge-update, multi-session, single-session-assistant/preference/user, temporal-reasoning). Le corpus est prétraité par Chronos pour extraire des événements temporels normalisés en parallèle des tours bruts.

Le plan factoriel croise quatre dimensions : retriever (grep / vector), harness (Chronos custom, Claude Code, Codex CLI, Gemini CLI), mode de livraison (inline / programmatic file-based), backbone (Claude Opus 4.6, Claude Haiku 4.5, GPT-5.4, Gemini 3.1 Pro, Gemini 3.1 Flash-Lite). L'expérience 2 ajoute un balayage du nombre de sessions distractrices (s5, s10, s20, s30, full).

L'évaluation s'appuie sur un grader GPT-4o produisant un jugement binaire conditionné par la catégorie. Tous les hyperparamètres du grader sont gelés entre conditions.

Le protocole présente trois limites méthodologiques notables. Premièrement, un grader unique pour toutes les conditions ne neutralise pas un biais d'auto-préférence éventuel envers les sorties du même fournisseur. Deuxièmement, l'échantillonnage des distractrices est redessiné à chaque palier de session, ce que les auteurs reconnaissent : les courbes de scaling ne mesurent donc pas une loi monotone mais un tirage stochastique. Troisièmement, la ligne Codex vector est explicitement incomplète sur les paliers intermédiaires, ce qui empêche toute conclusion vendor-complète.

Résultats principaux

En mode inline, grep dépasse vector pour les dix paires harness-modèle de l'expérience 1. L'écart le plus large concerne Chronos avec Gemini 3.1 Flash-Lite (86,2 % contre 62,9 %), le plus faible Claude Code avec Opus 4.6 (76,7 % contre 75,0 %).

Le passage en livraison programmatique inverse partiellement la hiérarchie : vector dépasse grep sur cinq paires sur dix. Le cas le plus instructif est Codex GPT-5.4 qui chute de 93,1 % (grep inline) à 55,2 % (grep programmatique), pendant que vector programmatique tient à 67,2 %. L'hypothèse retenue est que le cycle lire-intégrer-réessayer ajoute une charge compositionnelle que certaines piles n'absorbent pas de façon fiable.

L'effet du harness rivalise avec celui du retriever : Opus 4.6 atteint 93,1 % sous Chronos contre 76,7 % sous Claude Code, soit un delta du même ordre que le swap grep↔vector dans un harness fixe.

L'expérience 2 montre que l'ordre grep/vector n'est pas préservé lorsque le bruit augmente, et qu'il dépend du harness et du backbone. Claude Code favorise grep pour Opus et Haiku à tous les paliers, Gemini CLI favorise vector pour Gemini 3.1 Pro à tous les paliers, et Chronos présente des croisements dépendant du nombre de sessions. La courbe globale est plate plutôt que monotone, contredisant l'intuition d'un effondrement lexical avec la taille du corpus.

Discussion et limites

L'interprétation la plus défendable du papier n'est pas « grep bat vector », mais « retrieval × harness × delivery » forme un système indissociable. Cette lecture est cohérente avec les données : la même paire retrieval-modèle bouge de plus de quinze points selon le harness.

L'avantage de grep sur LongMemEval reste cependant lié à la nature du benchmark. Les réponses sont souvent ancrées sur des empans verbatim (dates, préférences explicites, faits utilisateur). Cette structure favorise mécaniquement le matching exact. Sur des corpus où la preuve est paraphrasée (synthèse scientifique, code, documents visuels), la conclusion ne tient pas, et les auteurs l'admettent dans la section Limitations.

Plusieurs faiblesses limitent la portée des claims. La taille de l'échantillon (116 questions) reste modeste, surtout fragmentée en six catégories. L'absence d'intervalles de confiance ou de tests de significativité rend incertain le statut des écarts inférieurs à 5 points. Les modèles cités utilisent des versions futures (Opus 4.6, Haiku 4.5, GPT-5.4, Gemini 3.1) dont la nature exacte n'est pas documentée, ce qui complique la reproduction.

Le harness Chronos est référencé par auto-citation vers un autre preprint des mêmes auteurs, sans description suffisante du dynamic prompting catégorie-conditionné. Cette dépendance peut introduire un biais systématique en faveur de Chronos, dont les scores plafonnent effectivement plus haut que ceux des CLI provider sur la majorité des configurations.

Reproductibilité

LongMemEval est public et le sous-ensemble de 116 questions est documenté. Les implémentations de grep et vector sont décrites au niveau du principe mais sans code ni paramètres exposés (modèle d'embedding, taille de chunk, paramètres du reranker, top-k). Le harness Chronos n'est pas open source dans l'article. Les wrappers bash invoqués par les CLI ne sont pas publiés. Les prompts catégorie-conditionnés ne sont pas montrés. En l'état, une réplication exacte est impossible ; seule une réimplémentation approchée l'est.

Impact et applications

Le résultat opérationnel est utile pour les ingénieurs de coding agents : sur des corpus textuels stables où la preuve est littérale, un grep bien intégré dans le harness suffit souvent, à condition que la sortie soit inline. Cela rejoint l'observation pratique des derniers coding agents en production qui exposent grep comme outil natif plutôt qu'un index vectoriel.

L'apport secondaire est méthodologique. Les auteurs montrent que comparer BM25 vs ANN sur des pipelines statiques sous-estime la variance introduite par le scaffolding agentique. Toute évaluation future de retriever pour agents devrait donc rapporter conjointement le harness et le mode de livraison.

Positionnement dans la littérature

Le papier s'inscrit dans une vague récente de travaux qui reconfigurent les stratégies de recherche dans les agents modernes : le shell comme alternative au RAG vectoriel, la pression de contexte (Liu et al. 2024, lost-in-the-middle), MemGPT (Packer et al. 2023) pour la livraison fichier. Il dialogue aussi avec SWE-agent (Yang et al. 2024) sur l'interface agent-ordinateur.

Sa contribution distincte est le plan factoriel explicite croisant retriever, harness et delivery. À notre connaissance, aucune étude antérieure n'avait isolé ces trois axes simultanément sur un benchmark de mémoire long-terme. La portée reste cependant restreinte au domaine conversationnel, et la dépendance au harness propriétaire Chronos affaiblit la généralisation vendor-neutre.
