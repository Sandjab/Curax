Adapting the Interface, Not the Model: Runtime Harness Adaptation for Deterministic LLM Agents

Lecture Critique d'Article

Objectif et contexte

Les agents LLM échouent fréquemment sur des tâches déterministes non par défaut de raisonnement mais par mésalignement à l'interface modèle-environnement : observations mal organisées, contrats d'outils mal compris, actions inexécutables, feedback non traduit en signal de récupération, trajectoires qui dégénèrent en répétition. Le papier cite l'écart frappant entre Qwen3.5-4B qui obtient 74,0% sur HMMT Feb (raisonnement mathématique) et seulement 43,1% sur ALFWorld pour ancrer le diagnostic.

La thèse centrale renverse l'orthodoxie : plutôt qu'absorber la structure du domaine dans les poids via SFT, RL ou distillation, on évolue un runtime harness qui sert d'interface stable et réutilisable entre un modèle gelé et un environnement réglé. La question de recherche est explicite : les trajectoires d'entraînement peuvent-elles servir à faire évoluer une interface runtime structurée qui améliore des agents gelés sur des tâches inédites et de nouveaux backbones ?

Méthodologie

LIFE-HARNESS structure l'adaptation runtime en quatre couches alignées sur le cycle de vie de l'interaction :

  • Environment Contract Layer : calibre les descriptions d'outils et les contraintes avant l'interaction.
  • Procedural Skill Layer : maintient une bibliothèque de skills distillés des trajectoires, récupérés par BM25.
  • Action Realization Layer : valide et canonise les actions avant exécution, bloque celles qui échoueraient déterministiquement.
  • Trajectory Regulation Layer : surveille les patterns dégénératifs (répétition, stagnation, épuisement du budget) et déclenche la récupération.

L'évolution du harness est pilotée par un coding agent (Codex) qui lit les traces d'un Qwen3-4B-Instruct gelé sur les tâches d'entraînement, mine les patterns d'échec récurrents et propose des mises à jour ciblées sur la couche responsable. Une annotation préalable des trajectoires échouées selon un protocole prioritaire (action realization → contract → trajectoire → raisonnement résiduel) fonde le design en évitant que les symptômes tardifs masquent les défaillances d'interface précoces.

L'évaluation couvre sept environnements (Airline, Retail, Telecom, ALFWorld, WebShop, OS, DBBench) et 18 backbones (familles Qwen, Llama, xLAM, dont des modèles instruct, reasoning et agent-spécialisés). Température 0,0, métriques pass@1 sur AgentBench et pass@1 / pass@3 / pass^3 sur τ-bench et τ²-bench. Le harness évolué uniquement sur Qwen3-4B-Instruct est gelé puis réutilisé tel quel sur les 17 autres modèles — un protocole strict pour tester la généralisation cross-model.

Résultats principaux

116 configurations modèle-environnement sur 126 sont améliorées, soit 92%, avec un gain relatif moyen de 88,5%. Les gains relatifs vont de 10% (Retail pass@1) à 84% (ALFWorld). Sur ALFWorld le passage est spectaculaire : 41,1% → 75,7% en moyenne.

L'ablation leave-one-layer-out confirme que les quatre couches sont indispensables mais avec une hétérogénéité forte entre environnements : retirer la Trajectory Regulation Layer fait chuter ALFWorld de 86,5%, retirer l'Action Realization Layer coûte 61,7% sur Airline et 59,6% sur OS. Aucune couche n'est universellement dominante, ce qui valide a posteriori le diagnostic des failures hétérogènes.

La comparaison avec l'entraînement spécialisé est particulièrement parlante : Qwen2.5-32B + LIFE-HARNESS dépasse xLAM-2-32B (sa dérivée tool-use trained sur τ-bench) de 7,5 points en in-domain. Le harness reste utile après entraînement (+6,8 à +28,9 points sur xLAM). Et l'entraînement spécialisé dégrade la généralisation OOD : xLAM sous-performe sa base Qwen2.5 sur τ²-bench et AgentBench, tandis que le harness apporte des gains positifs dans les deux régimes.

Face au prompt evolving (GEPA, OPRO), LIFE-HARNESS ajoute 120% de gain relatif moyen — un écart attendu puisque le prompt n'agit que sur l'entrée initiale alors que le harness intervient à chaque étape du cycle.

Discussion et limites

Les auteurs reconnaissent explicitement la limite principale : la méthode cible les environnements déterministes et réglés. Étendre l'approche à des tâches ouvertes où les outils, ressources et critères de succès varient par tâche reste un défi non résolu. Les travaux antérieurs cités (Meta-Harness, AHE) partagent cette restriction au coding ou au texte.

Quelques angles morts méritent discussion. D'abord, l'évolution du harness consomme un coding agent (Codex) et de nombreuses exécutions sur les tâches d'entraînement — le coût computationnel de cette évolution n'est jamais chiffré et comparé à celui d'un SFT équivalent. Deuxièmement, le harness final pour chaque environnement (voir Tables 3-5) est massif et hautement spécifique : pour Airline, on liste des dizaines de règles dures sur le tool booking. Cela soulève une question que les auteurs n'adressent pas : le harness encode-t-il de la structure environnementale réutilisable ou re-implémente-t-il en dur des règles métier qui auraient pu vivre dans le code du benchmark lui-même ? La frontière entre adaptation d'interface et patch task-specific est floue.

Troisièmement, le transfert cross-model est élégant mais asymétrique : la Figure 5 montre que certains modèles (xLAM-2-3b sur ALFWorld, Llama-3.3-70B sur OS) gagnent très peu voire perdent. La généralisation à 92% des settings masque une variance importante. Quatrièmement, le protocole d'annotation des failures est lui-même délégué à Codex, ce qui introduit une boucle où le système diagnostique ses propres bugs avec un agent de la même famille — un risque circulaire de confirmation que les auteurs ne discutent pas.

Enfin, l'évaluation se fait avec DeepSeek-V4-Flash comme user LLM pour τ-bench et τ²-bench. Le harness évolué pourrait surajuster aux patterns de ce user simulé spécifique.

Reproductibilité

Le code est annoncé comme disponible sur GitHub (lien dans le papier). Les Appendices fournissent le protocole d'annotation, le template de prompt complet pour l'évolution du harness via Codex, et un inventaire détaillé des composants par couche pour chaque environnement (Tables 3-5). Les paramètres d'évaluation (température, max tokens, max steps) sont tabulés. Les Tables 7 donnent les scores complets par modèle et benchmark.

Points moins clairs : le nombre exact d'itérations d'évolution par tâche (la Figure 6 montre 5 itérations mais sans préciser le critère d'arrêt), le budget Codex consommé, et la version exacte des modèles propriétaires utilisés (DeepSeek-V4-Flash). La nature semi-manuelle du processus d'évolution (Codex assisté) rend une réplication identique difficile, même si la généralisation cross-model atténue cette préoccupation.

Impact et applications

L'apport conceptuel est net : formaliser le harness comme objet d'adaptation first-class, distinct du prompt et des poids, avec une décomposition lifecycle qui localise les interventions. C'est une contribution architecturale qui s'inscrit dans la lignée récente Meta-Harness, AHE, HARBOR mais qui pousse plus loin la structuration en couches sémantiques plutôt qu'en code libre.

Pour la pratique en production, le résultat le plus actionnable est la démonstration qu'on peut atteindre ou dépasser un modèle fine-tuné tool-use spécialisé sans toucher aux poids, avec l'avantage d'un asset (le harness) qui se transfère à de nouveaux modèles. Cela transforme l'économie du déploiement d'agents : amortir le coût d'ingénierie d'interface sur plusieurs générations de backbones devient une stratégie viable.

L'effet de bord intéressant — l'entraînement spécialisé qui détériore l'OOD — est un signal pour la communauté agentique : sur-spécialiser un modèle sur τ-bench peut sacrifier ses capacités sur τ²-bench.

Positionnement dans la littérature

Le papier se positionne explicitement contre la dominance du paradigme model-centric (SFT, RL, distillation, post-training) et s'aligne avec la vague récente d'optimisation de scaffold autour de modèles gelés. La distinction revendiquée vis-à-vis de Meta-Harness et AHE est la structuration en quatre couches lifecycle dérivées d'un diagnostic de failures, plutôt qu'une recherche de code harness libre. Vis-à-vis du prompt optimization (OPRO, GEPA, ProTeGi, TextGrad), la séparation est claire : le prompt n'agit qu'en entrée, le harness médie chaque étape.

Le rapprochement avec les approches "code-as-harness" (cf. Reversa, l'ingénierie inverse de doc legacy) et avec les contrats agentiques formels suggère une convergence : la prochaine frontière sera probablement la spécification déclarative de contrats runtime, dont LIFE-HARNESS est une instance procédurale.
