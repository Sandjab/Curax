Code as Agent Harness: Toward Executable, Verifiable, and Stateful Agent Systems

Vulgarisation

Quand le code devient le squelette des agents IA

Un agent IA moderne qui résout un bug dans un dépôt GitHub ne se contente pas de générer du texte. Il lit des fichiers, exécute des tests, observe des traces d'erreur, modifie du code, relance la suite de tests, recommence si nécessaire. Entre le modèle de langage et cette chorégraphie d'actions, il existe une couche logicielle souvent invisible mais déterminante : le harness. C'est elle qui transforme un modèle stateless en un agent capable de mener une tâche complexe sur plusieurs heures.

L'équipe de l'Université de l'Illinois Urbana-Champaign, en collaboration avec Meta et Stanford, vient de publier un survey de plus de 60 pages qui propose une thèse forte : le code n'est plus seulement ce que les agents produisent, c'est aussi le matériau dont est faite leur infrastructure cognitive. Cette inversion de perspective, baptisée code as agent harness, change la façon dont on doit concevoir les systèmes agentiques.

Le problème : pourquoi les LLM seuls ne suffisent pas

Un modèle de langage isolé reste une fonction stateless. Vous lui donnez du texte, il vous rend du texte. Pour qu'il devienne un agent qui agit sur le monde, il faut lui adjoindre une infrastructure : outils, APIs, sandbox d'exécution, mémoire persistante, validateurs, contrôles de permissions, boucles d'exécution, canaux de feedback. C'est ce que la communauté appelle le harness, terme emprunté aux harnais de chevaux ou aux structures de test logiciel.

Le constat des auteurs est limpide : le goulot d'étranglement de l'autonomie n'est pas seulement la capacité de raisonnement du modèle, mais la fiabilité du système qui connecte ses sorties à des actions de longue durée et à des états persistants. Un GPT-5 brillant mais sans harness solide produira moins de valeur qu'un modèle moyen équipé d'une infrastructure bien pensée.

Le langage naturel, par défaut, ne suffit pas comme interface entre le modèle et son environnement. Il est ambigu, non vérifiable, non persistant. Quand un agent dit « je vais ouvrir ce fichier et corriger le bug », rien dans cette phrase ne garantit que l'action sera effectuée correctement. Les auteurs défendent une réponse précise à cette limitation : le code.

La méthode vulgarisée : trois propriétés qui changent tout

Pourquoi le code, et pas autre chose ? Les auteurs identifient trois propriétés qui en font un substrat naturel pour les agents.

Le code est exécutable. Une intention exprimée en programme produit un résultat formellement vérifiable. Le harness peut donc vérifier ce que le modèle a réellement voulu faire, plutôt que de deviner.

Le code est inspectable. Les traces d'exécution, les variables intermédiaires, les logs, les sorties de tests forment des objets structurés que le harness peut lire, stocker, comparer. Quand une action échoue, on peut diagnostiquer pourquoi.

Le code est stateful. Un dépôt Git, un workspace de fichiers, une base de données SQLite locale conservent l'état d'avancement entre deux pas de l'agent. L'historique d'interaction n'est pas perdu d'une étape à l'autre.

Pensez à un chef cuisinier qui transmet une recette à son équipe. Le faire à l'oral marche pour un plat simple mais devient catastrophique pour un menu de vingt couverts en service. Écrire la recette sur papier, avec des étapes numérotées, des températures précises, des points de contrôle visuels, transforme un échange éphémère en référence partagée, vérifiable, modifiable. Le code joue ce rôle pour les agents IA.

Trois couches d'organisation

Le survey structure le domaine en trois couches imbriquées.

La première, l'interface du harness, décrit comment le code connecte l'agent à trois fonctions fondamentales. Le code pour raisonner : au lieu de calculer mentalement, l'agent écrit un petit programme Python et laisse l'interpréteur faire le calcul. C'est le principe du Program-of-Thoughts, qui surpasse largement le chain-of-thought textuel sur les tâches arithmétiques ou logiques. Le code pour agir : un robot qui doit saisir un objet reçoit une politique de contrôle écrite en code, pas une description en langage naturel. Le code pour modéliser l'environnement : un dépôt Git, ses tests, ses logs deviennent la représentation explicite de l'état du monde dans lequel l'agent opère.

La deuxième couche regroupe les mécanismes du harness. C'est ici que l'agent gagne sa fiabilité sur le long terme. Cinq sous-systèmes coopèrent. La planification organise les tâches longues en étapes coordonnées, parfois sauvegardées dans un fichier PLAN.md qui survit aux resets de contexte. La mémoire gère l'état mutable, depuis le scratchpad immédiat jusqu'aux expériences accumulées sur plusieurs sessions. L'usage d'outils connecte l'agent aux APIs, terminaux, navigateurs, validateurs. La boucle plan-execute-verify transforme la simple génération en cycle contractuel, où chaque action passe par un sandbox et un contrôle de vérification. Enfin, l'optimisation du harness lui-même, qui consiste à mesurer et améliorer l'infrastructure via des télémétries fines.

La troisième couche s'attaque au passage à l'échelle multi-agents. Quand plusieurs agents collaborent sur le même dépôt, le code partagé devient leur espace de travail commun. Un manager planifie, un coder implémente, un reviewer relit, un tester vérifie. Le défi n'est plus seulement de générer du bon code, mais de maintenir un état cohérent entre des acteurs qui modifient les mêmes fichiers en parallèle.

Résultats clés : ce que cette grille de lecture révèle

Le survey recense plus de 200 systèmes publiés entre 2022 et 2026. Plusieurs résultats consolidés émergent de cette synthèse.

Sur le raisonnement, déléguer le calcul à un programme améliore la fiabilité de manière mesurable. Les systèmes comme PAL, PoT ou MathCoder dépassent les approches purement textuelles sur les benchmarks mathématiques, parce qu'ils séparent la proposition (le modèle décrit la procédure) de l'exécution (l'interpréteur produit le résultat). Plus récent et plus radical, CodeAdapt suggère qu'un LLM généraliste couplé à un harness d'exécution peut surpasser des modèles spécialisés en raisonnement.

Sur l'action, le passage par le code change la nature des erreurs. Un robot qui exécute une politique programmée échoue de façon explicite et inspectable, là où une instruction en langage naturel produit des comportements silencieusement incorrects. Voyager, le système qui apprend à jouer à Minecraft, illustre l'idée d'une bibliothèque de compétences exécutables qui s'enrichit en continu : chaque nouvelle tâche maîtrisée devient une fonction réutilisable.

Sur l'environnement, SWE-bench a imposé un nouveau standard : évaluer un agent sur sa capacité à modifier un vrai dépôt et à faire passer les tests existants. Cette idée a transformé la recherche, parce qu'elle remplace les jugements textuels approximatifs par une vérification binaire et reproductible. Les benchmarks suivants (LiveCodeBench, CRUXEval, AgentBench) prolongent cette logique sur des environnements de plus en plus variés.

Sur la mémoire, un résultat surprenant ressort : la qualité de l'expérience stockée importe davantage que la quantité. Les systèmes qui empilent naïvement leurs trajectoires passées se polluent avec du bruit et propagent des erreurs. Les approches comme MemGovern montrent qu'un filtrage soigneux de ce qu'on garde en mémoire produit de meilleurs résultats qu'une accumulation brute.

Sur l'orchestration multi-agents, les systèmes comme ChatDev, MapCoder ou les harnesses d'Anthropic démontrent que la spécialisation des rôles, combinée à des artefacts partagés (un dépôt commun, un fichier de plan, un blackboard), produit des trajectoires plus robustes que les architectures où un agent unique fait tout.

Implications pratiques : ce que ça change pour les équipes tech

Pour les équipes qui construisent des produits avec des agents, le cadre proposé fournit une grille de diagnostic concrète. Quand un agent échoue, la question n'est pas seulement « quel modèle utiliser ? » mais « quelle couche du harness est défaillante ? ».

Si les actions sont silencieusement incorrectes, c'est l'interface action qui manque de validation. Si l'agent se perd au bout de quelques étapes, c'est la mémoire et la gestion de contexte qui posent problème. Si les corrections ne tiennent pas après réexécution, c'est la boucle plan-execute-verify qui est trop laxiste. Cette décomposition permet d'investir au bon endroit, plutôt que de changer de modèle dans l'espoir vague d'une amélioration.

Le rôle des sandboxes mérite une attention particulière. Les environnements isolés (containers, microVMs) deviennent une brique d'infrastructure aussi importante que la base de données dans une application classique. Ils permettent l'exécution reproductible, l'audit des actions, le rollback en cas d'erreur. Les plateformes émergentes comme OpenHands, ou les SDK d'agents publiés par les grands acteurs, intègrent désormais ces capacités par défaut.

Pour les organisations qui développent des assistants de codage internes, l'idée d'artefacts persistants change la pratique. Un fichier ARCHITECTURE.md, un PLAN.md versionné dans Git, des conventions de tests documentées ne servent pas seulement aux humains : ils deviennent des objets que les agents consultent, mettent à jour et auxquels ils se référent. La documentation cesse d'être un coût pour devenir une infrastructure productive.

Le survey identifie cinq domaines d'application qui mûrissent rapidement : l'assistance au code (Claude Code, Codex, Cursor), l'automatisation GUI/OS (agents qui pilotent des navigateurs ou des systèmes), les agents embarqués (robotique et contrôle physique), la découverte scientifique (pipelines automatisés d'hypothèses et d'expériences), et la personnalisation (agents qui s'adaptent aux préférences utilisateur via des politiques exécutables).

Pour aller plus loin : les questions qui restent

Le survey se termine par une liste de problèmes ouverts qui dessinent l'agenda de recherche des prochaines années.

L'évaluation au-delà du succès final reste un trou béant. Un agent qui résout une tâche après vingt tentatives chaotiques n'est pas équivalent à un agent qui la résout en trois étapes propres, mais les benchmarks actuels les notent pareil. Comment mesurer la qualité de la trajectoire, pas seulement le résultat ?

La vérification sémantique, quand le feedback exécutable manque, est un défi sous-estimé. Les tests unitaires ne couvrent pas tout. Comment un agent peut-il valider qu'il a bien compris l'intention métier d'un changement, et pas seulement qu'il fait passer les tests ? Les vérificateurs LLM-as-judge restent fragiles et biaisés.

L'amélioration sans régression du harness lui-même devient critique à mesure que les systèmes se complexifient. Quand on modifie une partie de l'infrastructure agentique, comment garantir qu'on n'a pas cassé silencieusement des capacités sur d'autres tâches ? La question rappelle les défis du déploiement continu en SRE.

L'état partagé cohérent entre plusieurs agents pose des problèmes proches de ceux des bases de données distribuées : conflits sémantiques, résolution transactionnelle, garanties de consistance. Le code donne des outils (verrous, branches Git, tests d'intégration) mais ne résout pas magiquement la coordination.

La supervision humaine pour les actions critiques reste un sujet sensible. À mesure que les agents gagnent en autonomie, où placer les gates de validation manuelle ? Comment éviter à la fois la paralysie (tout demande approbation) et l'aveuglement (l'humain signe sans regarder) ?

L'extension aux environnements multimodaux, enfin, ouvre un chantier majeur. Le code suppose une représentation textuelle exécutable. Comment intégrer naturellement la perception visuelle, l'audio, les signaux des capteurs dans ce cadre ? Les premiers travaux sur les agents GUI montrent les promesses et les difficultés de cette extension.

La thèse centrale du survey mérite d'être retenue : le code n'est plus seulement la cible de ce que les LLM produisent, il est devenu leur infrastructure cognitive. Cette inversion de perspective rapproche le design d'agents IA de l'ingénierie logicielle classique, avec ses contrats, ses sandboxes, ses tests et ses logs. Pour les équipes qui construisent ces systèmes, le message est clair : investir dans le harness vaut souvent plus que d'attendre le prochain modèle.
