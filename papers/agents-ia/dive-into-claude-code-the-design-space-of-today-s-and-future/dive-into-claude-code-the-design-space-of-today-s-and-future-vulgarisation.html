Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems

Vulgarisation

Quand un agent IA devient un logiciel industriel

Seulement 1,6% du code de Claude Code concerne la logique de décision de l'IA. Les 98,4% restants sont de la plomberie : gestion des permissions, compression du contexte, orchestration des outils, persistance des sessions. Ce ratio, mesuré par une équipe de chercheurs de la MBZUAI qui a épluché le code TypeScript publié par Anthropic, raconte déjà une grande partie de l'histoire.

Les agents de codage autonomes comme Claude Code ne sont pas des LLM avec quelques outils branchés. Ce sont des systèmes complexes où le modèle de langage joue le rôle d'un cerveau qu'il faut encadrer avec précaution. Jiacheng Liu et ses co-auteurs ont entrepris un travail rare : une analyse architecturale complète à partir du code source, doublée d'une comparaison avec OpenClaw, un système open source qui répond aux mêmes questions dans un contexte très différent.

L'enjeu dépasse la simple curiosité technique. Une étude interne d'Anthropic citée dans le papier révèle que 27% des tâches réalisées avec Claude Code n'auraient tout simplement pas été tentées sans lui. Ces agents créent du travail nouveau, pas seulement du travail plus rapide. Comprendre comment ils sont conçus devient alors un sujet stratégique pour toute équipe qui veut les intégrer, les imiter, ou les encadrer.

Le problème : comment encadrer une IA qui agit vraiment

Un assistant comme GitHub Copilot suggère du code. L'utilisateur décide de l'accepter ou non. Le risque est contenu : une mauvaise suggestion produit une mauvaise ligne, qu'on efface.

Claude Code appartient à une autre catégorie. Il exécute des commandes shell, modifie des fichiers, appelle des services externes, écrit dans votre dépôt Git. Il peut enchaîner des dizaines d'actions sans demander confirmation. Cette capacité d'action autonome change complètement la donne architecturale.

Les chercheurs identifient un paradoxe central, formulé par Anthropic elle-même : les agents doivent pouvoir travailler seuls, c'est ce qui les rend utiles, mais les humains doivent garder le contrôle sur la manière dont leurs objectifs sont poursuivis. Comment concilier ces deux exigences ? Comment éviter qu'un modèle qui se trompe ou qui se fait manipuler par une injection de prompt détruise un dépôt entier ?

Les données montrent que la solution naïve ne marche pas. Quand on demande systématiquement à l'utilisateur d'approuver chaque action sensible, il finit par valider 93% des demandes sans vraiment les lire. L'approbation interactive, seule, ne protège personne. Il faut construire des garde-fous qui fonctionnent même quand l'humain est distrait.

La méthode : lire le code pour en extraire la philosophie

Les auteurs ont procédé comme des archéologues du logiciel. Anthropic publie une documentation destinée aux utilisateurs mais pas de description architecturale détaillée. Le code TypeScript, en revanche, est disponible publiquement. L'équipe l'a disséqué fichier par fichier pour reconstituer la carte des décisions de conception.

Leur approche repose sur une idée simple : derrière chaque choix d'implémentation se cachent des valeurs humaines et des questions récurrentes. Plutôt que de lister les composants, ils cherchent les questions que les concepteurs ont dû résoudre : où faire vivre le raisonnement ? Comment structurer la boucle d'itération ? Quelle posture de sécurité adopter par défaut ?

Cette lecture fait émerger cinq valeurs fondatrices qui structurent tout le système. L'autorité de décision humaine maintient l'utilisateur aux commandes. La sécurité protège même quand l'utilisateur est inattentif. L'exécution fiable garantit que l'agent fait ce qu'on lui a vraiment demandé. L'amplification des capacités vise à démultiplier ce qu'un humain peut accomplir. L'adaptabilité contextuelle fait que le système s'ajuste au projet et à l'utilisateur.

De ces valeurs découlent treize principes de conception. Certains sont surprenants. Minimal scaffolding, maximal operational harness : ne pas imposer de cadres de raisonnement au modèle, mais investir dans l'infrastructure opérationnelle. Deny-first : refuser par défaut, escalader à l'humain. Defense in depth : plusieurs couches de sécurité indépendantes, qui rattrapent chacune les échecs des autres.

L'analogie la plus parlante pour saisir l'architecture : un aéroport. Le pilote (le modèle) décide du plan de vol, mais il ne contrôle pas directement le radar, la tour de contrôle, les douanes, ni les barrières de sécurité. Chacun de ces systèmes fonctionne indépendamment. Si l'un tombe en panne, les autres continuent de filtrer.

Résultats : une boucle simple, entourée d'une forteresse

Le cœur de Claude Code tient en une boucle while-true. Le modèle génère une réponse qui peut contenir des demandes d'outils, le harness exécute ces outils, collecte les résultats, et relance le modèle. Rien de plus. Cette simplicité est volontaire : les équipes qui conçoivent des agents investissent souvent dans des graphes d'états explicites, des planificateurs, des machines à états typées. Claude Code fait le pari inverse.

Autour de cette boucle, le système déploie une infrastructure impressionnante. Les auteurs recensent sept couches de sécurité indépendantes qu'une demande d'outil doit traverser. Le pré-filtrage retire les outils complètement interdits avant même que le modèle les voie. Les règles deny-first évaluent chaque requête, avec priorité absolue aux interdictions. Sept modes de permission couvrent un spectre de confiance, du mode plan où tout doit être approuvé jusqu'au bypassPermissions où seules les règles critiques s'appliquent.

Un classificateur ML entre en scène quand le mode auto est activé. Il examine chaque invocation d'outil pour détecter les risques. Un sandbox shell, optionnel, ajoute une isolation au niveau du système d'exploitation. Les hooks PreToolUse permettent aux développeurs d'injecter leur propre logique. Et, point fondamental, les permissions accordées pendant une session ne survivent pas à sa reprise. Chaque session redémarre avec une confiance vierge.

La gestion du contexte suit la même philosophie de couches graduées. Le contexte disponible pour le modèle (200 000 jetons sur les modèles plus anciens, 1 million sur les Claude 4.6) reste une ressource rare. Cinq mécanismes de compression s'exécutent avant chaque appel au modèle. Le budget reduction limite la taille de chaque sortie d'outil. Le snip élague l'historique ancien. Le microcompact compresse de façon fine. Le context collapse projette une vue réduite sur la conversation. L'auto-compact, en dernier recours, demande au modèle de résumer l'ensemble.

Chaque couche intervient à un coût différent et traite une pression différente. L'approche contraste avec les architectures qui tronquent simplement les messages les plus anciens.

L'extensibilité suit le même principe de gradation. Quatre mécanismes distincts permettent d'étendre l'agent, chacun avec un coût en contexte différent. Les hooks coûtent zéro par défaut : ils interceptent des événements du cycle de vie sans rien injecter. Les skills coûtent peu : seule la description figure en permanence, le contenu complet n'arrive qu'à l'invocation. Les plugins ont un coût variable selon ce qu'ils embarquent. Les serveurs MCP (Model Context Protocol) coûtent cher : leurs schémas d'outils pèsent dans le contexte, mais ils donnent accès à des services externes.

La délégation à des sous-agents mérite une attention particulière. Quand Claude Code doit explorer un module complexe, il peut déléguer cette tâche à un sous-agent qui opère dans un contexte isolé. Ce sous-agent ne renvoie au parent qu'un résumé, jamais sa conversation complète. Les chercheurs soulignent un chiffre parlant : les équipes d'agents consomment environ sept fois plus de jetons qu'une session standard en mode plan. L'isolation a un coût, mais elle empêche l'explosion combinatoire des contextes.

La persistance des sessions utilise un format JSONL en mode ajout quasi-exclusif. Chaque événement est lisible, versionnable avec Git, reconstructible sans outillage spécialisé. Le choix privilégie l'auditabilité et la simplicité sur la puissance de requête.

Comparaison avec OpenClaw : mêmes questions, autres réponses

Pour mettre en perspective les choix de Claude Code, les auteurs les comparent à OpenClaw, un système open source qui joue dans une catégorie différente. OpenClaw est une passerelle persistante qui connecte une vingtaine de plateformes de messagerie (WhatsApp, Telegram, Slack, Signal) à un runtime d'agent embarqué. Le système tourne en tant que démon sur un port local.

Les deux systèmes répondent aux mêmes questions récurrentes mais aboutissent à des architectures opposées. Claude Code évalue chaque action individuellement. OpenClaw place le contrôle au périmètre du gateway : codes d'appairage, listes d'autorisation des expéditeurs, authentification du gateway. La différence reflète un choix sur l'emplacement de la frontière de confiance.

Claude Code utilise une boucle d'agent unique comme centre du système. OpenClaw embarque son runtime dans un plan de contrôle plus large, sérialise les appels par file d'attente par session, et gère des événements qui traversent plusieurs canaux. Pour les extensions, Claude Code propose quatre mécanismes gradués ; OpenClaw utilise un système de plugins manifeste-first avec douze types de capacités et un registre central.

Détail intéressant : les deux systèmes peuvent se composer. OpenClaw sait intégrer Claude Code, OpenAI Codex et Gemini CLI comme harnais de codage externes via son protocole ACP. Les architectures ne s'excluent pas, elles s'empilent.

Implications pratiques : ce que ça change pour les équipes tech

Trois leçons émergent de cette analyse pour qui veut construire, adopter ou gouverner ces systèmes.

Première leçon : la posture de sécurité par défaut compte plus que tout le reste. Le principe deny-first escalader-à-l'humain, combiné à une défense en profondeur, définit ce qu'il est possible ou non de faire avec l'agent. Les équipes qui déploient des agents en interne devraient poser cette question avant toutes les autres. Que se passe-t-il quand le modèle se trompe ? Quand un prompt adverse arrive via un fichier lu depuis un dépôt ? Les couches de protection doivent fonctionner indépendamment les unes des autres, sinon elles tombent ensemble.

Deuxième leçon : le contexte est la vraie ressource rare. Les équipes qui ajoutent sans discernement des instructions, des outils MCP, des règles dans un CLAUDE.md, dégradent la performance de leur agent sans s'en rendre compte. L'ordre graduel du coût contextuel (hooks < skills < plugins < MCP) donne un cadre de décision : préférer le mécanisme le moins cher qui résout le problème.

Troisième leçon : la transparence des fichiers l'emporte souvent sur les bases de données sophistiquées. Claude Code stocke sa mémoire et ses règles dans des fichiers Markdown versionnables. L'utilisateur peut lire, éditer, supprimer ce que l'agent voit. Les systèmes à base d'embeddings et de bases vectorielles offrent plus de flexibilité, mais rendent invisible ce qui influence les décisions du modèle. Pour du code critique, savoir ce que l'agent a lu compte plus que la pertinence d'une recherche sémantique.

Les chiffres longitudinaux cités par les auteurs ajoutent une dimension comportementale. Les taux d'auto-approbation passent d'environ 20% chez les utilisateurs ayant moins de 50 sessions à plus de 40% au-delà de 750 sessions. L'autonomie se construit dans la durée, entre le modèle, l'utilisateur et le produit. Les architectures doivent anticiper cette trajectoire de confiance, pas seulement un état fixe.

Pour aller plus loin : six directions ouvertes

Les auteurs identifient six questions non résolues qui structureront la prochaine génération d'agents.

Le fossé entre observabilité et évaluation reste béant. On sait enregistrer tout ce qu'un agent fait, mais on ne sait pas évaluer automatiquement si ce qu'il a fait est bon. La littérature récente pointe un biais connu : les modèles évaluateurs tendent à féliciter leurs propres productions, même médiocres.

La persistance entre sessions pose un dilemme non résolu. Faut-il qu'un agent se souvienne de ses interactions précédentes ? Si oui, comment éviter que des décisions périmées contaminent les nouvelles sessions ? Claude Code tranche aujourd'hui en faveur de l'oubli explicite, au prix d'une friction utilisateur.

Les frontières du harness évoluent. Où s'arrête le code déterministe, où commence la logique confiée au modèle ? Le ratio 98,4/1,6 pourrait changer dans les deux sens selon l'amélioration des modèles.

La mise à l'échelle de l'horizon temporel intrigue. Les agents tiennent quelques heures de travail cohérent. Comment les faire tenir plusieurs jours, plusieurs semaines, sans dériver ?

La gouvernance reste embryonnaire. Qui est responsable quand un agent commet une erreur coûteuse ? Les hiérarchies de principaux (Anthropic, opérateurs, utilisateurs) formalisent l'autorité, mais la jurisprudence reste à construire.

Dernière question, la plus provocatrice : les agents préservent-ils la capacité humaine à long terme ? Une étude indépendante citée par les auteurs montre que les développeurs assistés par IA obtiennent 17% de score en moins aux tests de compréhension. Claude Code amplifie les capacités à court terme des programmeurs. Rien, dans son architecture, ne soutient explicitement l'apprentissage à long terme, la compréhension profonde, ou la cohérence durable d'une base de code. Cette absence n'est pas un bug, c'est un choix de conception, et elle devrait peser dans l'évaluation des agents qui arriveront ensuite.
