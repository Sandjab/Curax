Effective Strategies for Asynchronous Software Engineering Agents

Vulgarisation

1. Quand les agents IA se marchent sur les pieds

Un agent IA résout un bug sur GitHub en quelques minutes. Deux agents travaillant en parallèle sur le même dépôt ? Ils produisent du code incompatible, écrasent mutuellement leurs modifications, et le résultat final ne compile même pas. Ce paradoxe — des agents individuellement compétents mais collectivement dysfonctionnels — est le point de départ d'une étude publiée en mars 2026 par Jiayi Geng et Graham Neubig, chercheurs à Carnegie Mellon University.

Leur article s'attaque à une question concrète : comment faire collaborer plusieurs agents logiciels sur un même projet, en parallèle, sans que le résultat soit un désastre d'intégration ? La réponse qu'ils proposent ne vient pas d'une percée en intelligence artificielle. Elle vient du génie logiciel humain, et plus précisément des outils que les développeurs utilisent depuis des décennies pour travailler ensemble : Git, les branches, les merges, les tests automatisés.

2. Le mur du passage à l'échelle

Les agents IA de développement logiciel ont fait des progrès rapides. Corriger un ticket GitHub isolé, écrire une fonction à partir d'une spécification, générer des tests unitaires — ces tâches sont désormais à leur portée. Mais les projets réels ne sont pas des collections de tâches indépendantes. Implémenter une bibliothèque Python complète ou reproduire les résultats d'un article scientifique exige de coordonner des dizaines de sous-tâches interdépendantes, sur des fichiers partagés, pendant des heures.

La solution intuitive : mettre plusieurs agents en parallèle. Un agent s'occupe du module de parsing, un autre du système de cache, un troisième des tests d'intégration. En théorie, le travail avance trois fois plus vite. En pratique, c'est la catastrophe.

Prenez deux agents qui travaillent simultanément sur le même projet. Le premier renomme une fonction process_data en transform_input. Le second, qui ne voit pas ce changement, écrit du nouveau code qui appelle process_data. Chaque agent a produit du code correct de son point de vue. Mais une fois les deux contributions fusionnées, le programme plante. Ce type de conflit n'est pas un cas limite — c'est le mode de défaillance dominant des systèmes multi-agents sur du code partagé.

Les approches existantes tentent de résoudre le problème par la communication. Des agents se répartissent des rôles (architecte, développeur, testeur), échangent des messages en langage naturel, suivent des « procédures opérationnelles standard ». Mais la coordination linguistique ne suffit pas. Dire à un agent « ne touche pas au fichier X » ne garantit pas qu'il respecte cette consigne sur une trajectoire de 100 itérations. Les conflits finissent par émerger, et on ne les découvre qu'au moment de l'intégration, quand il est trop tard pour un correctif simple.

3. Copier les développeurs humains, pas les réinventer

Les développeurs humains rencontrent exactement les mêmes problèmes depuis quarante ans. Deux personnes qui modifient le même fichier en même temps, des dépendances cassées par un refactoring en amont, des changements incompatibles découverts trop tard — tout cela fait partie du quotidien de n'importe quelle équipe logicielle. Et les humains ont construit une infrastructure robuste pour gérer ces situations : le contrôle de version, les branches isolées, les merges explicites, les suites de tests automatisés, les graphes de dépendances.

L'idée de Geng et Neubig tient en une phrase : au lieu d'inventer de nouveaux mécanismes de coordination pour les agents IA, utilisons ceux que le génie logiciel a déjà éprouvés. Leur système, baptisé CAID (Centralized Asynchronous Isolated Delegation), repose sur trois piliers empruntés directement aux pratiques humaines.

Le premier : un manager central qui analyse le projet, construit un graphe de dépendances, et découpe le travail en sous-tâches. Ce manager ne code pas lui-même — il distribue le travail aux agents « ingénieurs » en respectant l'ordre des dépendances. Si le module B dépend du module A, le module A est assigné en priorité. Les fichiers fortement couplés sont regroupés et confiés au même agent pour éviter les conflits croisés.

Le deuxième : l'isolation physique des espaces de travail. Chaque agent ingénieur reçoit son propre git worktree, une copie complète du dépôt sur une branche séparée. Les modifications de l'agent 1 n'affectent pas l'espace de travail de l'agent 2, et inversement. Pas de consignes verbales du type « ne touche pas à ce fichier » — l'isolation est matérielle, garantie par Git.

Le troisième : l'intégration par merge et tests. Quand un agent termine sa tâche, il fait un commit sur sa branche. Le manager fusionne cette branche dans la branche principale via git merge. Si un conflit apparaît, l'agent responsable doit le résoudre lui-même : il récupère la dernière version de la branche principale, corrige les incompatibilités, et soumet à nouveau. Les tests automatisés valident chaque intégration.

L'analogie est directe : CAID reproduit le workflow d'une équipe de développeurs qui utilisent GitHub avec des pull requests, des revues de code et une intégration continue. La différence, c'est que les « développeurs » sont des modèles de langage.

Une boucle asynchrone, pas un pipeline séquentiel

Le fonctionnement concret ressemble à une boucle événementielle. Le manager lance plusieurs agents en parallèle, chacun dans son worktree. Dès qu'un agent termine et soumet son commit, le manager fusionne le résultat, met à jour l'état des dépendances, et assigne la prochaine tâche à cet agent libéré. Les agents qui attendent des dépendances non résolues restent inactifs. La communication entre manager et ingénieurs passe par des spécifications JSON structurées — pas par du dialogue en langage naturel, ce qui élimine une source majeure de malentendus.

Chaque agent est aussi responsable de vérifier son propre travail avant de soumettre. Il exécute les tests pertinents dans son worktree, corrige les erreurs, et ne fait son commit que quand les tests passent. Le manager ne fait pas de revue de code détaillée à chaque étape — il surveille l'avancement global et gère la répartition des tâches.

4. Des gains mesurables, pas anecdotiques

Les chercheurs ont évalué CAID sur deux benchmarks exigeants. Le premier, Commit0, demande aux agents d'implémenter des bibliothèques Python entières à partir d'un squelette de code et d'une suite de tests unitaires : TinyDB, Jinja, Minitorch, entre autres. Le second, PaperBench, demande de reproduire les contributions principales d'articles scientifiques publiés en conférence — un exercice qui mêle implémentation, configuration expérimentale et vérification de résultats.

Sur PaperBench, CAID avec deux agents ingénieurs améliore le score de 26,7 points de pourcentage par rapport à un agent unique (en valeur absolue, avec le modèle MiniMax 2.5 — passant de 10,4 % à 36,7 %). Avec Claude Sonnet 4.5, le gain est de 6,1 points (de 57,2 % à 63,3 %). Sur Commit0, l'amélioration atteint 14,7 points avec MiniMax 2.5 (de 42,3 % à 57,0 %) et 6,0 points avec Claude Sonnet 4.5 (de 53,1 % à 59,1 %). Ces résultats sont cohérents sur trois modèles de langage différents — Claude Sonnet 4.5, GLM 4.7 et MiniMax 2.5 — ce qui confirme que le gain provient de l'architecture de coordination, pas du modèle sous-jacent.

Un résultat frappant : doubler le budget d'itérations d'un agent unique (de 100 à 200) n'améliore quasiment pas les résultats. Dans certains cas, les performances baissent même. L'agent tourne en rond, défait des modifications précédentes, ou s'enfonce dans des impasses. CAID, avec un budget d'itérations inférieur par agent, obtient des gains bien supérieurs. Le problème des tâches longues n'est pas un manque de temps de calcul — c'est un problème de coordination.

Autre constat : la stratégie « essayer d'abord avec un seul agent, puis basculer en multi-agents si ça échoue » gaspille du temps et de l'argent. Sur PaperBench avec Claude 4.5, cette approche séquentielle atteint 66,8 % — à peine mieux que les 63,3 % du multi-agents direct — mais le temps d'exécution double et le coût explose. Mieux vaut démarrer directement en mode multi-agents.

L'isolation physique fait la différence

Les chercheurs ont comparé l'isolation par worktree (séparation physique via Git) à une « isolation souple » où tous les agents partagent le même espace de travail, avec des consignes textuelles pour éviter les conflits. Sur Commit0, l'isolation souple améliore légèrement le score par rapport à un agent unique (56,1 % contre 53,1 %), mais l'isolation par worktree fait mieux (59,1 %). Sur PaperBench, l'isolation souple fait pire qu'un agent unique (55,5 % contre 57,2 %), alors que les worktrees atteignent 63,3 %. Quand la structure du projet est ambiguë et que le manager doit inférer le plan d'implémentation, partager un espace de travail amplifie les erreurs de coordination au lieu de les atténuer.

Trop d'agents tuent la performance

Augmenter le nombre d'agents ne donne pas des gains linéaires. Sur Commit0, passer de 2 à 4 ingénieurs améliore les résultats, mais passer à 8 les dégrade. Avec 8 agents, le manager commence à assigner des fonctions différentes du même fichier à des agents distincts. Les modifications se chevauchent au niveau fichier, les conflits de merge se multiplient, et la productivité locale de chaque agent ne se traduit plus en progrès global. Sur PaperBench, au-delà de 2 agents, les gains stagnent tandis que le coût grimpe. Le nombre optimal d'agents dépend de la modularité réelle du projet et de la capacité du manager à découper le travail proprement.

5. Ce que ça change pour la pratique

Le message principal de cet article dépasse le cadre académique. Pour quiconque construit ou déploie des systèmes multi-agents en entreprise, trois enseignements se dégagent.

D'abord, les outils de coordination existent déjà. Pas besoin d'inventer des protocoles de communication inter-agents sophistiqués quand Git, les branches et les suites de tests font le travail. Cette approche a un avantage immédiat : elle s'intègre dans l'infrastructure existante de n'importe quelle équipe de développement. Les agents utilisent les mêmes outils que les humains, ce qui rend leur travail auditable et compréhensible.

Ensuite, l'isolation physique n'est pas un luxe — c'est une nécessité. Les consignes textuelles (« ne modifie pas ce fichier ») ne tiennent pas sur des trajectoires longues. Les modèles de langage dérivent, oublient des contraintes, font des erreurs. Séparer physiquement les espaces de travail transforme un problème de fiabilité du modèle en un problème d'ingénierie logicielle résolu.

Enfin, le goulot d'étranglement se situe dans la délégation, pas dans l'exécution. L'étude de cas sur Minitorch est révélatrice : deux runs de CAID avec la même configuration produisent des résultats radicalement différents (8,7 % contre 34,3 %) selon les fichiers que le manager choisit d'assigner en priorité. Dans le run réussi, le manager identifie autodiff.py comme une dépendance critique et l'assigne tôt. Dans l'autre, ce fichier n'est jamais assigné, et tout le reste en souffre. La qualité de la décomposition des tâches détermine le plafond de performance du système.

Pour les plateformes d'agents autonomes comme Devin, OpenHands ou Claude Code — qui utilisent déjà des worktrees Git en interne — ces résultats valident une direction architecturale. La coordination multi-agents efficace ne passe pas par plus de dialogue entre agents, mais par plus de structure dans l'orchestration.

6. Les questions qui restent ouvertes

CAID améliore la précision, mais pas le coût. Le système multi-agents consomme systématiquement plus de tokens API et plus de temps d'exécution que l'agent unique, même si le temps mur n'explose pas grâce au parallélisme. L'intégration reste séquentielle (un merge à la fois, validé par les tests), ce qui limite l'accélération réelle. Réduire les cycles de vérification redondants et optimiser l'ordonnancement des merges sont des pistes directes.

La délégation repose aujourd'hui sur du prompt engineering — le manager reçoit des instructions textuelles pour découper le travail. Cette approche fonctionne mais reste fragile. Un manager qui rate une dépendance circulaire ou qui sous-estime la criticité d'un module peut plomber tout le run. Les chercheurs évoquent des politiques de délégation apprises par renforcement, capables de s'adapter dynamiquement à la structure réelle du projet.

La généralisation au-delà du code reste une inconnue. Le génie logiciel offre un terrain idéal pour cette approche : les espaces de travail ont des frontières claires, le contrôle de version est natif, les tests fournissent un signal de validation objectif. Transposer CAID à de la rédaction collaborative, de la planification de recherche ou de la construction d'artefacts multimodaux demandera d'inventer des équivalents à ces mécanismes — des « branches » et des « tests » pour des artefacts non logiciels.

Une question plus fondamentale émerge aussi : jusqu'où peut-on pousser le parallélisme sans que la coordination devienne plus coûteuse que le travail lui-même ? Les résultats montrent déjà que 8 agents font moins bien que 4 sur certaines tâches. La loi des rendements décroissants s'applique, et trouver le point optimal reste un problème ouvert qui dépend de chaque projet.

L'étude de Geng et Neubig montre en tout cas une chose claire : les bonnes pratiques du génie logiciel humain — isolation, intégration explicite, vérification automatisée — sont directement transférables aux systèmes multi-agents. Les agents IA n'ont pas besoin de réinventer la collaboration. Ils ont besoin d'utiliser les outils que les développeurs ont mis des décennies à construire.
