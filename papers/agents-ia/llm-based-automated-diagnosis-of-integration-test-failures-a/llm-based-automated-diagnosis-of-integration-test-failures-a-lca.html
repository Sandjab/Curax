LLM-Based Automated Diagnosis Of Integration Test Failures At Google

Lecture Critique d'Article

Objectif et contexte

Le diagnostic des échecs de tests d'intégration mobilise significativement plus de temps que celui des tests unitaires chez Google : souvent plus d'une heure, parfois plus d'un jour. Une enquête interne (EngSat, 6 059 développeurs) le classe dans le top 5 des plaintes récurrentes. Les tests incriminés produisent une médiane de 16 fichiers de logs et 2 801 lignes, répartis entre le test driver et les composants du système sous test (SUT).

Auto-Diagnose s'attaque à ce goulot d'étranglement en concaténant les logs horodatés de tous les composants, en les soumettant à Gemini 2.5 Flash via un prompt structuré, puis en postant un résumé de cause racine directement comme finding dans Critique, l'outil de code review interne. Le positionnement contextuel (pendant la revue) est revendiqué comme élément différenciant par rapport aux agents de debug post-hoc.

Méthodologie

Le système est décrit avec précision : logs de niveau INFO et supérieurs agrégés, prompt template reproduit intégralement dans l'article (Figure 7), température 0.1, top_p 0.8. Aucun fine-tuning n'est appliqué. Le prompt impose un raisonnement étape par étape avec contraintes négatives explicites contre la spéculation.

L'évaluation combine deux volets. Un volet manuel : 71 échecs réels issus de 39 équipes, jugés par 3 développeurs expérimentés de l'équipe d'infrastructure de test, avec réunion de consensus pour résoudre les désaccords. Un volet production : 224 782 exécutions sur 52 635 tests distincts, avec boutons de feedback "Helpful / Not helpful / Please fix" dans l'interface. Enfin, 11 entretiens qualitatifs auprès d'auteurs et de reviewers ayant laissé un feedback.

Le protocole souffre de plusieurs faiblesses structurelles. Aucune baseline quantitative : pas de comparaison avec des techniques classiques (SBFL, delta debugging) ni avec des approches LLM alternatives sur le même échantillon. Aucun score de concordance inter-juge rapporté sur les 71 cas. Les évaluateurs appartiennent à l'équipe d'infrastructure et peuvent porter un intérêt organisationnel au succès de l'outil.

Résultats principaux

Sur les 71 cas, 64 diagnostics sont jugés corrects, soit 90,14%. Les 7 échecs se décomposent en deux bugs d'infrastructure (logs non sauvegardés lors de crashs), pas en erreurs de raisonnement du modèle — une distinction qui gonfle artificiellement la performance attribuée au LLM.

En production, le temps médian de publication du diagnostic est de 56 secondes (p90 : 346 s), bien en deçà du temps de debug humain. Le taux "Not helpful" atteint 5,8%, sous le seuil opérationnel de 10% imposé par Critique. Le helpfulness-rate (H / H+N) s'établit à 62,96%, soit un écart substantiel avec les 90,14% mesurés manuellement, que les auteurs attribuent au biais de négativité sans le quantifier.

Le classement #14 sur 370 outils en helpfulness (top 3,78%) est présenté comme signal fort d'adoption. La consommation reste économiquement viable : 110 617 tokens d'entrée et 5 962 de sortie en moyenne, sur Gemini 2.5 Flash.

Discussion et limites

Le chiffre phare de 90,14% mérite d'être relativisé. Les évaluateurs décident si une des lignes de log signalées ou la conclusion mentionne la cause racine — critère permissif qui ne distingue pas un diagnostic précis d'une mention fortuite dans les logs cités. La métrique de production (5,8% not-helpful) souffre quant à elle d'un énorme biais de sélection : seuls 517 feedbacks sur 224 782 exécutions (0,23%), ce que les auteurs reconnaissent.

La section "Threats to Validity" est honnête et couvre l'essentiel : spécificité de Gemini 2.5 Flash, variabilité du prompt, qualité variable des logs, contexte Google. Mais l'absence de baseline reste le point aveugle majeur : rien ne prouve qu'un parseur de logs classique ne ferait pas aussi bien sur les cas où la trace d'erreur est explicite.

L'interview P-9, où Auto-Diagnose refuse de conclure faute de logs, illustre un effet secondaire vertueux : environ 20 diagnostics de ce type ont révélé des bugs d'infrastructure. Ce comportement est piloté par les contraintes négatives strictes du prompt, un choix de conception bien documenté.

Reproductibilité

Nulle. L'étude repose intégralement sur l'infrastructure interne Google (Critique, système de logs propriétaire, pub/sub, corpus de tests fermé). Aucun jeu de données, aucun code source, aucun log d'exemple n'est partagé. Seul le prompt template est reproduit (Figure 7), ce qui permet au moins de réutiliser la structure du raisonnement. Les 71 cas évalués manuellement ne sont pas libérés même de façon anonymisée, ce qui aurait pourtant constitué un benchmark précieux pour la communauté.

Impact et applications

L'échelle du déploiement — 52 635 tests, 22 962 auteurs distincts, 91 130 code changes — fait de ce travail l'un des rares retours d'expérience industriels documentés sur l'usage d'un LLM pour le diagnostic en CI/CD. Les enseignements opérationnels sont transférables : latence p50 sous la minute, seuil de tolérance utilisateur à 10% de not-helpful, intégration dans un outil existant plutôt que création d'une nouvelle surface UI.

La remarque de P-3 ("Auto-Diagnose ne devrait pas montrer un résumé, il devrait donner le fix") signale une dynamique d'attentes en spirale : l'adoption d'un outil LLM utile reconfigure immédiatement la référence et pousse vers de la réparation automatique. Les auteurs l'identifient comme piste de travail futur.

Positionnement dans la littérature

La revue de littérature est complète : statistical debugging (Liblit, SOBER), SBFL (Tarantula, Ochiai), delta debugging, failure sketching, approches ML/GNN, et la vague récente d'agents LLM (SWE-Agent, AutoCodeRover, RepairAgent, Agentless). Le positionnement est net : les benchmarks existants (SWE-Bench, HumanEvalFix, DebugBench) ciblent le niveau unitaire ; les tests d'intégration distribués restent sous-étudiés. Cette niche justifie la contribution.

Le rapprochement avec Passerine (Google) et Engineering Agent (Meta) situe le travail dans un petit cluster de publications industrielles récentes sur la réparation agentique en production. Auto-Diagnose se distingue en restant volontairement non-agentique : un seul appel LLM, pas d'outils, pas de boucle — un choix pragmatique qui privilégie latence et coût sur la généralité.
