Proactive Agent Research Environment: Simulating Active Users to Evaluate Proactive Assistants

Vulgarisation

Quand l'assistant IA doit deviner ce que vous voulez

Votre colocataire vous envoie un SMS : « plus de savon ». Trois minutes plus tard, vous ouvrez votre liste de courses à moitié remplie. Un assistant vraiment utile devrait ajouter le savon sans que vous ayez à le demander. C'est exactement ce que les chercheurs appellent un agent proactif : un assistant qui observe vos actions, infère vos objectifs, et propose des interventions au bon moment.

Le problème ? Personne ne sait vraiment évaluer ces agents. Une équipe de l'UC Santa Barbara, d'Apple et de l'Université de Washington vient de proposer une réponse avec PARE (Proactive Agent Research Environment), un cadre de simulation publié en avril 2026. Leurs résultats sont sans appel : même les meilleurs modèles frontières plafonnent à 42 % de taux de réussite sur les tâches proactives. Autrement dit, on est loin du compte.

Le problème : un assistant proactif sans utilisateur, ça ne veut rien dire

La plupart des agents conversationnels actuels fonctionnent en mode réactif : vous demandez, ils exécutent. ChatGPT, Claude, les copilotes de code — tous attendent une instruction explicite avant d'agir. Un agent proactif inverse cette logique. Il observe en continu votre contexte (emails, calendrier, messages, navigation) et décide tout seul quand intervenir.

Le défi méthodologique tient en une phrase : pour tester un agent proactif, il faut un utilisateur qui agit. Sans interaction réelle, impossible de mesurer si l'agent intervient au bon moment, s'il propose des plans pertinents, et si l'ensemble utilisateur-assistant atteint les objectifs visés. Les benchmarks existants comme τ-bench ou ToolSandbox simulent bien des utilisateurs, mais ces simulateurs traitent les applications comme de simples API plates : un appel de fonction, un résultat. Aucune navigation, aucun écran, aucune contrainte d'interface.

Ce raccourci pose un problème sérieux. Sur votre téléphone, envoyer un message ne se résume pas à un appel send_message(). Vous devez ouvrir l'application Messages, chercher la conversation, l'ouvrir, taper le texte, valider l'envoi. Cette séquence d'écrans génère des actions observables, des hésitations, des moments où un assistant peut détecter une intention. Réduire tout cela à un appel d'API unique, c'est gommer précisément le terrain sur lequel un agent proactif devrait briller.

La méthode : asymétrie volontaire entre l'utilisateur et l'assistant

L'idée centrale de PARE est une asymétrie radicale entre les deux acteurs. L'utilisateur simulé navigue à travers des écrans modélisés comme des automates à états finis (FSM). Chaque application possède sa machine à états : l'app Email passe de la boîte de réception à la lecture d'un mail, puis éventuellement à la composition d'une réponse. Pour envoyer un message, l'agent utilisateur doit traverser quatre ou cinq états successifs, exactement comme un humain qui touche son écran.

L'assistant, lui, dispose d'un accès plat à toutes les API de toutes les applications, simultanément. C'est cette asymétrie qui reflète le déploiement réel : un humain est limité à ce que son écran lui permet de faire, alors qu'un assistant logiciel installé sur le même téléphone peut interroger directement les bases de données via des appels backend.

Là où un framework classique permet à l'utilisateur d'envoyer un message en deux appels d'API, PARE l'oblige à enchaîner : ouvrir Messages, chercher la conversation, l'ouvrir, taper, envoyer. Cinq actions, cinq écrans, cinq occasions pour l'assistant d'observer et d'inférer.

L'architecture de l'assistant proactif elle-même se décompose en deux sous-agents distincts. Le premier, Observe, surveille les actions de l'utilisateur et les notifications de l'environnement. Il dispose uniquement d'outils en lecture seule. Quand il détecte une opportunité d'aide, il propose un plan via un message. Si l'utilisateur accepte, le second sous-agent, Execute, prend le relais avec un accès complet aux API pour réaliser la tâche. Cette séparation respecte un principe simple : aucune action irréversible sans consentement explicite.

Le tour de jeu suit une structure de Stackelberg : l'utilisateur agit d'abord, l'assistant observe puis décide. À chaque étape, l'assistant peut choisir entre trois options — attendre et continuer d'observer, lire des informations supplémentaires dans l'environnement, ou proposer une intervention concrète à l'utilisateur.

Un benchmark construit avec un agent générateur

Construire 143 scénarios à la main aurait été irréaliste. L'équipe a donc utilisé un agent de génération basé sur Claude Agent SDK pour produire les scénarios automatiquement. Chaque scénario passe par quatre étapes : génération d'une description narrative, peuplement des données initiales (contacts, emails, événements de calendrier), construction du flux d'événements, puis création des conditions de validation. Chaque étape est exécutée en mode oracle pour vérifier que le scénario fonctionne avant qu'un humain ne valide la cohérence finale.

Le benchmark résultant, PARE-Bench, couvre dix applications : email, messagerie, calendrier, contacts, rappels, notes, shopping, location d'appartements, taxi et système de fichiers. Email représente près de 20 % des scénarios, suivi de shopping (13 %) et messagerie (13 %). Quatre dimensions sont testées : observation du contexte, inférence d'objectif, choix du moment d'intervention, et orchestration multi-applications.

Résultats : les frontières plafonnent à 42 %

Sept modèles ont été évalués comme assistants proactifs : quatre modèles propriétaires (Claude 4.5 Sonnet, GPT-5, Gemini 3 Pro, Gemini 3 Flash) et trois modèles open-weights (Qwen 3 4B, Llama 3.2 3B, Gemma 3 4B). Chacun a été testé sur les 143 scénarios avec quatre exécutions par scénario.

Le tableau d'honneur ressemble à ceci : Gemini 3 Flash et Claude 4.5 Sonnet font la course en tête avec respectivement 42,1 % et 42,0 % de taux de réussite. GPT-5 atteint 37,4 %, Gemini 3 Pro 35,1 %. Du côté des modèles open-weights, Qwen 3 4B Instruct prend la tête avec 18,5 %, Llama 3.2 3B descend à 10 %, et Gemma 3 4B Instruct s'effondre à 3 %.

Plus parlant que les chiffres absolus : la cohérence. Quand on regarde Success@4 (au moins une réussite sur quatre essais) versus Success^4 (réussite systématique sur les quatre), Claude passe de 60,8 % à 18,2 %, soit une chute par 3,3. Llama, lui, dégringole de 23,8 % à 1,4 %, une chute par 17. Les petits modèles ne sont pas seulement moins capables, ils sont aussi imprévisibles.

Une métrique éclaire particulièrement les comportements : le taux de proposition. Claude propose seulement dans 12,8 % des tours mais voit 78,2 % de ses propositions acceptées. GPT-5 propose dans 28,1 % des tours avec 70,2 % d'acceptation — il s'aventure beaucoup plus, parfois à tort. Gemma 3 propose dans 14,2 % des tours mais ne convainc l'utilisateur que dans 17,6 % des cas. Le profil de chaque modèle se dessine : prudent et précis pour Claude, exubérant pour GPT-5, à côté de la plaque pour Gemma.

Le facteur observation

Une corrélation s'impose : plus le modèle lit l'environnement avant de proposer, mieux il performe. Gemini 3 Flash effectue en moyenne 21,7 actions de lecture par scénario, GPT-5 20,6, Claude 20,2. Qwen et Llama tournent autour de 16,7. Gemma plafonne à 8,8 — soit deux fois moins. La leçon est nette : observer suffisamment l'environnement précède une inférence d'objectif correcte.

Mais l'observation ne fait pas tout. Qwen 3 affiche un taux d'acceptation honorable (63,7 %) mais un taux de réussite faible (18,5 %). Diagnostic : ses propositions sont raisonnables, mais quand il passe en mode exécution, il rate les actions concrètes. Pour les petits modèles, le goulot d'étranglement n'est pas l'inférence d'objectif. C'est l'exécution.

Robustesse au bruit

L'équipe a testé deux types de perturbations. D'abord, des défaillances d'outils simulées avec des probabilités de 10 %, 20 % et 40 %. Claude tient 40-45 % de taux de réussite même à 40 % d'échecs d'API, là où Llama dégringole de 20 % à 8 %. Ensuite, du bruit environnemental sous forme de notifications parasites (spam, promotions) injectées à raison de 2, 4 ou 6 événements par minute. Claude reste stable, Gemini Flash et GPT-5 se dégradent visiblement à forte densité de bruit, Gemma reste proche de zéro indépendamment du bruit.

Une nouvelle catégorie : le « gather context »

L'analyse fine des trajectoires révèle un troisième type de réponse, en plus d'accepter ou de rejeter une proposition : aller chercher le contexte. L'utilisateur reçoit une proposition, mais au lieu de répondre tout de suite, il ignore et va lire l'email complet ou consulter son calendrier pour vérifier. Si l'assistant avait attendu, l'utilisateur aurait eu le contexte complet et la proposition aurait sans doute été acceptée. Un taux élevé de gather context signale donc un timing prématuré.

Gemma déclenche ce comportement dans 74,7 % des cas — la quasi-totalité de ses interventions arrivent trop tôt. Llama et Qwen sont entre 26 et 29 %. Claude et GPT-5 restent en dessous de 24 %. Le timing est une compétence à part entière, et les petits modèles peinent à la maîtriser.

Implications pratiques : l'avenir des assistants on-device

Pourquoi ces résultats comptent pour qui construit des produits ? Trois raisons concrètes.

D'abord, la vie privée. Un assistant qui observe en continu vos actions ne peut décemment pas envoyer ces données vers un serveur externe. Les auteurs défendent une position claire : les agents proactifs doivent tourner sur l'appareil. Le constat embêtant, c'est que les modèles open-weights de moins de 4B paramètres testés ici sont loin d'être prêts. Qwen 3 4B est le meilleur d'entre eux, et il atteint à peine 18,5 % de réussite.

Deuxième point : l'architecture asymétrique entre observation et exécution. Puisque l'observation tourne en continu mais l'exécution est ponctuelle, on peut imaginer une combinaison où un petit modèle quantifié à 4B tourne sur l'appareil pour observer, et où un modèle frontière dans le cloud n'est invoqué qu'après acceptation explicite de l'utilisateur. Les données restent locales jusqu'au consentement. Cette piste n'a pas encore été évaluée par l'équipe, mais leurs chiffres suggèrent qu'elle pourrait combler une partie du gap entre petits et grands modèles.

Troisième point : le cadre Observe-Execute force le consentement. Aucune action irréversible ne s'exécute sans validation utilisateur explicite. C'est un design pattern important pour toute équipe qui construit des assistants autonomes — la confiance utilisateur se gagne précisément sur ces garanties d'autonomie préservée.

Pour les équipes qui développent des produits, PARE-Bench fournit un terrain de mesure standardisé. Mesurer le taux de proposition, le taux d'acceptation, le taux de gather context et le taux de réussite donne une image bien plus complète que la seule métrique de complétion de tâche utilisée habituellement.

Pour aller plus loin : ce qui reste à résoudre

PARE modélise les interactions comme des appels d'outils, pas comme des interactions visuelles à l'écran. Cette abstraction est délibérée : elle crée une frontière de confidentialité naturelle (l'agent voit des actions, pas des pixels) et permet une évaluation à grande échelle. Mais elle ignore une dimension cruciale du déploiement réel : l'ancrage visuel. Un assistant multimodal devrait pouvoir lire votre écran, comprendre les éléments d'interface, gérer le contexte visuel. Cette extension vers le visuel reste à faire.

Le simulateur d'utilisateur, lui aussi, montre ses limites. Les auteurs l'ont fait varier (GPT-5-mini, Claude 4.5 Sonnet, Qwen 3 4B) et constatent que le classement relatif des assistants reste stable. Mais aucun simulateur ne capture la fatigue, l'humeur, le multitâche, ou les différences de personnalité entre utilisateurs. Certains acceptent par confiance sans vérifier, d'autres rejettent par principe quand le timing leur déplaît. Modéliser cette diversité, par exemple via des approches théorie de l'esprit, est un chantier ouvert.

Enfin, la formulation Stackelberg POMDP du problème suggère une voie d'amélioration claire : utiliser les métriques d'acceptation et de réussite comme signaux de récompense pour entraîner les agents proactifs par renforcement. Aucun des modèles testés n'a été spécifiquement entraîné pour cette tâche — ils ont été évalués hors distribution. L'écart entre frontière et petits modèles pourrait se réduire considérablement avec un entraînement ciblé sur ces signaux d'interaction.

Le code de PARE et les 143 scénarios de PARE-Bench sont publics. Pour quiconque travaille sur les assistants intelligents, les agents copilotes ou les produits IA embarqués, c'est un outil de mesure à intégrer dès maintenant. Le plafond de 42 % laisse une marge de progression considérable, et c'est précisément ce qui rend le terrain intéressant.
