Memory Transfer Learning: How Memories are Transferred Across Domains in Coding Agents

Lecture Critique d'Article

Objectif et contexte

Les agents de code auto-évolutifs exploitent une mémoire des exécutions passées pour améliorer leurs performances futures. Les approches existantes (ReasoningBank, AgentKB, AWM) restreignent l'usage de la mémoire au même domaine ou au même benchmark, privant les agents d'une base d'expériences potentiellement riche issue de tâches voisines partageant la même infrastructure (shells, langages, dépendances).

Les auteurs posent trois questions de recherche explicites : les mémoires hétérogènes améliorent-elles les performances ? Pourquoi le transfert cross-domaine fonctionne-t-il ? Quels facteurs déterminent son efficacité ? Le cadre proposé — Memory Transfer Learning (MTL) — unifie un pool mémoire provenant de six benchmarks de code couvrant programmation compétitive, ingénierie logicielle au niveau dépôt, génération de code scientifique et recherche ML.

Méthodologie

Le protocole compare quatre formats de mémoire organisés par niveau d'abstraction croissant : Trajectory (commandes brutes et observations), Workflow (séquences d'actions réutilisables), Summary (résumé structuré de l'expérience), Insight (principes généralisables sans référence aux fichiers). La génération de mémoire s'appuie sur gpt-5-mini avec des prompts distincts pour trajectoires réussies et échouées.

L'architecture du pipeline repose sur deux étapes : génération offline à partir d'inférences préalables, puis récupération top-N (N=3) par similarité cosinus d'embeddings (text-embedding-3-small). Pour les mémoires sans champ Task, la requête est générée en demandant au modèle de rédiger un plan de 4-5 phrases avant d'embedder.

L'évaluation porte sur six benchmarks (LiveCodeBenchv6, Aider-Polyglot, SWEBench-Verified, TerminalBench2, ReplicationBench, MLGym-Bench), avec 100 tâches échantillonnées par benchmark et un score Pass@3 sur trois runs. Trois modèles sont testés : GPT-5-mini, DeepSeek V3.2, Qwen3-Coder-480B-A35B-Instruct. Le harness mini-swe-agent et la plateforme harbor servent d'environnement d'exécution.

Résultats principaux

MTL avec mémoire Insight produit un gain moyen de +3,7 % en Pass@3 sur GPT-5-mini, atteignant jusqu'à +8,3 % sur MLGym-Bench. Les gains se confirment sur DeepSeek V3.2 (+2,6 %) et Qwen3-Coder (+1,8 %). Comparé aux baselines self-evolving, MTL surpasse ReasoningBank de +2,9 % et AgentKB de +1,7 %, tout en utilisant 431 mémoires contre 5 899 pour AgentKB — un ratio d'efficience de 13:1.

La hiérarchie des formats suit exactement le niveau d'abstraction : Insight > Summary > Workflow > Trajectory. Les auteurs le quantifient via l'indice Davies-Bouldin (3,09 → 6,50) et LISI (1,70 → 4,00), qui montrent une dissolution progressive des clusters par benchmark à mesure que l'abstraction monte.

L'analyse qualitative sur GPT-5 classe les contributions de la mémoire transférée : 15 % discipline de workflow itératif, 14,5 % adhérence au protocole d'interaction, 14,4 % vérification orientée tests, 10,4 % évitement d'anti-patterns. Le transfert d'algorithmes spécifiques ne représente que 5,5 % des gains — preuve que le bénéfice réside dans le comment agir plutôt que dans le quoi calculer.

Le passage en conditions contrôlées (insights task-agnostic vs task-specific au sein du même format) confirme que l'abstraction en elle-même, et non le format, porte le gain : +1,1 % en moyenne. Le transfert cross-modèle fonctionne aussi, y compris d'un modèle faible vers un modèle fort, confirmant l'hypothèse de méta-connaissance model-agnostic.

Discussion et limites

Le principal bémol méthodologique concerne le juge : gpt-5-mini sert simultanément de modèle de base, de générateur de mémoire et de juge pour évaluer succès/échec. Cette configuration introduit un biais d'auto-préférence documenté dans la littérature LLM-as-judge que les auteurs n'atténuent pas par validation humaine.

L'échantillonnage à 100 tâches par benchmark reste modeste pour des benchmarks comme SWEBench-Verified (500 tâches originales). Les intervalles de confiance ne sont pas reportés, ce qui complique l'interprétation des écarts de 1-2 points sur certaines cellules du Table 1 (Aider-Polyglot recule de 1 % sur DeepSeek V3.2 sans que la significativité soit discutée).

La section sur le transfert négatif est lucide et distingue trois modes d'échec : ancrage par similarité superficielle, fausse confiance de validation, imitation aveugle de patterns. Les ablations sur les méthodes de récupération avancées (reranking LLM, réécriture adaptative) sont franches : les deux approches sophistiquées dégradent les performances par rapport à la similarité d'embedding simple.

Le cadre formel en annexe C reste essentiellement descriptif. La décomposition embedding = zinv + zsp et la proposition 1 énoncent le résultat empirique sans apporter de prédiction falsifiable au-delà de ce qu'on observe déjà.

Reproductibilité

Le site memorytransfer.github.io est annoncé mais son contenu n'est pas vérifié dans le texte. Les prompts de génération de mémoire figurent en appendice E, ce qui facilite la réplication. Les benchmarks utilisés sont publics. Les modèles GPT-5-mini et DeepSeek V3.2 étant propriétaires ou à accès contrôlé, la reproduction exacte nécessite des accès API coûteux.

Aucun chiffre n'est donné sur le coût total d'inférence, ni sur la variance entre les trois runs utilisés pour Pass@3. La graine aléatoire utilisée pour le sampling des 100 tâches n'est pas précisée, ce qui peut affecter la comparabilité.

Impact et applications

Le travail déplace l'attention du design de mécanismes de mémoire sophistiqués vers une question plus fondamentale : quel niveau d'abstraction maximise la généralisation ? La réponse — plus c'est abstrait, mieux ça transfère — va à l'encontre de l'intuition que les trajectoires détaillées sont plus informatives. Elle rejoint la littérature sur les prompts meta-cognitifs et les checklists d'ingénierie logicielle.

Pour les praticiens, la recette est directe : générer des insights de type « principes de vérification » plutôt que stocker des logs d'exécution ; maintenir un pool cross-benchmark unifié ; ne pas surdimensionner avec de la mémoire générale (AgentKB utilise 13× plus de mémoires pour un résultat inférieur). La bascule conceptuelle de « mémoire-log » vers « mémoire-guide » est actionnable.

Positionnement dans la littérature

L'article dialogue avec trois lignées. Sur les agents auto-évolutifs, il complète ReasoningBank (Ouyang et al., 2025) en montrant que les insights cross-domaine surpassent les insights in-domain. Sur le transfer learning classique (Zhuang et al., 2020 ; Houlsby et al., 2019), il propose une variante non-paramétrique où le transfert se fait par mémoire textuelle plutôt que par adaptation de poids. Sur les frameworks multi-tâches, il dépasse AgentKB (Tang et al., 2025) qui mélangeait raisonnement général, web et code, en montrant que se restreindre au code améliore l'efficience.

L'argument central — l'abstraction dicte la transférabilité — pourrait se généraliser au-delà des agents de code, vers les agents web ou scientifiques. Les auteurs n'explorent pas cette piste mais leurs résultats suggèrent qu'une investigation cross-modalité serait une suite logique.
