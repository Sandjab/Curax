Memory Transfer Learning: How Memories are Transferred Across Domains in Coding Agents

Vulgarisation

Quand les agents de code apprennent à partager leurs souvenirs

Un agent de code qui résout un bug Django devrait-il pouvoir puiser dans ses expériences de compétitions de programmation ? Jusqu'ici, la réponse par défaut était non. Les agents mémorisent leurs succès et leurs échecs, mais chaque domaine reste cloisonné : une mémoire pour SWE-Bench, une autre pour MLGym, une troisième pour LiveCodeBench. Une équipe de KAIST, NYU et DeepAuto.ai vient de démontrer que ce cloisonnement est un gaspillage. En mutualisant les mémoires à travers six benchmarks hétérogènes, ils obtiennent un gain moyen de 3,7 % — et, plus intéressant encore, ils identifient précisément ce qui se transfère et pourquoi.

L'étude, intitulée Memory Transfer Learning, bouscule une hypothèse implicite du domaine : que l'expérience acquise sur un type de tâche serait trop spécifique pour servir ailleurs. Les résultats racontent une autre histoire. Ce qui voyage bien entre domaines, ce ne sont pas les bouts de code ni les algorithmes particuliers. Ce sont les réflexes du métier : vérifier avant de modifier, valider avec un test jetable, se méfier des raccourcis. Le savoir-faire plutôt que le savoir.

Le problème : des mémoires qui s'ignorent

Les agents de code modernes fonctionnent en boucle. Ils tentent une tâche, observent le résultat, et stockent l'expérience dans une mémoire qui sera réinjectée lors de tâches similaires. Le principe s'appelle auto-évolution : pas besoin de réentraîner le modèle, il s'améliore en capitalisant sur ses propres essais. C'est séduisant sur le papier, et ça fonctionne — à condition que la nouvelle tâche ressemble suffisamment à une ancienne.

Le hic, c'est que la plupart des systèmes actuels ne vont puiser que dans les souvenirs du même benchmark. Un agent qui a résolu cent exercices de LiveCodeBench n'utilisera pas ces expériences quand on lui demande de corriger un bug dans un repository Django. Pourtant, les deux tâches partagent énormément : le même shell Linux, le même Python, les mêmes bibliothèques, les mêmes pièges d'encodage, la même nécessité de tester avant de soumettre. En refusant de traverser les frontières entre domaines, on jette la moitié de l'expérience acquise.

Les auteurs posent trois questions frontales. La mémoire d'un domaine peut-elle vraiment aider dans un autre ? Si oui, qu'est-ce qui se transfère exactement ? Et comment formater cette mémoire pour maximiser le transfert ? Leur réponse tient en une phrase : l'abstraction fait tout.

La méthode : quatre façons de se souvenir

Pour comparer les formats de mémoire, les chercheurs ont généré la même expérience sous quatre représentations différentes, du plus concret au plus abstrait.

La Trajectoire conserve tout. Chaque commande bash tapée par l'agent, chaque sortie du terminal, dans l'ordre. C'est le journal brut de l'exécution. Utile pour reproduire, mais lourd et saturé de détails spécifiques à la tâche d'origine.

Le Workflow est un résumé opérationnel. On extrait de la trajectoire les étapes qui comptent vraiment — celles qui ont fait basculer le résultat — et on les organise autour d'un objectif clair. Une recette abrégée.

Le Résumé raconte l'expérience en prose. Un paragraphe qui décrit l'environnement, les actions menées, le résultat obtenu, et surtout une analyse du pourquoi ça a marché ou échoué. On passe du quoi au pourquoi.

L'Insight pousse l'abstraction plus loin. Titre, description d'une phrase, contenu en trois lignes maximum. La consigne donnée au modèle qui génère ces insights est explicite : ne mentionner aucun fichier spécifique, aucun détail particulier, produire une leçon généralisable. On distille l'expérience jusqu'à obtenir un principe.

Pour évaluer le transfert, les auteurs ont constitué un pot commun : les mémoires de cinq benchmarks servent à aider le sixième. Quand on teste l'agent sur SWE-Bench, il pioche uniquement dans les mémoires issues de LiveCodeBench, d'Aider, de MLGym, de TerminalBench et de ReplicationBench. Aucune contamination, pas de triche. Pour chaque nouvelle tâche, on récupère les trois souvenirs les plus proches par similarité cosinus, et on les injecte dans le prompt système de l'agent.

Une analogie simple : imaginez un développeur qui change de mission. Il peut ramener son carnet de code précédent (Trajectoire), ou la liste des étapes clés qui ont marché (Workflow), ou une rétrospective détaillée (Résumé), ou quelques principes gravés dans sa tête (Insight). Lequel l'aidera le plus dans un contexte totalement nouveau ? L'intuition suggère les principes. Les mesures confirment.

Résultats : l'abstraction l'emporte

Sur les six benchmarks testés avec GPT-5-mini, le format Insight pulvérise les autres. Gain moyen de 3,7 % en Pass@3, avec des pics à +8,3 % sur MLGym-Bench et +7,8 % sur ReplicationBench. Le format Trajectoire, lui, produit parfois des régressions — blindly suivre une commande spécifique à une autre tâche peut égarer l'agent. Le classement est sans appel : Insight > Résumé > Workflow > Trajectoire. Plus on abstrait, mieux ça transfère.

L'effet se reproduit sur d'autres modèles. DeepSeek V3.2 gagne 2,6 %, Qwen3-Coder gagne 1,8 %. Le mécanisme n'est pas propre à GPT-5-mini. Mieux : les mémoires générées par un modèle fonctionnent sur un autre. Un agent Qwen peut bénéficier d'insights produits par GPT-5-mini, même si l'effet reste inférieur aux mémoires auto-générées. Le savoir-faire encodé dans ces insights n'est pas lié à la manière dont un modèle particulier pense.

Un chiffre frappe dans la comparaison avec les approches concurrentes. AgentKB, une méthode récente, utilise une mémoire de 5 899 entrées. ReasoningBank en utilise 97. Memory Transfer Learning en utilise 431 et bat les deux. Dix fois moins de mémoires qu'AgentKB, pour une meilleure performance. La taille brute ne fait pas tout — la qualité du format compte davantage.

L'analyse qualitative révèle ce qui se transfère réellement. Les auteurs ont demandé à GPT-5 de catégoriser les cas où l'agent échouait en zéro-shot mais réussissait avec MTL. Le résultat est net : 85 % des gains viennent de ce qu'ils appellent du méta-savoir. Discipline de workflow itératif (inspecter, modifier, vérifier), respect des contraintes d'interface, validation pilotée par les tests, prudence face aux refactorings agressifs, robustesse des entrées. Seulement 5,5 % des gains proviennent du transfert direct de stratégies algorithmiques. Autrement dit, l'agent apprend à mieux se comporter, pas à mieux coder.

Un cas illustre bien cette dynamique. Sur une tâche SWE-Bench, l'agent zéro-shot échoue en tentant une correction frontale d'une erreur Django. Avec MTL, il récupère un insight venu de LiveCodeBench qui lui conseille d'écrire un petit test Python inline via un heredoc pour valider la correction avant de la soumettre. L'insight n'a rien à voir avec Django, rien à voir avec le bug précis. Il encode une habitude de travail. L'agent l'applique, construit son propre test, vérifie, soumet, réussit.

Quand le transfert tourne mal

Tout n'est pas rose. Memory Transfer Learning peut aussi dégrader la performance, et les auteurs passent un temps honorable à disséquer les échecs. Trois causes principales émergent.

L'ancrage trompeur intervient quand une mémoire superficiellement similaire — même vocabulaire, même type de fichier — impose des hypothèses qui ne s'appliquent pas. L'agent détourne son raisonnement vers des contraintes imaginaires. Un exemple édifiant : une mémoire Workflow générée sur une tâche en R, avec ses routines d'écriture de fichiers spécifiques, transférée sur une tâche en C++. L'agent reproduit mécaniquement le pattern R dans un environnement C++. Catastrophe syntaxique garantie.

La fausse confiance de validation apparaît quand l'agent reproduit des vérifications superficielles au lieu d'examiner les critères formels de la tâche. Il croit avoir validé, il n'a rien validé.

Le transfert indiscriminé de bonnes pratiques se produit quand un pattern efficace ailleurs devient une rigidité procédurale ici. L'agent applique une recette parce qu'elle lui est familière, et passe à côté des spécificités de la nouvelle tâche.

Ces échecs éclairent le plafond actuel de l'approche. Le problème n'est pas la mémoire elle-même, mais la façon de la récupérer et de l'adapter. Les auteurs ont testé des méthodes de retrieval avancées — reranking par LLM, réécriture adaptative des mémoires — et elles sous-performent toutes le simple embedding cosinus. Les techniques classiques de retrieval, conçues pour des contextes statiques, ne se transposent pas bien aux agents multi-étapes dynamiques.

Implications pratiques : repenser la mémoire des agents

Pour quiconque construit des agents de code en production, cette étude envoie trois messages concrets.

Premier message : arrêtez de compartimenter les mémoires par domaine. Si vous opérez un agent qui traite à la fois du debugging, de la génération de code, des tâches de data science, faites un pot commun. Vous avez plus à gagner qu'à perdre, à condition de bien formater.

Deuxième message : stockez des insights, pas des traces. La tentation naturelle, quand on conçoit un système de mémoire, est de tout garder — c'est bon marché, c'est exhaustif, ça paraît sûr. Mais une mémoire riche en détails bruts peut activement nuire. Mieux vaut un post-traitement qui demande au modèle de distiller chaque expérience en un principe court et généralisable. Le coût de génération est ponctuel, le bénéfice est permanent.

Troisième message : la mémoire scale avec la diversité. Les expériences de passage à l'échelle montrent que les gains augmentent avec la taille du pool ET avec le nombre de domaines sources. Un pool de 400 insights issus de neuf domaines bat un pool de 400 insights issus d'un seul domaine. La diversité est un multiplicateur, pas un bruit.

Pour les équipes qui déploient des assistants de code internes, l'implication est directe. Un agent qui assiste des développeurs sur du code métier peut tirer profit d'expériences venues de DevOps, de tests d'infrastructure, d'analyses de données — même si aucune de ces tâches ne ressemble au cas d'usage principal. Les réflexes de validation, les guardrails face aux contraintes d'environnement, la discipline d'édition minimale se transfèrent. Il suffit de les encoder correctement.

Pour aller plus loin

L'étude laisse plusieurs chantiers ouverts, et certains sont stratégiques pour la suite.

Le premier concerne le retrieval. Les méthodes actuelles, basées sur la similarité d'embedding, sont simples mais myopes. Elles récupèrent ce qui ressemble lexicalement à la tâche, pas ce qui aidera à la résoudre. Imaginez un moteur de recherche qui vous renverrait uniquement les pages contenant les mêmes mots que votre requête, sans tenir compte de leur utilité. On sait que c'est sous-optimal — mais dans un contexte multi-étapes où les besoins évoluent au fil de l'exécution, aucune alternative n'a encore démontré sa supériorité. Les auteurs suggèrent des pistes : routing par domaine, retrieval pas-à-pas, réécriture contextuelle. Aucune n'est mûre.

Le second chantier porte sur l'adaptation. Même avec la bonne mémoire récupérée, l'agent peut l'appliquer mal. Les cas d'échec en C++ à partir d'un workflow R montrent qu'il manque une étape de traduction contextuelle. Comment apprendre à un agent à extraire le principe d'un exemple, sans copier ses détails ? C'est une question ancienne dans l'apprentissage par analogie, mais elle prend un relief nouveau quand le coût d'une mauvaise analogie est un échec de build en production.

Le troisième point concerne le transfert inter-modèles. Les résultats montrent qu'il fonctionne, mais moins bien que les mémoires auto-générées. Cela suggère que les mémoires encodent des biais propres au modèle qui les produit — préférences de style, tournures de raisonnement, familiarités avec certains outils. Identifier ces biais et les neutraliser permettrait de construire des bibliothèques de mémoires vraiment partageables entre équipes utilisant des modèles différents. Un rêve d'interopérabilité qui reste à concrétiser.

Dernière piste : l'évolution continue. L'étude travaille sur un pool figé. Dans la vraie vie, un agent produit de nouvelles mémoires en permanence, et certaines anciennes deviennent obsolètes ou contradictoires. Gérer ce flux — oublier intelligemment, consolider, détecter les conflits — reste un problème ouvert. Les auteurs citent des travaux récents comme MemEvolve qui s'y attaquent, mais le terrain est neuf.

Reste une observation qui mérite d'être méditée. Les gains les plus forts se produisent sur les benchmarks les plus difficiles — MLGym et ReplicationBench, où le zéro-shot plafonne respectivement à 58 % et 11 %. Sur les tâches plus simples comme LiveCodeBench, où l'agent réussit déjà 91 % des cas, le transfert n'apporte que 2 points. La mémoire, semble-t-il, aide surtout là où le modèle seul bute. C'est cohérent avec l'idée qu'elle transmet du méta-savoir : quand une tâche est à portée de la capacité brute du modèle, aucune expérience externe n'est nécessaire ; quand elle dépasse ce plafond, le savoir-faire accumulé fait la différence. Ce pattern mérite d'être confirmé à plus grande échelle, mais il suggère une règle de conception : investir dans la mémoire là où les modèles peinent, pas là où ils excellent déjà.
