Agentic Code Reasoning

Lecture Critique d'Article

Objectif et contexte

Le raisonnement agentique sur le code, défini ici comme la capacité d'un agent LLM à explorer un dépôt et à établir des propriétés sémantiques sans exécuter le code, occupe une position inconfortable entre deux extrêmes. D'un côté, les approches non structurées de type chain-of-thought autorisent l'agent à conclure sans justifier, ce qui produit des hallucinations sémantiques. De l'autre, la vérification formelle en Lean ou Coq exige une formalisation complète des sémantiques de langage, irréaliste sur du code de production multi-langage.

Ugare et Chandra proposent une voie médiane qu'ils nomment raisonnement semi-formel : un template de prompt qui force l'agent à énoncer des prémisses explicites, à tracer les chemins d'exécution test par test, puis à dériver une conclusion formelle. Le certificat reste en langage naturel mais sa structure rigide empêche l'agent de sauter des cas. La cible applicative annoncée est claire : fournir un signal de récompense fiable pour l'entraînement RL des agents de coding sans dépendre de sandboxes coûteux.

Méthodologie

Trois tâches structurent l'évaluation. La vérification d'équivalence de patches demande à l'agent, étant donné deux patches résolvant la même issue, de prédire s'ils produisent les mêmes résultats sur la suite de tests. La localisation de fautes sur Defects4J impose d'identifier les lignes buggées à partir du seul nom du test échouant, sans stack trace. Le code QA sur RubberDuckBench mesure la capacité à répondre à 15 questions de compréhension de code évaluées par grilles d'experts.

Le harness agentique repose sur SWE-agent avec accès bash, exploration sur 100 étapes maximum, mais sans pouvoir exécuter le code du dépôt ni interroger l'historique git. Les comparaisons sont des ablations entre raisonnement standard (chain-of-thought libre) et raisonnement semi-formel (template structuré) sur les mêmes modèles : Sonnet-4.5 et Opus-4.5.

Le dataset d'équivalence de patches mérite attention. Les auteurs ne tirent pas uniformément depuis SWE-bench-Verified mais curent activement 170 paires difficiles via un score de similarité combiné LLM (0-10) et difflib (>0.3), pour stresser le verifier sur les cas où la similarité de surface masque la divergence sémantique. Un second jeu de 200 patches issus de live-swe-agent (gemini-3-pro) est échantillonné aléatoirement avec équilibrage 50/50 correct/incorrect.

Résultats principaux

Sur les patches curés, le raisonnement semi-formel fait passer Opus-4.5 de 78,2% à 88,8% de précision, soit une réduction d'erreurs de près de moitié, au prix d'un coût computationnel multiplié par 2,8 (28 étapes contre 10). Sur les patches réels avec test patches disponibles, Opus-4.5 atteint 93% contre 87% en standard et 73% pour la baseline difflib avec seuil optimisé a posteriori.

Sur RubberDuckBench, Opus-4.5 progresse de 78,3% à 87% (+8,7 points) avec le template semi-formel. Effet notable : Sonnet-4.5 ne bénéficie pas du template structuré (84,2% standard contre 84,8% semi-formel), suggérant un plateau dépendant du modèle. Les auteurs interprètent cela comme un signe que le template corrige principalement les défauts d'Opus à deviner depuis les noms de fonctions.

Sur Defects4J, le gain est de +5 à +12 points en Top-5 selon le mode et la métrique. Le mode agentique avec semi-formel atteint 72,1% Top-5 sous la métrique stricte « All » sur l'échantillon de 50 bugs. La validation à plus grande échelle sur 100 bugs réduit l'écart à +5 points, ce que les auteurs attribuent à la présence de bugs trivialement résolus depuis le seul code de test.

Discussion et limites

L'analyse d'erreurs est l'un des points forts de l'article. Les auteurs identifient des modes d'échec qualitativement distincts : tracé d'exécution incomplet malgré l'instruction, sémantique des bibliothèques tierces devinée par le nom, différences sémantiques détectées mais jugées hors-sujet à tort. Le cas py_5 illustre une limite intrinsèque : le raisonnement structuré peut produire des erreurs plus confiantes en construisant des chaînes plausibles mais incomplètes.

Les faiblesses méthodologiques sont nettes. Le benchmark RubberDuckBench ne contient que 15 questions, ce qui ne permet aucune analyse statistique sérieuse — un écart de 9 points sur 15 items représente une poignée de réponses. La curation du dataset d'équivalence introduit un biais de sélection assumé mais non corrigé : on mesure la performance sur la queue dure de la distribution, pas sur le cas moyen. La contamination des données SWE-bench est mentionnée puis évacuée par l'argument des comparaisons relatives, ce qui est valable pour l'ablation mais ne dit rien des chiffres absolus.

Le coût n'est jamais quantifié en dollars ou en tokens. L'argument économique central — éviter les sandboxes en RL — repose sur l'hypothèse implicite que 28 à 43 étapes d'agent Opus-4.5 sont moins coûteuses qu'une exécution de tests. Cette hypothèse mériterait une comparaison empirique, surtout face à difflib qui atteint 73% à coût quasi nul.

L'absence de comparaison avec d'autres techniques de prompting structuré (Tree-of-Thoughts, self-consistency, programme assistant) limite l'attribution causale du gain à la « semi-formalité ». On ne sait pas si le bénéfice provient de la structure du certificat, de la longueur du raisonnement, ou simplement du budget d'étapes plus élevé qu'autorise le format.

Reproductibilité

Les annexes A et B fournissent les templates de prompt complets pour l'équivalence de patches et la localisation de fautes, ce qui est nécessaire mais insuffisant. Aucun lien vers un dépôt de code, aucune mention de release du dataset curé de 170 patches, aucun script d'évaluation publié. Les benchmarks tiers (Defects4J, RubberDuckBench, SWE-bench) sont publics, mais le pipeline de curation et l'agent SWE minimal utilisé ne sont pas distribués. La reproductibilité reste partielle : un lecteur peut réimplémenter l'idée mais pas répliquer les chiffres exacts.

Impact et applications

L'application la plus tangible est le verifier sans exécution pour les pipelines RL d'agents de coding, où le coût de setup d'environnements (CI, sandboxes) domine. À 93% de précision, le signal reste trop bruité pour remplacer les tests sur les modèles frontières, mais devient utilisable comme reward shaping ou comme filtre de pré-sélection. Les auteurs mentionnent les pipelines SWE-RL, SWE-Gym et R2E-Gym comme bénéficiaires potentiels.

L'extension à l'analyse statique générale (détection de vulnérabilités, code smells, mauvais usage d'API) est plausible mais spéculative. La généralisation inter-langages est démontrée à petite échelle sur Java, Python et C++ via RubberDuckBench, sans creuser la question des sémantiques spécifiques (closures, ownership, généricité).

Positionnement dans la littérature

L'article se positionne explicitement entre SWE-RM (reward model entraîné), Agentic Rubrics (rubriques générées par LLM) et CodeJudge (LLM-as-judge), tous présentés comme « non structurés ». Le contraste avec la vérification formelle (Lean, Coq, Datalog) est posé comme l'autre extrême. La filiation revendiquée passe par le chain-of-thought de Wei et al. (2022), ReAct (Yao et al. 2023) et CodeAct (Wang et al. 2024), avec l'argument que le template task-specific est ce qui généralise mieux que la rubrique générée.

Le travail le plus complémentaire est celui de Sistla et al. (2025) sur la vérification post-hoc du raisonnement LLM via Datalog : Ugare et Chandra opèrent côté input (forcer la qualité du raisonnement), Sistla et al. côté output (vérifier formellement le raisonnement produit). Une combinaison des deux approches semble naturelle et n'est pas encore explorée.
