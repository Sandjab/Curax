Agentic Code Reasoning

Vulgarisation

Faire raisonner une IA sur du code sans jamais l'exécuter

Deux correctifs Python pour le même bug. Visuellement, ils font la même chose : formater une année sur deux chiffres. Un agent IA standard les déclare équivalents en quelques secondes. Mauvaise réponse. L'un des deux plante avec une AttributeError, parce qu'une fonction format() définie dans le module masque silencieusement la fonction native de Python. Pour le découvrir, il aurait fallu ouvrir le fichier, descendre ligne 340, lire la définition. L'agent ne l'a pas fait.

Cet exemple, tiré d'un vrai ticket Django, illustre le problème que Shubham Ugare et Satish Chandra (Meta) attaquent dans leur article Agentic Code Reasoning. Comment fait-on pour qu'un agent LLM analyse sérieusement du code, suive les dépendances entre fichiers, et conclue avec une certitude raisonnable — sans jamais exécuter le code ? Leur réponse tient en deux mots : raisonnement semi-formel.

Le problème : raisonner sans exécuter

Quand un développeur expérimenté relit un patch, il fait constamment deux choses : il navigue dans le code pour vérifier des hypothèses, et il trace mentalement ce qui va se passer à l'exécution. Les agents LLM modernes savent faire la première partie. Ils ouvrent les fichiers, cherchent les définitions, lisent les tests. Pour la deuxième partie — le raisonnement sémantique précis — ils trichent. Ils devinent. Ils supposent qu'une fonction nommée format est la format de Python. Ils affirment sans vérifier.

Pourquoi est-ce un problème industriel et pas juste académique ? Parce que vérifier qu'un patch fonctionne coûte cher. Aujourd'hui, pour entraîner un agent de programmation par renforcement, il faut exécuter chaque patch dans un sandbox, installer les dépendances, lancer la suite de tests. Multiplié par des centaines de milliers d'itérations, ça devient le poste de coût dominant. Si un LLM pouvait juger la correction d'un patch sans rien exécuter, le pipeline d'entraînement deviendrait dramatiquement moins cher.

Le problème, c'est la fiabilité. Un agent qui se trompe une fois sur quatre donne un signal de récompense pourri pour le RL. Les approches purement formelles — traduire le code en Lean ou Coq pour faire une preuve mécanique — sont irréalistes sur un dépôt Python ou Java arbitraire. Personne ne va formaliser la sémantique de Django ou de Mockito. Il faut donc une voie médiane.

La méthode : un certificat à remplir

L'idée des auteurs est presque banale, ce qui la rend intéressante. Au lieu de demander à l'agent « ces deux patches sont-ils équivalents ? », ils lui imposent un gabarit structuré à compléter, case par case. Une sorte de formulaire qui force l'agent à montrer son travail.

Le gabarit ressemble à ceci pour la tâche d'équivalence de patches : énoncer les définitions utilisées, lister les prémisses (que modifie le patch 1 ? que modifie le patch 2 ? que vérifient les tests ?), puis pour chaque test, formuler une réclamation du type « avec le patch 1, le test X passe parce que [trace d'exécution] ». À la fin, soit un contre-exemple explicite si les patches diffèrent, soit une conclusion formelle d'équivalence appuyée sur les traces.

Le mot important ici est certificat. L'agent ne produit pas une démonstration formelle au sens mathématique, mais un document structuré dans lequel chaque conclusion pointe vers une preuve concrète tirée du code. On reste en langage naturel, on garde la souplesse d'un LLM, mais on enlève la possibilité de sauter des étapes. Pour remplir la case « avec le patch 1, le test échoue parce que… », l'agent doit aller chercher la fonction réellement appelée, lire sa définition, suivre les appels. Il ne peut plus se contenter de deviner.

Une analogie utile : c'est la différence entre demander à un junior « est-ce que ce code marche ? » et lui demander « décris-moi ligne par ligne ce qui se passe quand on exécute le test ». La deuxième formulation l'oblige à ouvrir les fichiers. La première l'autorise à bluffer.

Les auteurs déclinent ce gabarit pour trois tâches différentes. Pour l'équivalence de patches, le squelette est celui décrit ci-dessus. Pour la localisation de bugs, le gabarit demande à l'agent de poser des hypothèses explicites (« je pense que le bug est dans tel fichier parce que… »), puis de les confirmer ou les réfuter au fil de l'exploration. Pour les questions sur du code, le formulaire impose une table de trace des fonctions (avec emplacements fichier:ligne et comportement vérifié), une analyse de flux de données, et une vérification de l'hypothèse contraire — autrement dit, l'agent doit chercher activement ce qui contredirait sa réponse.

Le setup expérimental mérite d'être noté. L'agent tourne avec un harness SWE-agent minimal, peut lire les fichiers et lancer du Python isolé, mais ne peut pas exécuter le dépôt cible. Pas d'installation de dépendances, pas de sandbox, pas de tests. Git est désactivé pour empêcher de tricher en lisant les commits de correction. C'est de l'analyse statique pure, conduite par un agent.

Résultats : 93 % de précision sans exécuter

Les chiffres parlent d'eux-mêmes. Sur la tâche centrale d'équivalence de patches avec Opus-4.5, le raisonnement standard atteint 78 % de précision sur un dataset délibérément difficile. Le raisonnement semi-formel monte à 88,8 %. Une réduction des erreurs de près de moitié, simplement en changeant la forme du prompt — pas le modèle, pas l'entraînement.

Sur un cas d'usage plus réaliste — vérifier si un patch généré par un agent gemini-3-pro correspond bien au patch de référence — le semi-formel atteint 93 % de précision. À titre de comparaison, la méthode actuellement utilisée dans SWE-RL (un calcul de similarité textuelle avec difflib) plafonne à 73 %. Un appel LLM unique sans exploration fait 86 %. L'exploration agentique apporte donc 7 points, et la structuration semi-formelle en apporte encore 6 de plus.

Pour la localisation de bugs sur Defects4J (un benchmark classique de bugs Java reproductibles), le semi-formel améliore la précision Top-5 de 5 à 12 points selon les configurations. Et pour le question-answering sur du code via RubberDuckBench, on passe de 78 % à 87 % avec Opus.

Tout n'est pas rose. Le coût en tokens est réel : le semi-formel consomme environ 2,8 fois plus d'étapes de raisonnement que le standard. L'agent prend son temps, ouvre plus de fichiers, écrit des certificats verbeux. Si la cible était de remplacer une exécution réelle, l'arbitrage économique reste favorable — un sandbox Docker avec installation de dépendances coûte bien plus. Mais ce n'est pas gratuit.

Autre nuance intéressante : l'effet du semi-formel dépend du modèle. Sur Sonnet-4.5, en question-answering, le gain est négligeable (84,2 % standard contre 84,8 % semi-formel). Sur Opus-4.5 même tâche, le gain est de 8,7 points. Hypothèse des auteurs : Sonnet a déjà tendance à raisonner de façon structurée, le gabarit ne change pas grand-chose ; Opus a une propension plus forte à deviner sur les noms de fonctions, et le gabarit corrige ce biais.

Pourquoi ça compte pour qui construit avec des LLM

Trois implications concrètes émergent.

La première touche directement les équipes qui entraînent des agents de programmation. Aujourd'hui, le coût dominant d'un pipeline RL pour agent SWE n'est pas le GPU du modèle, c'est l'infrastructure d'exécution : sandboxes Docker, gestion des dépendances par dépôt, parallélisation des suites de tests. Un vérificateur LLM à 93 % de précision, c'est un signal de récompense exploitable pour une grande partie des itérations. On n'élimine pas l'exécution réelle — on la garde pour valider périodiquement et pour les cas ambigus — mais on peut absorber le gros du volume avec de l'inférence pure. Le ratio coût/itération change d'ordre de grandeur.

La deuxième concerne l'analyse statique en général. Les outils classiques — linters, vérificateurs de types, analyses de flux — encodent une logique d'analyse dans des algorithmes spécialisés, langage par langage. Un agent piloté par un gabarit de raisonnement n'a pas cette contrainte. Le même gabarit fonctionne sur du Python, du Java, du C++. Pour des tâches comme la détection de vulnérabilités ou les code smells, où la spécialisation par langage coûte cher à maintenir, c'est une alternative crédible. On échange des garanties formelles contre de la flexibilité.

La troisième implication est plus inconfortable. Elle concerne ce qui fait qu'un agent IA raisonne « bien » sur du code. Les auteurs montrent qu'il ne s'agit pas seulement de capacité brute du modèle : la forme du prompt change qualitativement le comportement. Un agent qui doit remplir un gabarit explore davantage, suit plus loin les appels de fonctions, vérifie ses hypothèses au lieu de pattern-matcher sur des noms. Cela suggère qu'une partie du « manque de fiabilité » des agents de programmation est moins un problème de modèle qu'un problème de cadrage de la tâche.

L'analogie côté humain est parlante. Un développeur senior expérimenté ne raisonne pas mieux qu'un junior parce qu'il a un cerveau différent. Il raisonne mieux parce qu'il a internalisé une discipline : énumérer les cas, vérifier ses hypothèses, ne pas faire confiance aux noms. Le semi-formel impose cette discipline de l'extérieur, via le prompt.

Pour aller plus loin

L'étude laisse plusieurs portes ouvertes.

D'abord, le gabarit semi-formel est aujourd'hui un artefact de prompt. Les auteurs suggèrent qu'un post-entraînement supervisé sur des trajectoires structurées pourrait internaliser cette discipline, et économiser les tokens d'overhead. Si Anthropic ou OpenAI sortent des modèles de programmation entraînés sur ce type de trace, le gain pourrait devenir gratuit côté inférence. C'est une piste à suivre.

Ensuite, les modes d'échec résiduels sont instructifs. Sur les 7 % de cas où Opus + semi-formel se trompe encore, trois causes dominent. L'agent suppose le comportement d'une fonction de bibliothèque tierce dont il n'a pas le code source. Il identifie une différence sémantique réelle mais la juge à tort sans impact sur les tests. Et parfois — c'est le plus dérangeant — il construit une chaîne de raisonnement élaborée mais incomplète, qui le rend plus confiant dans une mauvaise réponse. La structure de raisonnement peut donc amplifier l'erreur quand elle est mal posée. Ce n'est pas un argument contre la méthode, mais un rappel : un agent qui raisonne longtemps n'est pas automatiquement un agent qui raisonne juste.

Une autre piste touche à la vérification hybride. Le travail de Sistla et al. cité par les auteurs traduit a posteriori les raisonnements LLM en faits Datalog et les vérifie avec de l'analyse statique. Combiner les deux — un agent qui produit un certificat semi-formel, puis un vérificateur formel qui contrôle la cohérence du certificat — donnerait des garanties plus solides sans renoncer à la flexibilité.

Enfin, une question reste suspendue. Les benchmarks utilisés (SWE-bench, Defects4J) sont anciens et présents dans les corpus d'entraînement des LLM modernes. Les auteurs reconnaissent le risque de contamination et argumentent que leurs conclusions sont relatives (semi-formel contre standard, à modèle constant) plutôt qu'absolues. C'est honnête, mais ça laisse ouverte la question de la généralisation à des dépôts inédits, écrits dans des langages ou frameworks moins représentés. L'argument structurel — le gabarit oblige à explorer plutôt qu'à mémoriser — est plausible, mais reste à prouver hors distribution.

Au-delà du résultat technique, ce papier propose un cadre mental utile pour quiconque travaille avec des agents LLM. La performance d'un agent dépend autant de la forme imposée à son raisonnement que de la puissance du modèle sous-jacent. Concevoir un agent, c'est concevoir le protocole que l'agent doit suivre. Le code n'a pas changé. Le modèle non plus. Seul le formulaire a changé — et avec lui, dix points de précision.
