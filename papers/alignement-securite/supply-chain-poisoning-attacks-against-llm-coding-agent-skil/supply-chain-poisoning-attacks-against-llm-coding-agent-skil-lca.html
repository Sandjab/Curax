Supply-Chain Poisoning Attacks Against LLM Coding Agent Skill Ecosystems

Lecture Critique d'Article

Objectif et contexte

Les agents de coding LLM (Claude Code, OpenHands, Codex, Gemini CLI) étendent leurs capacités via des agent skills téléchargés depuis des marketplaces publiques sans revue de sécurité obligatoire. Contrairement aux packages traditionnels, ces skills sont interprétés comme des directives opérationnelles dotées de privilèges système (écriture fichier, shell, réseau). La marketplace SkillsMP héberge déjà plus de 631 000 skills, et la CVE-2025-59536 a démontré l'exploitation effective de skills empoisonnés.

La question centrale est tranchée : un skill empoisonné peut-il forcer un agent à exécuter du code malveillant sur la machine hôte malgré l'alignement de sécurité du modèle et les garde-fous architecturaux du framework ? Les travaux antérieurs (ToolTweak, Skill-Inject, PoisonedRAG) restaient cantonnés à la pollution du choix d'outils ou de la génération textuelle, sans jamais atteindre l'action space système.

Méthodologie

Les auteurs proposent PoisonedSkills, articulé autour de trois composants. Le premier, DDIPE (Document-Driven Implicit Payload Execution), enfouit la logique malveillante dans des blocs de code Markdown et des templates de configuration plutôt que dans des instructions impératives. Le modèle, traitant ces exemples comme des références de bonne pratique, les reproduit puis les exécute via sa boucle code-generation-then-execution.

Le second composant est un pipeline LLM en deux étapes (Claude Opus 4.6 comme générateur) : expansion de 81 seeds vers 820 échantillons, puis mutation par six opérateurs de camouflage (ContextShift, AuthorityInject, EncodingWrap, etc.) jusqu'à 1 070 skills adversariaux couvrant 15 catégories MITRE ATT&CK. Le contrôle qualité repose sur déduplication Jaccard (seuil 0,85), validation de format Markdown et linting de syntaxe.

Le troisième composant est l'évaluation : 8 combinaisons agent-modèle × 1 070 skills, classification ternaire (refus / génération / exécution) par un juge LLM (Sonnet 4.6) plus revue humaine sur 10 % stratifié (Cohen's κ = 0,88). Chaque exécution est rejouée au moins trois fois dans des conteneurs Docker isolés.

Résultats principaux

DDIPE déclenche une exécution directe sur les huit configurations testées. Sous Claude Code, la configuration la mieux défendue, le taux de contournement (BR) varie de 13,5 % (Sonnet 4.6) à 20,5 % (MiniMax-M2.5), et le taux d'exécution directe (DER) atteint 2,3 % à 13,3 %. La baseline d'injection d'instructions explicites obtient 0 % d'exécution dans cette même configuration.

L'interaction modèle/architecture est asymétrique. Pour GLM-4.7, retirer la couche architecturale de Claude Code et passer à OpenHands fait bondir le DER de 2,4 % à 27,1 % (×11,3). Pour Sonnet 4.6, le DER ne progresse que de 2,3 % à 10,7 %. Sur GLM, 219 « sleeper payloads » sont neutralisés par les contrôles architecturaux de Claude Code et activés sous OpenHands ; chez Sonnet, ce nombre tombe à 5.

Le payload le plus efficace mesure 479 octets : un script de 9 lignes modifiant pip.conf pour rediriger l'index PyPI vers un dépôt attaquant. C'est le seul échantillon exécuté par les trois modèles sous Claude Code. La brièveté contourne l'alignement parce qu'elle évite les mots-clés sémantiques (exfiltrate, reverse_shell) qui déclenchent les refus à haute confiance.

Le vote croisé multi-modèles comprime drastiquement la surface d'attaque : seuls 1,6 % des payloads contournent simultanément les trois modèles sous Claude Code, contre 13 à 20 % par modèle isolé. Quatre vulnérabilités ont été confirmées par les éditeurs (HackerOne pour Anthropic, Google VRP, Bugcrowd) et deux correctifs déployés.

Discussion et limites

Le résultat structurant tient en une phrase : les frameworks accordent des privilèges d'exécution sur la base de frontières syntaxiques (chemins, flags de permission), pas sémantiques. Un pip.conf légitime et un pip.conf empoisonné sont indistinguables par bubblewrap. La cause racine est architecturale, pas implémentationnelle.

Les limites reconnues par les auteurs sont sérieuses. Le générateur unique (Claude Opus 4.6) crée un risque d'overfitting intra-famille, partiellement atténué par le fait que Sonnet 4.6 affiche le BR le plus bas (transfert cross-family observé). DDIPE combine trois techniques de camouflage sans ablation par composant. Deux configurations dépassent 60 % de taux d'erreur (OpenHands+MiniMax, Codex+GPT-5.4), erreurs API non liées à la sécurité mais qui rendent les DER reportés conservateurs.

La comparaison Claude Code / OpenHands est observationnelle, pas une ablation contrôlée : les deux frameworks diffèrent sur plusieurs axes (sandbox, prompt système, gestion des permissions). Le DER quasi-stable de Sonnet à travers les frameworks sert toutefois de témoin naturel isolant l'alignement comme variable modératrice.

La baseline unique (injection d'instructions explicites, 0 %) gonfle artificiellement l'avantage de DDIPE. Comparer à Skill-Inject ou à des techniques d'injection indirecte plus sophistiquées réduirait probablement l'écart. L'évaluation des défenses se limite à SkillScan ; le sandboxing dynamique et l'audit LLM ne sont pas testés.

La phase de retrieval est assumée comme réussie. Dans un environnement de production avec des centaines de skills concurrents, la probabilité d'activation d'un skill empoisonné spécifique diminue mécaniquement. L'étude ne couvre pas Llama ni Cursor.

Reproductibilité

Un site de réplication anonymisé (sites.google.com/view/poisoning-agent-skills) accompagne le papier. Les paramètres sont précisés : T=0,0 pour l'évaluation, max_tokens=10 000, timeout 180 s, seuil Jaccard 0,85, K tentatives par étape borné, n≥3 répétitions. Le juge LLM est documenté et la concordance inter-annotateurs (κ=0,88) renforce la crédibilité de la classification automatique.

Les 81 seeds initiaux et les opérateurs de mutation sont décrits, mais la nature LLM-driven du pipeline rend la reproduction exacte des 1 070 échantillons impossible sans accès au prompt complet de génération. Le risque d'overfitting au famille Claude n'est pas testable sans rejouer le pipeline avec un autre générateur (e.g., GPT-5 ou Llama).

Impact et applications

Quatre vulnérabilités CVE confirmées et deux correctifs déployés en production constituent un signal fort. Le fix d'OpenHands (PR #2XX5) consiste en une simple annotation prompt-level marquant le contenu de repository comme non fiable, et réduit les trois exécutions observées à des refus — preuve que des frontières de confiance explicites au niveau prompt sont efficaces quand l'alignement sous-jacent est suffisant.

Pour les défenseurs, trois recommandations émergent : auditer la sémantique des skills au-delà des patterns lexicaux (SkillScan rate 9,3 %), scoper les permissions au niveau du skill individuel, et calibrer les défenses architecturales sur la force d'alignement du modèle. Le déploiement multi-modèles hétérogènes (ensemble voting) compresse la surface d'attaque jointe à 1,6 % et constitue le levier opérationnel le plus immédiat.

Pour les marketplaces (SkillsMP, Anthropic Skills Hub), la conclusion est sans appel : l'absence de revue obligatoire est intenable. Les 631 813 skills publiés sans audit représentent une surface d'attaque industrielle.

Positionnement dans la littérature

Le papier comble explicitement un trou identifié : ToolTweak et Skill-Inject restaient au niveau de la sélection d'outils ou de la pollution textuelle ; PoisonedRAG induit de la désinformation mais pas d'exécution ; Greshake et al. (indirect prompt injection) traitent du contexte mais via des instructions impératives bloquées par l'alignement moderne. DDIPE est la première démonstration que la supply-chain de skills peut détourner l'action space système d'un agent.

L'ancrage MITRE ATT&CK (15 catégories, 7 stades tactiques) et OWASP LLM Top 10 inscrit le travail dans une taxonomie reconnue. Les 1 070 échantillons dépassent les volumes de ToolTweak et Skill-Inject, ce qui établit un benchmark utilisable par la communauté.
